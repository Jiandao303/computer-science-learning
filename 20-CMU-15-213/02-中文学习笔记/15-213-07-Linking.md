# L07 Linking（链接）

> 开课日期：2026 年 9 月 15 日。链接是「编译」和「运行」之间那段常被忽略的工序：把多个 `.o` 拼成一个可执行文件，把所有「这里先空着」的地址填上。本讲回答三个问题：为什么需要链接器、它做了什么（符号解析 + 重定位）、它怎么做到的（静态库、动态库、PIC）。

## 1. 本节学习目标

1. 说明链接器的两个核心步骤：符号解析（symbol resolution）与重定位（relocation）。
2. 区分三种目标文件（`.o` / `a.out` / `.so`）与 ELF 的各个 section。
3. 区分全局符号、外部符号、局部符号，并说明 `static` 如何让符号变成局部符号。
4. 熟练运用强/弱符号的三条规则判断一段多文件代码能否链接、以及引用会解析到哪个定义。
5. 读懂 `objdump -r` 输出的重定位条目，并手工算出一个 `R_X86_64_PC32` 调用在链接后的位移字节。
6. 说明静态库的链接算法与「命令行顺序敏感」的根源，并给出正确写法。
7. 区分加载时动态链接与运行时动态链接，说明 `.interp`、`.dynamic`、`ldd`、`dlopen`/`dlsym` 的作用。
8. 说明为什么共享库需要 `-fpic`（位置无关代码）。

## 2. 前置知识

- **L03–L06**：汇编、`call`/`ret`、`%rip` 相对寻址、`leaq`、内存布局（Text 从 `0x400000` 开始）。
- **C 语言**：多文件编译、`extern`、`static`、头文件。
- 命令行：`gcc`、`objdump`、`readelf`、`ar`、`ldd`。

## 3. 核心概念

- **Linking（链接）**：把多个可重定位目标文件合并成一个可执行目标文件的过程。
- **Relocatable Object File（可重定位目标文件，`.o`）**：含代码与数据，可与其它 `.o` 合并；每个 `.o` 来自恰好一个 `.c`。
- **Executable Object File（可执行目标文件，`a.out`）**：可直接复制进内存执行。
- **Shared Object File（共享目标文件，`.so`）**：可在加载时或运行时动态链接；Windows 称 DLL。
- **ELF（Executable and Linkable Format，可执行与可链接格式）**：三种目标文件的统一二进制格式。
- **Symbol Resolution（符号解析）**：把每个符号引用关联到恰好一个符号定义。
- **Relocation（重定位）**：合并 section，把符号从 `.o` 内的相对位置搬到最终绝对地址，并改写所有引用。
- **Symbol Table（符号表，`.symtab`）**：条目数组，每条含名字、大小、位置。
- **Strong Symbol（强符号）**：函数、已初始化的全局变量。
- **Weak Symbol（弱符号）**：未初始化的全局变量、`extern` 声明。
- **Static Library（静态库，`.a`）**：`.o` 的归档（archive），带索引，链接时按需取用。
- **Shared Library（共享库，`.so`）**：不在可执行文件里复制代码，运行时映射一份供多进程共享。
- **PIC（Position-Independent Code，位置无关代码）**：只用 `%rip` 相对寻址，不依赖加载地址。

## 4. 通俗理解

**链接像装修后的「接线」。** 电工（编译器）在每间房里留了线头，写着「接到总闸」。总闸在哪、线要多长，电工不知道——那是整栋楼（整个程序）的事。链接器就是拿着图纸把每根线头接到正确的端子上，并把「线长」这个数字填进墙里预留的空位（重定位条目）。

**静态库像自助餐。** 你只夹你吃的菜（只把用到的 `.o` 拷进可执行文件）。盘子端走后，菜再改也与你无关。

**共享库像食堂。** 大家共用同一个大锅（内存里只有一份 `libc.so`），厨师改了配方（升级库），所有人下一顿就吃到新的——不用各自重新买菜。

**强/弱符号像「谁说了算」。** 强符号是拍板的决定（有初始值、有函数体），弱符号是「暂定、可被覆盖」。两个人都拍板就吵架（链接错误）；一个拍板一堆暂定就听拍板的；全是暂定就随便挑一个——**这正是 bug 的温床**。

## 5. 原理与推导

### 5.1 为什么需要链接器

讲义 p7–p8 给出两条理由。

**理由 1：模块化（Modularity）**

程序可以写成多个小源文件的集合，而不是一整块巨石。可以构建常用函数库（数学库、标准 C 库）。C 的头文件只**声明**类型，**定义**在库里。

**理由 2：效率（Efficiency）**

| 维度 | 收益 |
|---|---|
| 时间 | **分离编译（separate compilation）**：改一个源文件只需重编它，再重新链接，无需重编其它文件；多个文件可并行编译 |
| 空间（静态链接） | 可执行文件与运行内存映像**只含实际用到的库代码** |
| 空间（动态链接） | 可执行文件**不含**库代码；运行时库代码在所有进程间**共享一份** |

### 5.2 编译器驱动程序做了什么

讲义 p6 的流程图：

```
main.c ──[Translators: cpp, cc1, as]──> main.o ─┐
                                                ├─[Linker: ld]──> prog
sum.c  ──[Translators: cpp, cc1, as]──> sum.o  ─┘
```

```
linux> gcc -Og -o prog main.c sum.c
linux> ./prog
```

- **翻译器（Translators）**：`cpp`（预处理器）、`cc1`（C 编译器）、`as`（汇编器）。三者把 `.c` 变成 **可重定位目标文件（relocatable object file）** `.o`。
- **链接器（`ld`）**：把多个 `.o` 合成**完全链接的可执行目标文件（fully linked executable object file）**，其中含 `main.c` 与 `sum.c` 里所有函数的代码与数据。

**三种目标文件**（讲义 p12）：

| 类型 | 扩展名 | 说明 |
|---|---|---|
| 可重定位目标文件 | `.o` | 可与其它 `.o` 合并成可执行文件；每个来自一个 `.c` |
| 可执行目标文件 | `a.out` | 可直接复制进内存执行 |
| 共享目标文件 | `.so` | 特殊的可重定位文件，可在加载时或运行时动态链接；Windows 称 DLL |

**ELF 格式**（讲义 p13–p15）：三种目标文件共用一种格式，统称 **ELF 二进制（ELF binaries）**。

| Section | 内容 |
|---|---|
| ELF header | 字长、字节序、文件类型（`.o`/exec/`.so`）、机器类型 |
| Segment header table | 页大小、虚拟地址段（section）、段大小；可执行文件必需 |
| `.text` | 代码 |
| `.rodata` | 只读数据：跳转表、字符串常量等 |
| `.data` | 已初始化的全局变量 |
| `.bss` | 未初始化的全局变量；"Block Started by Symbol" / "Better Save Space"；**有 section header 但不占文件空间** |
| `.symtab` | 符号表：过程名与静态变量名、section 名与位置 |
| `.rel.text` | `.text` 的重定位信息：需要被改写的指令地址 + 如何改写 |
| `.rel.data` | `.data` 的重定位信息：需要被改写的指针数据地址 |
| `.debug` | 符号调试信息（`gcc -g`） |
| Section header table | 各 section 的偏移与大小 |

**`.bss` 不占空间**这一点很关键：`int a[1000000];` 作为全局变量只让 `.bss` 的「大小」加 4 MB，可执行文件不会真的变大——加载时内核给它映射一块全零页。

### 5.3 符号解析（Step 1）

**符号从哪来**（讲义 p9）：

```c
void swap() { … }      /* 定义符号 swap */
swap();                /* 引用符号 swap */
int *xp = &x;          /* 定义符号 xp，引用符号 x */
```

符号定义由**汇编器**存进目标文件的**符号表**（`.symtab`）。符号表是条目数组，每条含**名字、大小、位置**。符号解析就是「把每个符号引用关联到恰好一个符号定义」。

**三类链接器符号**（讲义 p16）：

| 类型 | 定义 | 例子 |
|---|---|---|
| **Global（全局）** | 由模块 m 定义，可被其它模块引用 | 非 `static` 的 C 函数、非 `static` 全局变量 |
| **External（外部）** | 被模块 m 引用，但由别的模块定义 | `printf` |
| **Local（局部）** | 只由模块 m 定义并引用 | 带 `static` 属性的函数与全局变量 |

> **「局部链接器符号」不是「局部程序变量」。** 局部程序变量（函数参数、自动变量）在栈上，**根本不在符号表里**。这是最常见的误解。

**`static` 如何改变符号**（讲义 p19）：

```c
static int x = 15;              /* 文件作用域 → .data，符号 x（local） */
int f() { static int x = 17; return x++; }   /* → 符号 x.1721（local） */
int g() { static int x = 19; return x += 14; } /* → 符号 x.1724（local） */
int h() { return x += 27; }     /* 引用文件作用域的 x */
```

编译器为**每个** `x` 的定义在 `.data` 里分配空间，并在符号表里生成**唯一名字**（如 `x`、`x.1721`、`x.1724`）。`.1721`/`.1724` 是编译器生成的编号，不同编译器/版本会不同。

**符号表里有什么**（讲义 p18 的练习）：

```c
/* symbols.c */
int incr = 1;
static int foo(int a) {
    int b = a + incr;
    return b;
}
int main(int argc, char *argv[]) {
    printf("%d\n", foo(5));
    return 0;
}
```

候选名单：`incr`、`foo`、`a`、`argc`、`argv`、`b`、`main`、`printf`、`"%d\n"`。

**答案**：`incr`（全局数据）、`foo`（局部符号——因为是 `static`）、`main`（全局函数）、`printf`（外部符号，未定义）。**不在符号表里**的是 `a`、`b`、`argc`、`argv`（自动变量，在栈上）与 `"%d\n"`（`.rodata` 里的字符串常量，无用户可见符号名）。

验证：

```
linux> readelf -s symbols.o
```

### 5.4 强符号与弱符号（Step 1 的核心难点）

讲义 p20 的定义：

| 类别 | 内容 |
|---|---|
| **Strong（强）** | 过程（函数）、**已初始化**的全局变量 |
| **Weak（弱）** | **未初始化**的全局变量、用 `extern` 声明的 |

```c
/* p1.c */              /* p2.c */
int foo = 5;   /* 强 */  int foo;   /* 弱 */
p1() {}        /* 强 */  p2() {}    /* 强 */
```

**三条规则**（讲义 p21）：

1. **不允许多个强符号**（每个条目只能定义一次）→ 否则**链接错误**。
2. **一个强符号 + 多个弱符号 → 选强符号**，所有对弱符号的引用都解析到强符号。
3. **多个弱符号 → 任选一个**（可用 `gcc -fno-common` 改变行为）。

**链接器谜题**（讲义 p22）：

| # | p1.c | p2.c | 结果 |
|---|---|---|---|
| 1 | `int x; p1(){}` | `int x; p2(){}` | 都是弱符号，引用指向**同一个未初始化的 int**——「这真的是你想要的吗？」 |
| 2 | `int x; int y; p1(){}` | `double x; p2(){}` | p2 里对 `x` 的写入**可能覆盖 `y`**——**Evil!** |
| 3 | `int x=7; int y=5; p1(){}` | `double x; p2(){}` | 同上，**Nasty!** |
| 4 | `int x=7; p1(){}` | `int x; p2(){}` | 引用指向同一个**已初始化**变量 |
| 5 | `int x; p1(){}` | `p1(){}` | **链接错误**：两个强符号 `p1` |

**谜题 2/3 的机制**：`double x;` 是弱符号，链接器把它和 p1 的 `int x` 合并，只分配 **4 字节**给 `x`。但 p2 里 `x` 的类型是 `double`，赋值会写 **8 字节**——多出的 4 字节就覆盖了紧邻的 `y`。

> **最重要的一句话（讲义 p22）**：**链接器不做类型检查（Linker does not do type checking）。**

**类型不匹配的极端例子**（讲义 p23）：

```c
/* mismatch-variable.c */     /* mismatch-main.c */
double x = 3.14;   /* 强 */    long int x;        /* 弱 */
                               int main(int argc, char *argv[]) {
                                   printf("%ld\n", x);
                                   return 0;
                               }
```

**编译无任何错误或警告。** 打印什么？取决于 `x` 那 4 字节被怎样解释成 `long`——通常是垃圾值。两个文件各自看到不同的 `x` 类型，编译器无从发现。

**全局变量的实践建议**（讲义 p24）：

- **尽量避免全局变量。**
- 必须用时：能用 `static` 就用 `static`（变成局部符号，不会被别的模块撞上）。
- **定义**全局变量时**要初始化**（变成强符号，冲突时立刻报错而不是悄悄合并）。
- **引用**外部全局变量时用 `extern`（被视为弱符号；但若某处没有定义，会报链接错误）。

**`extern` 在头文件里的正确用法**（讲义 p25）：

```c
/* global.h */
extern int g;    /* 声明，不分配空间 */
int f();

/* c1.c */
#include "global.h"
int f() { return g + 1; }

/* c2.c */
#include <stdio.h>
#include "global.h"
int g = 0;       /* 唯一的定义 */
int main(int argc, char *argv[]) {
    int t = f();
    printf("Calling f yields %d\n", t);
    return 0;
}
```

头文件放 `extern` 声明，**恰好一个** `.c` 放真正的定义——这是 C 里「定义一次、声明多次」的标准做法。

### 5.5 重定位（Step 2）

**做什么**（讲义 p11）：

1. 把各 `.o` 的代码段与数据段**合并**成单个 section。
2. 把符号从 `.o` 内的**相对位置**搬到可执行文件里的**最终绝对地址**。
3. **改写**所有对这些符号的引用，反映新位置。

讲义 p27 的图：`main.o` 的 `.text`/`.data` 与 `sum.o` 的 `.text`/`.data` 合并进可执行文件的 `.text`/`.data`，再加上「系统代码/系统数据」。

**重定位条目**（讲义 p28），`objdump -r -d main.o`：

```
0000000000000000 <main>:
   0: 48 83 ec 08        sub    $0x8,%rsp
   4: be 02 00 00 00     mov    $0x2,%esi
   9: bf 00 00 00 00     mov    $0x0,%edi      # %edi = &array
                 a: R_X86_64_32 array            # ← 重定位条目
   e: e8 00 00 00 00     callq  13 <main+0x13>  # sum()
                 f: R_X86_64_PC32 sum-0x4        # ← 重定位条目
  13: 48 83 c4 08        add    $0x8,%rsp
  17: c3                 retq
```

**注意**：`.o` 里的地址从 **0** 开始（`main` 在偏移 0），占位符全是 `00 00 00 00`——汇编器不知道 `array` 和 `sum` 最终在哪，只能留空并写一条「待填」记录。

**链接后**（讲义 p29），`objdump -d prog`：

```
00000000004004d0 <main>:
  4004d0: 48 83 ec 08        sub    $0x8,%rsp
  4004d4: be 02 00 00 00     mov    $0x2,%esi
  4004d9: bf 18 10 60 00     mov    $0x601018,%edi  # %edi = &array
  4004de: e8 05 00 00 00     callq  4004e8 <sum>    # sum()
  4004e3: 48 83 c4 08        add    $0x8,%rsp
  4004e7: c3                 retq
00000000004004e8 <sum>:
  4004e8: b8 00 00 00 00     mov    $0x0,%eax
  4004ed: ba 00 00 00 00     mov    $0x0,%edx
  4004f2: eb 09              jmp    4004fd <sum+0x15>
  4004f4: 48 63 ca           movslq %edx,%rcx
  4004f7: 03 04 8f           add    (%rdi,%rcx,4),%eax
  4004fa: 83 c2 01           add    $0x1,%edx
  4004fd: 39 f2              cmp    %esi,%edx
  4004ff: 7c f3              jl     4004f4 <sum+0xc>
  400501: f3 c3              repz   retq
```

**逐个算清两处重定位。**

**（1）`R_X86_64_32 array` —— 绝对 32 位地址**

- 公式：`值 = S + A`（S = 符号最终地址，A = 加数）。
- 这里 `A = 0`，`array` 最终地址 `S = 0x601018`。
- 填入字段位置偏移 `0xa`（4 字节）：`18 10 60 00`（小端）→ `mov $0x601018,%edi`。
- **含义**：指令里直接编码了绝对地址 `0x601018`。

> **重要后果**：`R_X86_64_32` 只有 32 位，所以**非 PIE 可执行文件必须被加载到 4 GB 以下**。这就是经典 `0x400000` 基址的由来。

**（2）`R_X86_64_PC32 sum-0x4` —— PC 相对 32 位位移**

- 公式：`值 = S + A - P`（P = 被改写字段本身的地址）。
- 字段在 `0xf`（`e8` 在 `0xe`，位移字段在 `0xf`），`A = -4`。
- 链接后：`P = 0x4004df`，`S = 0x4004e8`（`sum` 的地址）。
- `值 = 0x4004e8 + (-4) - 0x4004df = 0x4004e8 - 0x4004e3 = 0x00000005`。
- 填入：`e8 05 00 00 00`。

**为什么加数是 `-4`？** CPU 计算 `call` 目标时用的是「**下一条指令**的地址 + 位移」，而下一条指令地址 = 字段地址 + 4。所以位移必须等于 `S - (P + 4)` = `S + (-4) - P`。`-4` 就是在把「以字段开头为基准」换算成「以字段结尾为基准」。

**讲义 p29 的原话**：「callq instruction uses PC-relative addressing for sum(): **0x4004e8 = 0x4004e3 + 0x5**」——`0x4004e3` 是 `callq` 的下一条指令地址（`add` 的起始），`0x5` 就是那 4 个字节 `05 00 00 00`。

**PC 相对寻址的好处**：位移与代码被加载到哪里无关。代码整体平移 1000 字节，`sum` 与 `call` 的**相对距离**不变，位移 `0x5` 依然是 `0x5`。这就是 PIC 的基础。

**2027 年的编译器输出**（讲义 p30–p31）：现代 GCC 默认生成 **PIE（Position-Independent Executable，位置无关可执行文件）**，两处都变成 PC 相对：

```
   9: 48 8d 3d 00 00 00 00   lea    0x0(%rip),%rdi   # 取 array 的地址
                 c: R_X86_64_PC32  array-0x4
  10: e8 00 00 00 00         call   15 <main+0x15>
                11: R_X86_64_PLT32 sum-0x4
```

两处变化：

1. **`mov $imm32,%edi` → `lea 0x0(%rip),%rdi`**：不再把绝对地址塞进指令，而是用 RIP 相对偏移算地址。
2. **`R_X86_64_32` → `R_X86_64_PC32`**；`R_X86_64_PC32` → **`R_X86_64_PLT32`**（PLT = Procedure Linkage Table，过程链接表；允许链接器在需要时改走 PLT 跳板，动态链接时必需）。

讲义 p31 还多了一条 `endbr64`（`f3 0f 1e fa`）——这是 **CET（Control-flow Enforcement Technology，控制流强制技术）** 的间接跳转合法入口标记，与 L06 的 ROP 防护直接相关。

**链接后的 PIE 版本**（讲义 p32）：

```
0000000000001129 <main>:
    1129: f3 0f 1e fa        endbr64
    112d: 48 83 ec 08        sub    $0x8,%rsp
    1131: be 02 00 00 00     mov    $0x2,%esi
    1136: 48 8d 3d d3 2e 00 00  lea  0x2ed3(%rip),%rdi   # <array>
    113d: e8 05 00 00 00     call  1147 <sum>
    1142: 48 83 c4 08        add   $0x8,%rsp
    1146: c3                 ret
```

验证 `lea`：下一条指令在 `0x113d`，`0x113d + 0x2ed3 = 0x4010`——`array` 在 PIE 里的偏移是 `0x4010`。**注意这里没有 `0x400000` 基址**：PIE 的链接地址从 0 附近开始，加载时再加一个随机的基址（ASLR）。

验证 `call`：下一条指令在 `0x1142`，`0x1142 + 5 = 0x1147` ✓。

### 5.6 加载可执行文件

讲义 p33 的图：可执行文件被加载器（loader）复制进内存，形成：

```
高地址  ┌──────────────────────┐
       │  User stack          │  ← %rsp，运行时创建
       ├──────────────────────┤
       │  Memory-mapped region│
       │  for shared libraries│
       ├──────────────────────┤
       │  Run-time heap       │  ← brk，malloc 创建
       ├──────────────────────┤
       │  Read/write data seg │  (.data, .bss)
0x400000├──────────────────────┤
       │  Read-only code seg  │  (.init, .text, .rodata)
0      └──────────────────────┘
```

**注意「从可执行文件加载」的部分只有 code segment 与 data segment**；heap 与 stack 是**运行时**创建的（「invisible to user code」指内核虚拟内存部分）。这一段与 L06 的内存布局图完全一致，只是这里强调「哪些来自磁盘上的文件」。

### 5.7 静态库

**问题**（讲义 p35）：如何打包常用函数（数学、I/O、内存管理、字符串）？

- 方案 1：全放进一个源文件 → 每个程序都链接这个巨大 `.o`，**空间与时间都低效**。
- 方案 2：每个函数一个源文件，程序员显式链接需要的 → 高效但**负担重**。

**静态库方案**（讲义 p36）：

- **静态库（`.a` archive file）**：把相关的 `.o` 用**索引**（archive）串成一个文件。
- 增强链接器：遇到未解析的外部引用时，去一个或多个 archive 里找符号。
- **若某个 archive 成员能解析引用，就把它链接进可执行文件。**

**创建**（讲义 p37）：

```
unix> ar rs libc.a atoi.o printf.o … random.o
```

`ar` 支持增量更新：只重编改动的函数，用新的 `.o` 替换 archive 里的旧文件。

**常见库的规模**（讲义 p38）：

| 库 | 大小 | 成员数 | 内容 |
|---|---|---|---|
| `libc.a` | 4.6 MB | **1496** 个 `.o` | I/O、内存分配、信号、字符串、日期时间、随机数、整数数学 |
| `libm.a` | 2 MB | **444** 个 `.o` | 浮点数学（`sin`、`cos`、`tan`、`log`、`exp`、`sqrt`…） |

```
% ar -t libc.a | sort
…
fork.o
…
fprintf.o
fpu_control.o
fputc.o
freopen.o
fscanf.o
fseek.o
fstab.o
…
```

**链接算法**（讲义 p41）——这是本讲最实用的一段：

1. **按命令行顺序**扫描 `.o` 与 `.a` 文件。
2. 扫描过程中维护一个**当前未解析引用列表**。
3. 每遇到一个新的 `.o` 或 `.a`，尝试用其中定义的符号解析列表里的每个未解析引用。
4. 扫描结束时若列表非空 → **报错**。

**关键后果：命令行顺序有影响。**

```
unix> gcc -L. libtest.o -lmine        # ✓ 正确
unix> gcc -L. -lmine libtest.o        # ✗ 错误
libtest.o: In function 'main':
libtest.o(.text+0x4): undefined reference to 'libfun'
```

**为什么？** 链接器先扫 `-lmine` 时，未解析列表是**空的**（还没看到 `libtest.o` 的引用），于是 archive 里一个成员都不取。等扫到 `libtest.o`、发现需要 `libfun` 时，`-lmine` 已经过去了，不再回头。

**口诀（讲义 p41）**：**把库放在命令行末尾（put libraries at the end of the command line）。**

**循环依赖的补救**：若 `libA` 依赖 `libB`、`libB` 又依赖 `libA`，可用 `-Wl,--start-group -lA -lB -Wl,--end-group` 让链接器在这组库之间反复扫描。这是 GNU ld 的扩展，不属于标准。

### 5.8 共享库

**静态库的缺点**（讲义 p42）：

1. **存储重复**：每个可执行文件都存一份库代码（每个程序都要 `libc`）。
2. **运行内存重复**：每个运行中的进程各有一份。
3. **修 bug 要重链接**：系统库的小修小补要求每个应用显式重新链接——「用 glibc 重编一切？」讲义引用 Google 安全博客的 CVE-2015-7547（glibc `getaddrinfo` 栈溢出）说明这个痛点。

**共享库方案**（讲义 p43）：包含代码与数据的 `.o`，在**加载时或运行时**被动态加载并链接进应用。也称**动态链接库（dynamic link library, DLL）**、`.so` 文件。

**两种动态链接时机**（讲义 p44）：

| 时机 | 说明 | 典型用途 |
|---|---|---|
| **加载时链接（load-time linking）** | 可执行文件首次加载运行时，由**动态链接器 `ld-linux.so`** 自动处理；Linux 常见情形，标准 C 库 `libc.so` 通常这样链接 | 绝大多数程序 |
| **运行时链接（run-time linking）** | 程序**开始运行之后**，通过 `dlopen()` 接口 | 软件分发插件、高性能 Web 服务器、运行时库插入（interpositioning） |

**共享库可被多个进程共享**（讲义 p44 小注：等学虚拟内存时再展开——每个进程的页表把同一份物理页映射到自己的地址空间）。

**动态库信息存在哪**（讲义 p45）：

| Section | 内容 |
|---|---|
| `.interp` | 指定要用的动态链接器（如 `ld-linux.so`） |
| `.dynamic` | 指定依赖的动态库名字等 |

```
(NEEDED)  Shared library: [libm.so.6]
```

**库在哪里？用 `ldd` 查**（讲义 p45，以 cachelab 的 `csim-ref` 为例）：

```
unix> ldd csim-ref
  linux-vdso.so.1 =>  (0x00007ffc195f5000)
  libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007f345eda6000)
  /lib64/ld-linux-x86-64.so.2 (0x00007f345f181000)
```

- `linux-vdso.so.1` 是内核提供的「虚拟动态共享对象」，没有实体文件（`gettimeofday` 之类可避免系统调用开销）。
- `ld-linux-x86-64.so.2` 是动态链接器本身。
- 地址都在 `0x7f...`——与 L06 内存布局中的「shared libraries」区域一致。

**加载时动态链接**（讲义 p46）：

```
unix> gcc -shared -o libvector.so addvec.c multvec.c -fpic
```

流程：翻译器把 `main2.c` 编成 `main2.o` → 链接器把 `main2.o` 与 `libvector.so`/`libc.so` 的**重定位与符号表信息**（不含代码）合成**部分链接的可执行文件（partially linked executable）** → 加载器 `execve` 启动 → **动态链接器 `ld-linux.so`** 把库的代码与数据真正装入内存并完成最后的重定位 → 内存中的**完全链接可执行文件**。

**`-fpic`**：生成**位置无关代码（Position-Independent Code）**。共享库被映射到哪个地址在编译时未知，所以库内所有对全局数据/函数的引用都必须用 `%rip` 相对寻址（或经 GOT/PLT 间接寻址），不能写死绝对地址。

**运行时动态链接**（讲义 p47–p48）：

```c
#include <stdio.h>
#include <stdlib.h>
#include <dlfcn.h>

int x[2] = {1, 2};
int y[2] = {3, 4};
int z[2];

int main(int argc, char **argv) {
    void *handle;
    void (*addvec)(int *, int *, int *, int);
    char *error;

    /* 动态加载包含 addvec() 的共享库 */
    handle = dlopen("./libvector.so", RTLD_LAZY);
    if (!handle) { fprintf(stderr, "%s\n", dlerror()); exit(1); }

    /* 取得刚加载的 addvec() 的指针 */
    addvec = dlsym(handle, "addvec");
    if ((error = dlerror()) != NULL) { fprintf(stderr, "%s\n", error); exit(1); }

    /* 现在可以像普通函数一样调用 */
    addvec(x, y, z, 2);
    printf("z = [%d %d]\n", z[0], z[1]);

    /* 卸载共享库 */
    if (dlclose(handle) < 0) { fprintf(stderr, "%s\n", dlerror()); exit(1); }
    return 0;
}
```

**五个 API**：

| 函数 | 作用 |
|---|---|
| `dlopen(path, flag)` | 加载共享库，返回句柄；`RTLD_LAZY` 表示符号在首次使用时才解析 |
| `dlsym(handle, name)` | 在库里查找符号，返回地址 |
| `dlerror()` | 返回上一次错误的字符串（无错误返回 `NULL`） |
| `dlclose(handle)` | 卸载 |
| 链接时加 `-ldl` | 早期 glibc 需要；glibc 2.34 起 `libdl` 已并入 `libc` |

**`void (*addvec)(int *, int *, int *, int)`** 这个声明值得注意：`addvec` 是**函数指针**，其类型必须与库里的函数签名手工保持一致——**编译器无法校验**（名字是运行时字符串 `"addvec"`）。这是 `dlsym` 最危险的地方。

### 5.9 谜题重演：类型不匹配的真实后果

讲义 p49–p51 把 5.4 节的谜题做成可运行程序。

```c
/* int.c */
#include <stdio.h>
char x = 'c';
int y = 2;
extern void p2();
void p1() {
    x = 'a';
    p2();
    printf("x=%d y=%d\n", x, y);
}

/* double.c */
#include <stdio.h>
extern void p1();
double x;
void p2() {
    printf("x=%f\n", x);
    x = 20000.00002;
}
int main() { p1(); }
```

**分析**：

- `int.c` 里 `x` 是 **`char`**（1 字节）、`y` 是 `int`（4 字节），两者在 `.data` 里紧邻。
- `double.c` 里 `x` 是 **`double`**（8 字节）——未初始化全局，**弱符号**。
- 链接器合并两个 `x`，按强符号（`char x = 'c'`）分配 **1 字节**。
- `p2` 里 `x = 20000.00002` 按 `double` 写 **8 字节**，越过 `x` 覆盖了后面的 `y`。

**实测输出（讲义 p50，链接顺序 1）**：

```
x=0.000000
x=-42 y=1087604736
```

- 第一行：`p2` 把 `x` 当 `double` 读，8 字节里主要是零 → `0.000000`。
- 第二行：`p1` 把同一个位置当 `char` 读 → `-42`（`double 20000.00002` 的最低字节被当作有符号 char）；把 `y` 当 `int` 读 → **`1087604736`**，即 `0x40D3xxxx`——**`y` 被 `double` 写入的高 4 字节覆盖了**。

**实测输出（讲义 p51，链接顺序 2：`double.o` 在 `int.o` 之前）**：

```
x=0.000000
x=-42 y=2
```

**`y` 保住了**——因为链接顺序变了，`y` 被放在 `x` 之前（或远离 `x`）的位置，8 字节写入没碰到它。

**两个结论**：

1. **同一个程序，只改链接顺序，行为就变了。** 这是「未定义行为」最直观的演示——不是崩溃，而是**悄悄给出不同的错误答案**。
2. **`gcc` 全程没有任何警告。** 两个编译单元各自看来都完全合法。

> 待核实：讲义 p50 的命令行以 `-fno-common` 出现。GCC 10 起 `-fno-common` 已是默认，此时 `double x;` 会成为**强符号**，与 `char x = 'c'` 构成「两个强符号」而应当链接报错。讲义 p3 的免责声明也提到「部分例子可能与链接器默认值/术语不一致」。因此上面的实测输出应以讲义为准，在现代工具链上复现时可能需要加 `-fcommon`。

**示例 D：加载时链接 vs 运行时链接的对照**

```c
/* dl_demo.c —— 非官方示例，仅用于说明概念 */
#include <stdio.h>
#include <dlfcn.h>

int main(void) {
    void *h = dlopen("./libmine.so", RTLD_LAZY);
    if (!h) { printf("dlopen failed: %s\n", dlerror()); return 1; }

    int (*f)(void) = (int (*)(void))dlsym(h, "libfun");
    const char *e = dlerror();
    if (e) { printf("dlsym failed: %s\n", e); dlclose(h); return 1; }

    printf("libfun() = %d\n", f());
    dlclose(h);
    return 0;
}
```

```

$ gcc -o dl_demo dl_demo.c -ldl
$ ./dl_demo

```

## 7. 容易混淆的概念

| 概念 A | 概念 B | 区别 |
|---|---|---|
| 符号解析（step 1） | 重定位（step 2） | 前者「把引用绑定到唯一一个定义」；后者「把地址填进指令/数据的空位」 |
| 强符号 | 弱符号 | 前者是函数与已初始化全局变量；后者是未初始化全局变量与 `extern` |
| 局部链接器符号 | 局部程序变量 | 前者是 `static` 函数/全局变量，**在符号表里有条目**；后者在栈上，**不在符号表里** |
| `.data` | `.bss` | 前者存已初始化全局变量，**占文件空间**；后者存未初始化全局变量，**不占文件空间** |
| `.o` | `a.out` | 前者地址从 0 开始、含重定位条目；后者地址已定、可直接加载 |
| 静态库 `.a` | 共享库 `.so` | 前者代码**复制进**可执行文件；后者只留「依赖声明」，运行时映射 |
| 加载时链接 | 运行时链接 | 前者由 `ld-linux.so` 在 `execve` 后自动完成；后者由程序自己 `dlopen` |
| `R_X86_64_32` | `R_X86_64_PC32` | 前者填**绝对地址**（限 4 GB 以下）；后者填**相对位移**（位置无关） |
| `mov $addr,%edi` | `lea 0x0(%rip),%rdi` | 前者需要绝对地址（非 PIE）；后者算 RIP 相对地址（PIE） |
| `-fpic` | `-fPIC` | 前者小模式（GOT ≤ 32 KB，快）；后者大模式（无限制）。共享库通常用后者更稳妥 |
| `-shared` | `-static` | 前者生成 `.so`；后者强制全部静态链接 |
| `dlopen` 失败 | `dlsym` 失败 | 前者是「库找不到/加载失败」；后者是「库加载了但没有这个名字」 |
| 命令行 `-lfoo` 位置靠前 | 位置靠后 | 靠前 → 未解析列表还空着，**一个成员都不取**；靠后 → 正确 |
| 链接错误 | 运行错误 | 前者（多强符号、未定义引用）在链接时发现；后者（强/弱合并、类型不匹配）**静默通过**，运行时才发作 |

## 10. 本节复习

- 链接器两步：**符号解析**（引用 → 唯一定义）+ **重定位**（合并 section、填地址）。
- `gcc` 驱动链：`cpp` → `cc1` → `as` → `.o` → `ld` → `a.out`。
- 三种目标文件：`.o`（可重定位）、`a.out`（可执行）、`.so`（共享）；统一格式 ELF。
- `.bss` 有 section header 但**不占文件空间**。
- 三类链接器符号：global、external、local；**local 链接器符号 ≠ 局部变量**。
- `static` 让符号变局部，编译器给它唯一名字（`x.1721`）。
- 强符号 = 函数 + 已初始化全局；弱符号 = 未初始化全局 + `extern`。
- 三条规则：多强 → 错误；强 + 多弱 → 选强；多弱 → 任选。
- **链接器不做类型检查**——这是强/弱符号所有坑的根源。
- 全局变量：能不用就不用；必须用则 `static`、**定义时初始化**、引用时 `extern`。
- `R_X86_64_32`：填绝对地址；`R_X86_64_PC32`：填 `S + A - P` 相对位移，`A = -4`。
- PIE 用 `lea 0x0(%rip),%rdi` 取代绝对地址 `mov`；调用用 `R_X86_64_PLT32`。
- 静态库 `.a` 是带索引的 `.o` 归档；`ar rs` 创建。
- **链接器按命令行顺序扫描，库必须放末尾**；否则未解析列表为空时库被跳过。
- 共享库优点：存储不重复、内存共享一份、升级库不用重链接。
- `.interp` 指定动态链接器，`.dynamic` 列出依赖库；`ldd` 查看依赖。
- `-fpic`/`-fPIC` 生成位置无关代码，共享库必需。
- 运行时链接：`dlopen` → `dlsym` → 调用 → `dlclose`；`dlsym` 的函数签名**编译器不校验**。

## 11. 自我检查

**题 1**：下面三个文件链接时会发生什么？如果发生错误，是哪条规则？

```c
/* a.c */  int x = 1;  void fa(void) {}
/* b.c */  int x;      void fb(void) {}
/* c.c */  int x = 2;  void fc(void) {}
/* main.c */ int main(void) { return 0; }
```

<details><summary>参考答案</summary>

**链接错误。**

- `a.c` 的 `int x = 1;` → **强符号**
- `b.c` 的 `int x;` → **弱符号**
- `c.c` 的 `int x = 2;` → **强符号**

`x` 有**两个强定义**（`a.c` 与 `c.c`），违反**规则 1（不允许多个强符号）**。

典型报错：

```
multiple definition of `x'; a.o:(.data+0x0): first defined here
```

**修正**：把 `c.c` 的 `int x = 2;` 改成 `extern int x;`，或把两个强定义合并成一个。

**注意**：若把 `a.c` 和 `c.c` 都改成 `int x;`（都弱），则不报错，链接器**任意挑一个**——`x` 的初值可能是 0，也可能是别的模块里的值。这类 bug 静默通过编译与链接。

</details>

**题 2**：某 `.o` 的反汇编如下，链接后 `foo` 落在 `0x401136`，该 `call` 指令落在 `0x401020`（`e8` 所在地址）。位移字段应填什么？

```
  401020: e8 00 00 00 00    callq  401025 <bar+0x25>
                  401021: R_X86_64_PC32  foo-0x4
```

<details><summary>参考答案</summary>

**已知**：

- 指令（`e8`）在 `0x401020`，长度 5 字节 → **下一条指令在 `0x401025`**。
- 位移字段在 `0x401021`，加数 `A = -4`。
- 目标 `S = 0x401136`。

**计算**：

```
位移 = S - 下一条指令地址
     = 0x401136 - 0x401025
     = 0x111
```

用公式 `S + A - P` 验证（`P = 0x401021`）：

```
0x401136 + (-4) - 0x401021 = 0x401136 - 0x401025 = 0x111  ✓
```

**填入的 4 字节**（小端）：

```
11 01 00 00
```

**完整指令**：`e8 11 01 00 00`。

**验证**：CPU 执行时算 `0x401025 + 0x111 = 0x401136` ✓。

**要点**：位移是**相对下一条指令**而不是相对本条指令开头；`-4` 的加数正是为了把基准从「字段起始」搬到「字段结尾」。

</details>

**题 3**：为什么 `gcc -L. -lmine libtest.o` 会报 `undefined reference`，而 `gcc -L. libtest.o -lmine` 正常？

<details><summary>参考答案</summary>

**链接器的扫描算法**（讲义 p41）：按命令行顺序扫描 `.o` 与 `.a`，维护一个「当前未解析引用列表」；每遇到一个新文件，尝试用它的符号解析列表中的项；扫描结束时列表非空则报错。**archive 只在「当前有未解析引用」时才会被取用**。

**顺序 1（错误）**：`-lmine libtest.o`

1. 扫到 `-lmine`：此时**还没看到 `libtest.o`**，未解析列表是**空的**。链接器认为「没有需要从 `libmine.a` 里取的东西」，于是**一个成员都不链接**。
2. 扫到 `libtest.o`：发现引用了 `libfun`，加入未解析列表。
3. 扫描结束，`libfun` 仍未解析 → **报错**。

**顺序 2（正确）**：`libtest.o -lmine`

1. 扫到 `libtest.o`：`libfun` 进入未解析列表。
2. 扫到 `-lmine`：列表非空，检查 archive 索引，发现 `mine.o` 定义了 `libfun` → **把 `mine.o` 链接进来**，列表清空。
3. 扫描结束，列表为空 → **成功**。

**核心**：`.o` 文件**总是**被完整链接（无论是否需要），而 `.a` 里的成员**按需**取用。因此 `.o` 必须排在 `.a` 之前。

**口诀**：库放命令行末尾。

**补充**：若 `libA` 与 `libB` 互相依赖，可用

```
-Wl,--start-group -lA -lB -Wl,--end-group
```

让链接器在这组库之间反复扫描直到收敛。

</details>

**题 4**：`static int x = 15;`（文件作用域）、`static int x = 17;`（函数 `f` 内）、`static int x = 19;`（函数 `g` 内）在符号表里分别叫什么？为什么必须改名？

<details><summary>参考答案</summary>

**名字**：

| 定义 | 符号名 | 绑定 |
|---|---|---|
| 文件作用域 `static int x = 15;` | `x` | LOCAL |
| `f` 内 `static int x = 17;` | `x.1721`（编号由编译器生成，会变） | LOCAL |
| `g` 内 `static int x = 19;` | `x.1724`（同上） | LOCAL |

**存在位置**：三份都在 `.data` 里（因为**已初始化**；若写成 `static int x;` 则在 `.bss`）。

**为什么必须改名**：符号表是**按名字索引**的。三个 `x` 若同名，汇编器/链接器无法区分「`f` 里要访问哪一个」。编译器给每个局部静态变量生成**唯一名字**，让它们在同一张符号表里共存而互不冲突。

**为什么编号会变**：编号是编译器的内部计数器产物，取决于编译顺序、优化级别、编译器版本。**不要依赖具体数字**（比如在 `objdump` 输出里 grep `x.1721`）——它下次编译就可能变成 `x.1720`。

**关键对比**：`static` 的「局部」是**链接意义上的局部**（别的模块看不到、不会撞名），而**不是存储期意义上的局部**。这些变量的生命周期是**整个程序运行期**，与自动变量完全不同：

```c
int f() { static int x = 17; return x++; }   /* 每次调用返回 17,18,19... */
int g() { int x = 17; return x++; }          /* 永远返回 17 */
```

</details>

**题 5**：讲义 p49–p51 的程序在两种链接顺序下分别输出 `y=1087604736` 与 `y=2`。请解释 `1087604736` 是怎么来的，以及为什么改链接顺序就能「修好」它。

<details><summary>参考答案</summary>

**代码要点**：

- `int.c`：`char x = 'c';`（强符号）、`int y = 2;`
- `double.c`：`double x;`（弱符号）、`p2()` 里 `x = 20000.00002;`

**机制**：

1. 链接器合并两个 `x`。按**规则 2**（强 + 弱 → 选强），采用 `int.c` 的 `char x`，只分配 **1 字节**。
2. 但 `double.c` 在**编译时**看到的是 `double x`，生成的代码写 **8 字节**：`movsd` 一条指令覆盖 `x` 及其后 7 字节。
3. `y` 紧跟在 `x` 之后（`x` 占 1 字节 + 对齐填充，`y` 落在 `x+4` 附近），于是 `y` 被 `double` 的高 4 字节覆盖。

**`1087604736` 的来源**：它是 `0x40D3_xxxx` 量级的值。`20000.00002` 的 IEEE 754 双精度指数部分是 `0x40D`（1023 + 14 = 1037 = `0x40D`）。**`y` 装进去的正是这个 double 的高 32 位**——即「指数 + 高位尾数」，`1087604736 = 0x40D38800`。

> 待核实：`0x40D38800` 与 `1087604736` 的对应关系按 `20000.00002` 的近似位模式推算；精确低 32 位取决于该字面量的舍入结果，讲义只给出了十进制输出。

**为什么改顺序就好**：链接器把各 `.o` 的 `.data` **按命令行顺序拼接**。`int.o` 先链接时，`x`、`y` 依次排布，`y` 就在 `x` 后面；`double.o` 先链接时，布局改变，`y` 被排到别处（或 `x` 后面留了足够的对齐空隙），8 字节写入不再命中 `y`。

**结论**：

1. **这不是「修好」，只是「碰巧没坏」。** 程序依然有未定义行为——两个编译单元对 `x` 的类型认知不一致。换编译器、换优化级别、加一个变量，结果就可能再变。
2. **编译器与链接器全程零警告。** 各自的编译单元内部完全合法。
3. 正确的修法只有一个：**让两处声明的类型一致**（这里应把 `double.c` 的 `double x;` 改成 `extern char x;`，或把定义收进一个头文件）。

</details>
