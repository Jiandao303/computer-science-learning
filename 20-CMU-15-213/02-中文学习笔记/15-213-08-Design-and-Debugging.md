# L08 Design and Debugging（设计与调试）

> 开课日期：2026 年 9 月 17 日。这是全课唯一一讲**不讲机器、只讲人**的课：前半讲如何系统地找出缺陷（科学调试法），后半讲如何写出「让人能读懂」的代码。讲义开头提出一个贯穿全讲的问题——**好的设计与有效的调试之间是什么关系？** 答案在最后一页：**推理（reasoning）**。

## 1. 本节学习目标

1. 区分 **defect（缺陷）**、**error（错误状态）**、**failure（失效）**，并说明为什么「有缺陷不等于会失效」。
2. 复述科学调试法的六个环节：问题描述 → 假设 → 预测 → 实验 → 观察与结论 → 诊断 → 修复与确认。
3. 用「fib 未初始化」案例完整走一遍科学调试流程，并说明为什么 `-Wall -Werror` 一步就能定位它。
4. 说明为什么「换优化级别重编」和「跑 Valgrind」是低成本的暴力排查手段，以及 Valgrind 在 `-O3` 下为什么可能漏报。
5. 说出六种代码坏味道（code smell）。
6. 说明「可测试的设计」为什么等于「可调试的设计」，以及测试与契约（contract）的关系。
7. 应用讲义的命名七条实践，改写一段糟糕的命名。
8. 说明「注释写什么」与「注释不写什么」，并区分「说明代码做什么」与「说明代码为什么存在」。

## 2. 前置知识

- **L01–L07**：C 语言与机器级程序的基础；至少要能读懂简单的 C 与汇编。
- **L06**：未定义行为、栈上未初始化内存（本讲 fib 案例的根源）。
- 工具：`gcc`、`gdb`、`valgrind`（讲义 p25 只提到 gdb 与 Valgrind 两类工具）。

## 3. 核心概念

- **Defect / Fault（缺陷）**：程序员写进代码里的错误。
- **Error（错误状态）**：缺陷导致的数据值或控制信号不正确。
- **Failure（失效）**：错误传播到接口，组件或系统没有产生预期结果。
- **Latent Defect（潜伏缺陷）**：存在但当前不触发失效的缺陷。
- **Scientific Debugging（科学调试法）**：把调试当作「假设—预测—实验—观察」的循环。
- **Rubber Duck Debugging（小黄鸭调试法）**：把问题讲出来（对人、对玩偶、对纸）往往就能自己找到答案。
- **Occam's Razor（奥卡姆剃刀）**：多个假设并存时，选最简单、离当前工作最近的那个。
- **Code Smell（代码坏味道）**：暗示存在缺陷的代码形态。
- **Assertion（断言）**：检查「应该成立」的条件；**不得有副作用**。
- **Invariant（不变式）**：在程序某点必须始终成立的性质。
- **Contract（契约）**：函数的前置条件、后置条件与不变量，作为模块间的约定。
- **Separation of Concerns（关注点分离）**：每个函数只做一件事。
- **Encapsulation（封装）/ Information Hiding（信息隐藏）**：模块自己管自己的内部，外部不得侵入。
- **DRY（Don't Repeat Yourself，不要重复自己）**。

## 4. 通俗理解

**缺陷、错误、失效像「水管渗漏」。** 缺陷是那圈没拧紧的螺纹（程序员造成）；错误是水慢慢渗进墙体（状态变坏）；失效是你家天花板开始滴水（接口处可观察到）。**螺纹没拧紧不一定会滴水**——如果水压不够、或者渗出的水被防水层挡住了（**错误被屏蔽**），你永远不知道有问题。ECC 内存就是「防水层」：位翻转发生了（error），但被纠正了，没有变成 failure。

**科学调试法像医生看病。** 你不会一上来就开刀。你先问诊（问题描述），再猜「可能是胃炎」（假设），然后想「如果是胃炎，验血应该有 X 指标」（预测），去验血（实验），看结果（观察），得出结论（诊断），开药（修复），复诊（确认）。**跳过任何一步，你就是在赌博。**

**好的设计像整理过的工具箱。** 你不需要记住每个螺丝刀在哪——因为每个格子有标签、每类工具分开。**调试时你之所以能找到问题，是因为代码本来就是按「能被单独检查」的方式组织的。** 这就是讲义最后一页的答案：好的设计让「推理」成为可能。

## 5. 原理与推导

### 5.1 缺陷 → 错误 → 失效

讲义 p6 给出四步链条：

1. **程序员造成缺陷（defect / fault）。**
2. **缺陷（可能）造成错误（error）**——数据值或控制信号不对。
3. **错误传播（propagate）。**
4. **错误造成失效（failure）**——某个组件或系统在接口处没有产生预期结果。

讲义 p6 的追问：**为什么「错误」不一定变成「失效」？** 因为**错误可以被屏蔽或被检测**。例子是 **ECC 内存（Error-Correcting Code memory）**：内存位翻转发生了（这是 error），但 ECC 硬件纠正了它，程序读到的值是对的——没有 failure。

**为什么调试这么难**（讲义 p7）：

- **不是每个缺陷都会造成失效。** 缺陷可以是**潜伏的（latent）**或**活跃的（active）**。多数时候不执行的那段代码里的缺陷，永远不发作。
- **Dijkstra 1972**：「**测试只能证明缺陷的存在，不能证明缺陷的不存在。**」（Testing can only show the presence of [defects] — not their absence.）

**讲义 p8 的图**：有效状态（valid state）的圆环里有一小块「错误状态（error in state）」。代码有缺陷会引入错误状态或错误控制流；**正确的代码也可能把这个错误状态继续传播下去**（它看不出自己拿到的是坏数据）；最终某个时刻错误状态被观察到。**有些执行根本不触发缺陷，有些触发了但不传播**——所以「我跑了一遍没问题」毫无意义。

**调试的本质**（讲义 p8）：**在代码里筛找那个缺陷。**

### 5.2 显式调试：把问题说出来

讲义 p9：**陈述问题（stating the problem）**——大声或在纸上描述问题。也叫「**小黄鸭法（rubber duck / teddy bear method）**」。

关键论断：**「通常一份完整的问题描述就足以解决这个失效。」**

为什么有效？因为「描述」迫使你把隐含假设显式化。你写下「程序在 `i=1` 时返回 134513905」，就必须回答「`f` 在这一步的值是多少」——而这个问题本身就暴露了 `f` 未初始化。

### 5.3 科学调试法

讲义 p10–p12 给出完整循环。

**输入（讲义 p10）**：四个信息源——**问题描述（problem description）**、**代码（code）**、**失败的运行（failing runs）**、**其它运行（other runs）**。

**第一环：构造假设（hypothesis）**

- 调试**之前**就要先构造一个关于缺陷的假设。
- 假设要说清两件事：**可能的缺陷是什么** + **为什么它能解释这个失效条件**。
- 若完全没有想法：「**做什么实验能给我有用的信息？**」

**奥卡姆剃刀（Occam's Razor）**：多个假设并存时，**选最简单的、或离当前工作最近的那个**。不要一上来就怀疑操作系统或编译器。

**第二环：预测（prediction）**

- 基于假设做出预测：**在新条件下你预期会发生什么？**
- **什么数据能证实或推翻你的假设？**
- **我怎样收集这些数据？**——用哪些实验？用哪种采集机制？

**第三环：实验（experiment）**

讲义 p23 的关键约束：实验必须**与之前某次运行的条件完全相同，只改一个条件**。

可改的条件有三类：**程序输入**、**使用调试器**、**修改代码**。

**第四环：观察与结论（observation & conclusion）**

讲义 p24 给出四条纪律：

1. **观察必须是事实**，例如「调用 `fib(1)` 返回了 1」；**结论才做解释**。
2. **不要干扰（don't interfere）**——`printf()` 对某些 bug 会改变行为（经典的 heisenbug：加打印就消失）。
3. **系统推进（proceed systematically）**——条件**增量**更新，让每次观察只对应一个具体改动。
4. **绝不越过第一个 bug（Do NOT ever proceed past first bug）**。发现一个 bug 就先解决它，别继续往下看——后面的现象可能是它引起的。

**第五环：诊断（diagnosis）**

讲义 p26：能解释当前观察、并能做出未来预测的科学假设，就成为**理论（theory）**，这里叫**诊断**。

用诊断去开发修复。**要避免「post hoc, ergo propter hoc」谬误**（「在这之后」误当作「因为这个」）——也就是**相关不等于因果（correlation does not imply causation）**。你必须**理解缺陷与修复之间的关系**。

**第六环：修复与确认（fix and confirm）**

- 确认修复真的解决了失效。
- **若你同时修了多个「疑似缺陷」，哪一个才是真正修好这个失效的？**——所以要系统化，一次改一个。

**第七环：学习（learn）**

讲义 p28：

- 记录**常见失效与洞察**：这段代码为什么失败？**我常犯的缺陷是什么？**
- **断言与不变式（assertions and invariants）**：为预期行为加检查。**注意：断言不得有副作用**（`assert(x++)` 是错的——关掉断言后行为就变了）。
- 把检查扩展到能检测这个已修复的失效。
- **测试**：每一组成功的条件都加入测试集。

### 5.4 案例：fib 的未初始化变量

**有 bug 的代码**（讲义 p13）：

```c
int fib(int n)
{
    int f, f0 = 1, f1 = 1;
    while (n > 1) {
        n = n - 1;
        f = f0 + f1;
        f0 = f1;
        f1 = f;
    }
    return f;
}

int main(..) {
    ..
    for (i = 9; i > 0; i--)
        printf("fib(%d)=%d\n", i, fib(i));
}
```

**运行**（讲义 p13）：

```
$ gcc -o fib fib.c
fib(9)=55
fib(8)=34
...
fib(2)=2
fib(1)=134513905
```

**第一步：怎么知道这是失效？**（讲义 p13）——**它违反了规格（spec）。所以先要知道「应该发生什么」。** 规格定义第一个斐波那契数是 1，所以 `fib(1)` 应返回 1，实际返回 134513905。

**第二步：构造假设**（讲义 p14）。已知：规格说 `fib(1)=1`；有正常运行的例子（`fib(2)=2`）；有失败的运行（`fib(1)`）；读过代码。

三条候选假设：

| 代码位置 | 假设 |
|---|---|
| `for (i = 9; …)` | 结果依赖调用顺序 |
| `while (n > 1) {` | 循环条件写错了 |
| `int f;` | **`f` 未初始化** |

**第三步：预测**（讲义 p22）：

| 假设 | 预测 |
|---|---|
| 结果依赖调用顺序 | 若先调用 `fib(1)`，应能正确返回 |
| 循环条件错 | 改成 `n >= 1` 再跑 |
| `f` 未初始化 | 改成 `int f = 1;` |

**第四步：实验**（讲义 p23）：

| 实验 | 结果 |
|---|---|
| 先调用 `fib(1)` | **失败**（假设被推翻） |
| 改成 `n >= 1` | `fib(1)=2`、`fib(0)=...`（**不对**，也推翻） |
| 改成 `int f = 1;` | **成功** |

讲义 p23 的批注：**「有时候一个预测本身就是修复（Sometimes a prediction can be a fix）」**——这是科学调试法最爽的时刻。

**为什么 `fib(1)` 返回 134513905？** 当 `n = 1` 时，`while (n > 1)` 一次都不执行，`f` 从未被赋值，`return f;` 返回栈上那块内存里残留的垃圾。`134513905` 是某次运行恰好残留的值——**换个编译选项、换个机器、换个调用顺序，数字就变**。

**为什么「先调用 `fib(1)`」没能修好？** 因为 `main` 里循环是从 9 递减到 1，`fib(1)` 总是**最后**被调用；而「先调用」这个改动并没有改变「`n=1` 时 `f` 未初始化」这个事实。假设被实验推翻。

### 5.5 暴力排查：编译选项与 Valgrind

讲义 p15–p19 给出「先做最省力的事」的清单。

**第一招：编译选项 `-Wall -Werror`**

```
Prompt> gcc -Wall -Werror -O3 -o badfib badfib.c
badfib.c: In function 'fib':
badfib.c:12:5: error: 'f' may be used uninitialized in this function
     return f;
     ^
cc1: all warnings being treated as errors
```

讲义 p15 的措辞很强：

- **必须（MUST）**加 `-Wall`。
- **应该（Should）**加 `-Werror`。

**为什么 `-Werror` 重要**：警告是「可能有问题」，人会自动忽略刷屏的警告。`-Werror` 把警告变成错误，**逼你面对**。这个 bug 在 `-Wall` 下**一步定位**，比科学调试法快得多。

**第二招：换优化级别重编**

讲义 p16 的实测：

| 优化级别 | `fib(1)` | `fib(0)` |
|---|---|---|
| `-O3` | 0 | 0 |
| `-O2` | 0 | 0 |
| `-O1` | 9 | 9 |
| `-O0` | 2 | （未定义/无输出） |
| （`-O0` 且不优化，讲义 p13 的原始编译） | 134513905 | — |

**同一份源码，四个优化级别，四种不同的错误答案。** 讲义要求「**至少试 `-O3` 与 `-O0`**」。

**为什么这有用**：未定义行为的典型特征就是「**结果依赖编译器的具体决定**」。不同优化级别下栈布局、寄存器分配、是否把变量放在内存里都不同——**结果不一致本身就是「这里有未定义行为」的强信号**。

**第三招：Valgrind**

讲义 p17 的三条纪律：

1. **即使程序看起来正常也要跑**（even if your program appears to be working!）。
2. **`-O3` 与 `-O0` 都跑。**
3. **只在所有警告都消失之后才跑**（only run after all warnings are gone）——否则 Valgrind 的噪音会淹没真正的信号。

**`-O3` 下 Valgrind 漏报**（讲义 p18）：

```
prompt> gcc -g -O3 -o badfib badfib.c
prompt> valgrind badfib
==1462== Memcheck, a memory error detector
...
fib(9)=55
fib(8)=34
...
fib(2)=2
fib(1)=0
fib(0)=0
==1462==
```

**Valgrind 在 `-O3` 下一个错误都没找到！** 讲义 p18 的结论：「**Valgrind 不是完美的（Valgrind is not perfect）。**」

**为什么漏报**：`-O3` 下编译器可能把 `f` 分配到一个寄存器里，而 Valgrind 的 Memcheck 追踪的是**内存**的「已定义性」，寄存器级别的未初始化值不在它的检测范围（或者说优化把「从内存读未初始化值」这个动作消除了）。

**`-O0` 下抓到了**（讲义 p19）：

```
prompt> gcc -g -O0 -o badfib badfib.c
prompt> valgrind badfib
...
fib(2)=2
==1561== Conditional jump or move depends on uninitialised value(s)
==1561==    at 0x4E988DA: vfprintf (vfprintf.c:1642)
==1561==    by 0x4EA0F25: printf (printf.c:33)
```

讲义 p19 的结论：「**Valgrind 不是完美的，但相当不错（pretty good）。**」

**注意报错位置在 `vfprintf`**——Valgrind 报的是「**未初始化值最终被用于条件跳转**」的地方（`printf` 内部格式化数字时），而不是「变量被读取」的地方。这是 Memcheck 的典型特征：它追踪「未定义性」的**传播**，报在第一次「必须确定这个值」的地方。

**LLM 也能给假设**（讲义 p20）：讲义用一整页标题写「**LLM Gives Hypotheses Also**」——大语言模型可以作为一个假设来源。但注意它与 L01 的 AI 政策的关系：讲义 L01 p28 明确写「**YOU MAY NOT use AI to debug your code**」。**提供假设 ≠ 替你调试**，具体边界以课程当学期的 AI 政策为准。

> 待核实：讲义 p20 只有标题，无正文内容；其确切表述与课程 AI 政策的关系需查阅当学期 Canvas 公告。

**调试工具的分工**（讲义 p25）：

| 工具 | 回答什么问题 |
|---|---|
| **调试器（如 `gdb`）** | 局部/全局变量的值是什么（若已知）？程序走了哪条路径？ |
| **Valgrind** | 执行是否依赖未初始化变量？内存访问是否越界？ |

### 5.6 速战速决：给调试设时间盒

讲义 p29 给出一张极实用的表：

| 时间 | 做什么 |
|---|---|
| **0 分钟** | `-Wall`、`valgrind` |
| **1–10 分钟** | 非正式调试（informal debugging） |
| **10–60 分钟** | 科学调试法（scientific debugging） |
| **> 60 分钟** | **休息一下 / 求助** |

讲义 p29 的标题是「**Quick and Dirty**」，开头一句：「**不是每个问题都需要科学调试法。**」

**这张表的价值在于「> 60 分钟就停下」**——长时间卡住通常意味着你的假设集里缺了一个前提，而不是你需要更努力。

### 5.7 六种代码坏味道

讲义 p30：

| 坏味道 | 说明 |
|---|---|
| **使用未初始化变量（use of uninitialized variables）** | 正是 fib 案例 |
| **未使用的值（unused values）** | 算了不用，说明逻辑有误或残留代码 |
| **不可达代码（unreachable code）** | 条件永远不成立，说明前面的判断写错了 |
| **内存泄漏（memory leaks）** | `malloc` 后没有对应的 `free` |
| **接口误用（interface misuse）** | 参数顺序错、返回值忽略、`fgets` 长度算错 |
| **空指针（null pointers）** | 解引用未检查的指针 |

**这六条与 Valgrind 的检测能力高度重合**——Memcheck 恰好擅长抓未初始化值、泄漏、越界。这就是为什么讲义把它排在「0 分钟」那一档。

### 5.8 设计：可读性优先

讲义 p33 列出好设计要满足的许多目标：

- 性能（Performance）
- 可用性（Availability）
- 可修改性、可移植性（Modifiability, portability）
- 可扩展性（Scalability）
- 安全性（Security）
- **可测试性（Testability）**
- 易用性（Usability）
- 构建成本、运维成本（Cost to build, cost to operate）

讲义 p34 在**同一页**加了最后一句：

> **但最重要的是：它必须是可读的（But above all else: it must be readable）。**

**讲义 p35 的浓缩**：好设计做两件事——**复杂度管理（Complexity Management）** 与 **沟通（Communication）**。

**人脑的复杂度上限**（讲义 p36）：「人能够轻松管理的复杂度有众所周知的极限。」讲义 p37 补充：「然而，**模式（patterns）** 非常有帮助」——这就是设计模式存在的理由：把常见复杂度压缩成可识别的形状。

**复杂度管理技术**（讲义 p38）：

- 关注点分离（separation of concerns）
- 模块化（modularity）
- 可复用性（reusability）
- 可扩展性（extensibility）
- **DRY**（不要重复自己）
- 抽象（abstraction）
- 信息隐藏（information hiding）
- ……

**讲义 p39 的关键连接**：「**把代码设计成可测试的；尽量复用可测试的块。**」——这句话把后半讲（设计）和前半讲（调试）接上了。

### 5.9 复杂度实例：把大任务切成可测试的块

讲义 p40–p41 用两个例子演示「切块」。

**例 1：cache 访问（cachelab 的 csim）**——把一次访问拆成可独立测试的步骤：

1. 把地址转换成 **tag、set index、block offset**。
2. 用 set index 查找 set。
3. 检查 tag 是否与该 set 中某一行匹配。
4. 若匹配 → **hit**。
5. 若不匹配 → **miss**，然后：
   - 找到 **LRU** 块
   - 逐出 LRU 块
   - 从内存读入新行
   - 更新 LRU
   - 若这次是 store，更新 **dirty** 位

**为什么这样切有用**：每一步都能单独验证。地址解析错了？写个 5 行的测试立刻知道。LRU 更新错了？单独测。**如果全写在一个 200 行的函数里，你只能整体调试。**

**例 2：wordle 工具**：

1. 读入字典文件。
2. 为每个词创建 struct。
   - **这个 struct 适合当前复杂度/输入规模吗？**（讲义特意追问——数据结构选择本身是设计决策）
3. 从 stdin 读入猜测 + 绿/黄反馈。
4. 搜索符合约束的其它词。
5. 按「最大信息增益」排序。

**注意第 2 步的追问**：讲义在「步骤列表」里插入了一个**设计问题**。这说明「列出步骤」这个动作本身就会暴露设计问题。

### 5.10 测试与契约

讲义 p42–p43：

- **可测试设计（testable design）**：**测试（testing）** 与 **契约（contracts）** 是**互补的**两种技术。
- 它们**不只是验证，更是设计行为**（acts of design more than verification）。
- 它们**是文档行为**（acts of documentation）——讲义强调是「**可执行的文档（executable documentation）**」。

**讲义 p43 的两条推理链**：

```
好的设计 → 小部件 + 清晰的契约
清晰的契约 → 调试时可以放置假设的锚点
```

第二句是全讲最重要的连接：**调试时你做的每个实验，都需要一个「已知应该成立的东西」作为参照。契约提供了这个参照。** 如果函数没有明确的前置/后置条件，你连「这里的行为对不对」都无法判断。

### 5.11 模块化与「相信编译器」

**模块化代码具备**（讲义 p44）：关注点分离、封装（encapsulation）、抽象（abstraction）。**带来**：可复用性、可扩展性、可读性、可测试性。

**关注点分离**：

- 造辅助函数，让每个函数「只做一件事」。
- **函数既不该做太多，也不该做太少。**
- 避免重复代码。

**封装、抽象、尊重接口**：

- 每个模块对自己的内部负责。
- **外部代码不得「侵入」另一个模块的内部运作。**

> 这条与 L07 的强/弱符号、`static` 直接呼应：`static` 就是把「内部」在链接层面隐藏起来，让别的模块无法侵入。

**「相信编译器！（Trust the Compiler!）」**（讲义 p45）：

- **多用临时变量。**
- **多用函数。**
- **让编译器去做算术。**

**这三条在 15-213 语境下特别有分量**：你可能觉得「多写个临时变量会慢」「多调个函数会有开销」。但现代编译器会做内联、寄存器分配、常量传播、强度削减（L02 的 `u*24 → (u<<5)-(u<<3)`、L05 的 `5*i*4` 都是编译器干的事）。**为了「性能」而写难读的代码，通常是净损失**——你牺牲了可读性和可调试性，换来的可能是编译器本来就会做的优化。

### 5.12 沟通：代码是写给人看的

讲义 p46 列出写代码时作者在跟谁沟通：

1. **机器**
2. **系统的其他开发者**
3. **代码审查者（code reviewers）**
4. **未来的自己（their future self）**

讲义 p46 追问：**「如果你想得到最好的结果，哪一个应该是优先级？」**

答案（结合讲义整体立场）：**人**。机器不在乎可读性——编译器能读任何合法的 C。而「未来的自己」是**最常被低估的读者**：三个月后你已经忘了为什么这么写。

**沟通技术**（讲义 p47）：测试、命名、注释、提交信息（commit messages）、代码审查、设计模式……

### 5.13 命名

**避免刻意无意义的名字**（讲义 p49）。

**讲义 p50 引用 Sam Gardiner**：

> 「如果你不知道一个东西该叫什么，你就不知道它是什么。如果你不知道它是什么，你就没法坐下来写代码。」
> （If you don't know what a thing should be called, you cannot know what it is. If you don't know what it is, you cannot sit down and write the code.）

**这解释了命名为什么是设计活动**：命名困难 = 概念没想清楚。

**七条更好的命名实践**（讲义 p51）：

1. **从含义与意图出发**（start with meaning and intention）。
2. **用含义精确的词**——避免 `data`、`info`、`perform` 这类空词。
3. **名字里的词越少越好**（prefer fewer words）。
4. **避免缩写**。
5. **用代码审查来改进名字**。
6. **把代码读出声**，检查听起来是否顺。
7. **真的去改名**（actually rename things）——不要只在心里觉得该改。

**具体准则**：

| 准则 | 出处 | 要点 |
|---|---|---|
| 只用词典词与词典里的缩写 | p52 | `FileCpy` → `FileCopy`；避免 `acc`、`mod`、`auth` 这类模糊缩写 |
| 避免单字母名 | p53 | 单字母**无法搜索**、不提供任何用途提示。**例外**：循环计数器（尤其你知道 `i`、`j` 的历史来源时）；C/Unix 惯例如 `fd`（file descriptor）、`str`（字符串参数）——**遵循既有风格是好事** |
| 限制名字的字符长度 | p54 | 引用 Philip Relf：「好的命名限制单个名字的长度，并减少对专门词汇的需求」 |
| 限制名字的词数 | p55 | **最多四个词**；限制到「人一眼能读完」的词数 |
| 描述含义 | p56 | 避免 `a`、`foo`、`blah`、`tmp`。**合理例外**：`swap` 里的 `tmp` |
| 用大词汇量 | p57 | 能更具体就更具体：`Person` → `Employee` |
| 用问题领域的术语 | p58 | 用领域语言里正确的词；提示：作为学生，看作业里的术语 |
| 精确使用反义词 | p59 | 用标准配对：`first`/`last`（而不是 `first`/`end`） |

**讲义 p55 的选择题**（值得记住的对照）：

| 选项 | 名字 | 评价 |
|---|---|---|
| a1 | `arraysOfSetsOfLinesOfBlocks` | 太长，五个词，读不完 |
| a2 | `cache` | **更好**——领域里这个词就代表这个结构 |
| b1 | `evictedData` | 尚可，但没说单位 |
| b2 | `evictedDataBytes` | **更好**——两个词，说清了单位 |

**讲义 p57 的 `size` 之问**：`struct binaryTree { int size; … }` 里的 `size` 是什么？候选：`height`（高度）、`numChildren`（子节点数）、`subTreeNumNodes`（子树节点数）、`keyLength`（键长度）。**一个 `size` 可以有四种完全不同的含义**——这就是「用大词汇量」的理由。

**讲义 p58 的 cachelab 例子**：在 cachelab 里，`line` 与 `element` 是两个不同的概念（缓存行 vs 数据元素），**用错词就会写错代码**。

### 5.14 注释

**不要写的注释**（讲义 p61）：

1. **不要说代码在做什么**——代码已经说了。
2. **不要解释别扭的逻辑**——**去改进代码让它变清楚**。
3. **不要加太多注释**——很乱，而且会过时。

**别扭代码的例子**（讲义 p62）：

```c
(*(void **)((*(void **)(bp)) + DSIZE)) = (*(void **)(bp + DSIZE));
```

vs

```c
bp->prev->next = bp->next;
```

讲义 p62 的原话：**「这两行以相同方式更新程序状态。」** 追问：**你更愿意重写还是加注释？**

**答案显然是重写。** 第一行是 malloclab 里典型的「用裸指针操作双向链表」写法——它没有 bug，但没人能一眼看懂。加注释等于给烂代码贴创可贴。

> 顺带说明：第一行是 `bp->prev->next = bp->next` 的手工展开。`bp->prev` = `*(void **)bp`，`->next` 在偏移 `DSIZE` 处，所以左值是 `*(void **)(*(void **)bp + DSIZE)`；右值是 `*(void **)(bp + DSIZE)` = `bp->next`。

**应该写的注释**（讲义 p63）——回答这些问题：

- **代码为什么存在（why the code exists）**
- **什么时候该用这段代码？**
- **什么时候不该用？**
- **这段代码的替代方案是什么？**
- **这段代码背后的意图是什么？**

**解释「为什么」的例子**（讲义 p64）：

```c
// Each address is 64-bit, which is 16 + 1 hex characters
const int MAX_ADDRESS_LENGTH = 17;
```

这个注释解释了一个**魔数（magic number）**：为什么是 17？因为 64 位地址 = 16 个十六进制字符 + 1 个 `'\0'`。**没有这个注释，读者只能猜。**

同一页还有一个值得注意的例子：

```c
unsigned power2(unsigned base, unsigned expo) {
    unsigned i;
    unsigned result = 1;
    for (i = 0; i < expo; i++) {
        result += result;
    }
    return result;
}
```

**这段代码其实是错的**——它算的是 `2^expo`，完全忽略了 `base` 参数。这正好演示了「注释该写什么」的另一面：**注释「这段代码应该做什么」会立刻暴露它做错了**。参数 `base` 没被用（unused value，讲义 p30 的坏味道之一）本身就是信号。

**写注释的流程**（讲义 p65–p66）：

1. **用注释来写代码（Code by commenting!）**——先写短的注释，帮助你思考设计，克服「空白页问题（blank-page problem）」。
2. 写**单行注释**。
3. 例：为快排写四行单行注释：

```c
// Initialize locals
// Pick a pivot value
// Reorder array around the pivot
// Recurse
```

4. **然后写那些代码。**
5. **修订注释/代码**：如果代码或注释别扭或复杂，就把注释合并/拆分。
6. **维护代码与修订后的注释。**

**「先写注释再写代码」的价值**：这四行注释就是快排的骨架。如果你写不出这四行，说明你还没想清楚算法——**和命名的道理一样，表达困难 = 理解不足**。

### 5.15 提交信息

讲义 p67：把代码提交到源码仓库是开发的**关键部分**。

- **防止系统故障与手误**：`cat foo.c` vs `cat > foo.c`（后者会**覆盖**文件——一个字符的差别，毁掉全部工作）。
- **提交信息是你工作的记录**，是**给未来的自己**的沟通。
- **一行说清你做了什么**：

```
"Parses command line arguments"
"fix bug in unique tests, race condition not solved"
"seg list finished, performance is …"
```

**注意第二条**：它诚实地写了「race condition 还没解决」。**好的提交信息不掩饰未完成的部分**——这正是给未来的自己的重要信息。

- **使用分支（use branches）。**

### 5.16 全讲结论

讲义 p68 的三条总结：

1. **程序有缺陷** → **要系统地找它们。**
2. **程序比人所能管理的更复杂** → **把代码写成可管理的。**
3. **编程不是孤独的**——即使你只是在跟评分器或未来的自己沟通 → **让你的沟通可被理解。**

**讲义 p69–p70 回答开头的问题**（原文重复了两页，可见其分量）：

> **好的设计与有效的调试之间是什么关系？**
> **→ 推理（Reasoning）**
> - **好的设计：让「对你的程序进行推理」变得更容易。**
> - **有效的调试：用推理来组织对「已存在的程序」的调查。**

**这句话把全讲的两半缝在一起**：

- 设计不是「好看」，而是**降低推理成本**。小函数、清晰契约、好名字、说明「为什么」的注释——每一样都在减少你调试时需要同时装进脑子的东西。
- 调试不是「试错」，而是**用推理组织调查**。假设—预测—实验的循环，本质是「用最小的实验获取最大的信息」。

**反过来也成立**：如果你发现某段代码「无法调试」——你没法构造一个能区分两个假设的实验——那通常说明**设计坏了**（职责太多、契约不清、状态太隐晦），而不只是「这个 bug 太难」。

### 6.2 Agent 自行编写的教学示例

> 非官方，仅用于说明概念。

**示例 A：完整走一遍科学调试法（含可复现的「加 printf 就消失」）**

```c
/* hb.c —— 非官方示例，仅用于说明概念 */
#include <stdio.h>

int acc(int n) {
    int total;              /* 未初始化 */
    for (int i = 0; i < n; i++) total += i;
    return total;
}

int main(void) {
    printf("acc(0)  = %d\n", acc(0));
    printf("acc(10) = %d\n", acc(10));

}
```

排查顺序：

```
$ gcc -Wall -Werror -O0 -o hb hb.c        # 第一步：应该立刻报 uninitialized
$ gcc -O0 -o hb hb.c && ./hb               # 去掉 -Werror 看实际行为
$ gcc -O3 -o hb hb.c && ./hb               # 换个优化级别，结果可能不同
$ gcc -g -O0 -o hb hb.c && valgrind ./hb   # 内存级检查
```

在 `-O0` 下 `acc(0)` 返回栈上残留值；在 `-O3` 下编译器可能把 `total` 放进寄存器并「顺手」用某个值。**两种结果不一致，本身就是「这里有未定义行为」的证据。**

```c
/* 计算数组元素之和；negate 为真时先取反 */
long sum_values(const int *values, int count, int negate) {
    long total = 0;
    for (int i = 0; i < count; i++) {
        int value = values[i];
        if (negate) value = -value;
        total += value;
    }
    return total;
}
```

改动清单（对应讲义 p51 的七条）：

| 原名 | 新名 | 依据 |
|---|---|---|
| `calc` | `sum_values` | 从意图出发（第 1 条）；`calc` 无信息 |
| `d` | `values` | 避免单字母（p53） |
| `n` | `count` | 精确含义 |
| `f` | `negate` | 布尔量用形容词 |
| `r` | `total` | 领域词 |

| `int` | `long` | 累加可能溢出（顺带修 bug） |
| — | `const` | 表达「不修改输入」的契约 |

**示例 E：契约 + 断言（无副作用）**

```c
/* contract.c —— 非官方示例，仅用于说明概念 */
#include <assert.h>

/* 前置：data != NULL, n >= 0, data[0..n-1] 可读
   后置：返回 sum(data[0..n-1])，不修改 data
   不变式：0 <= i <= n，total == sum(data[0..i-1]) */
long sum_values(const int *data, int n) {
    assert(data != NULL);
    assert(n >= 0);

    long total = 0;
    for (int i = 0; i < n; i++) {
        assert(0 <= i && i <= n);
        total += data[i];
        assert(total == total);      /* 占位：真实不变式应可独立计算 */
    }
    assert(0 <= n);
    return total;
}
```

**注意反例**：`assert(x++)`、`assert(free(p))` 这类**有副作用的断言是错的**——用 `-DNDEBUG` 关掉断言后程序行为就变了。讲义 p28 明确要求「断言不得有副作用」。

**示例 F：用注释驱动开发（快排骨架）**

```c
/* qsort_skel.c —— 非官方示例，仅用于说明概念 */
void my_qsort(int *a, int lo, int hi) {
    // Initialize locals
    // Pick a pivot value
    // Reorder array around the pivot
    // Recurse

    if (lo >= hi) return;                    // 0
    int pivot = a[lo + (hi - lo) / 2];       // 1
    int i = lo, j = hi;                      // 2
    while (i <= j) {
        while (a[i] < pivot) i++;
        while (a[j] > pivot) j--;
        if (i <= j) { int t = a[i]; a[i] = a[j]; a[j] = t; i++; j--; }
    }
    my_qsort(a, lo, j);                      // 3
    my_qsort(a, i, hi);
}
```

先写四行注释，再填代码，最后回看注释是否仍准确——这就是讲义 p65–p66 的四步流程。

## 7. 容易混淆的概念

| 概念 A | 概念 B | 区别 |
|---|---|---|
| Defect（缺陷） | Failure（失效） | 前者在代码里（静态存在）；后者在接口处可观察（动态发生）。**有缺陷不一定失效** |
| Error（错误状态） | Failure（失效） | 前者是内部数据/控制信号不对；后者是错误传播到接口并被观察到 |
| 潜伏缺陷（latent） | 活跃缺陷（active） | 前者所在代码很少执行，永不发作；后者会被触发 |
| 假设（hypothesis） | 预测（prediction） | 前者是「缺陷是什么」；后者是「若假设成立，新条件下应观察到什么」——**可检验的是预测** |
| 观察（observation） | 结论（conclusion） | 前者是事实（「返回 1」）；后者是解释（「所以 f 未初始化」）——**不要把解释当事实记录** |
| 诊断（diagnosis） | 修复（fix） | 前者是能解释并预测的理论；后者是据此写的代码改动 |
| `-Wall` | `-Werror` | 前者打开警告；后者把警告升级为错误。**`-Wall` 必须，`-Werror` 应该** |
| `-O0` 下 Valgrind | `-O3` 下 Valgrind | 前者能抓到寄存器/内存级未初始化；后者可能漏报（优化把内存访问消除了） |
| 测试（testing） | 契约（contracts） | 前者验证具体输入；后者声明前置/后置条件。**互补，且都是设计行为** |
| 封装（encapsulation） | 抽象（abstraction） | 前者「外部不能碰内部」；后者「外部只需知道接口」 |
| 注释「做什么」 | 注释「为什么」 | 前者冗余（代码已说）；后者是唯一有价值的信息 |
| `size` | `height`/`numChildren`/`subTreeNumNodes`/`keyLength` | 前者有四种可能含义，是坏名字 |
| `arraysOfSetsOfLinesOfBlocks` | `cache` | 前者五个词读不完；后者是领域术语 |
| 循环里的 `i` | 别处的 `i` | 前者是**允许的例外**；后者不可搜索 |
| `tmp` 在 `swap` 里 | `tmp` 在别处 | 前者是**合理例外**（约定俗成）；后者是无意义名 |
| `cat foo.c` | `cat > foo.c` | 前者读文件；后者**覆盖**文件——一个 `>` 毁掉全部工作 |

## 10. 本节复习

- 链条：**缺陷 → （可能）错误 → 传播 → 失效**；错误可被屏蔽（ECC）或检测。
- **不是每个缺陷都造成失效**；测试只能证明缺陷存在，不能证明不存在（Dijkstra 1972）。
- 显式调试（小黄鸭法）：把问题说完整，往往就够了。
- 科学调试法：问题描述 + 代码 + 失败运行 + 其它运行 → 假设 → 预测 → 实验 → 观察与结论 → 诊断 → 修复与确认 → 学习。
- 奥卡姆剃刀：选最简单、离当前工作最近的假设。
- 实验纪律：**只改一个条件**；**观察是事实，结论才解释**；**不越过第一个 bug**；`printf` 可能干扰。
- 避免 post hoc 谬误：相关不等于因果，要理解缺陷与修复的关系。
- 断言**不得有副作用**；把每个成功的条件加入测试集。
- 时间盒：0 分钟 `-Wall` + Valgrind；1–10 分钟非正式；10–60 分钟科学调试；>60 分钟休息或求助。
- `-Wall` **必须**，`-Werror` **应该**；至少试 `-O3` 与 `-O0`。
- Valgrind **不是完美的**：`-O3` 下可能漏报，`-O0` 下才抓到；报错位置常在 `vfprintf`（未初始化值第一次被用于判断处）。
- 六种坏味道：未初始化变量、未使用的值、不可达代码、内存泄漏、接口误用、空指针。
- 好设计最重要的属性是**可读**；核心是**复杂度管理 + 沟通**。
- 可测试的设计 = 小部件 + 清晰契约；**契约是调试时放假设的锚点**。
- 「相信编译器」：多用临时变量、多用函数、让编译器做算术。
- 命名七条：从意图出发、精确词、词少、不缩写、用代码审查改进、读出声、真的去改。
- 名字最多四个词；只用词典词；避免单字母（循环计数器与 `fd`/`str` 例外）；用领域术语；精确用反义词。
- 注释写**为什么存在**，不写**做什么**；别扭代码要**重写**而不是加注释。
- 先写注释再写代码（快排四行）；写不出注释 = 没想清楚。
- 提交信息一行说清做了什么，**诚实记录未解决的部分**；用分支。
- 全讲结论：好设计让**推理**更容易；有效调试**用推理**组织调查。

## 11. 自我检查

**题 1**：某程序在 `-O0` 下输出 `fib(1)=134513905`，在 `-O3` 下输出 `fib(1)=0`，在 `-O1` 下输出 `fib(1)=9`。这三个数字本身能告诉你什么？下一步最省力的动作是什么？

<details><summary>参考答案</summary>

**三个数字说明了什么**：

1. **同一份源码在三个优化级别下给出三个不同的答案** → 这**不是**「某个优化级别算错了」，而是程序存在**未定义行为（undefined behavior）**。合法程序在任何 `-O` 级别下都必须给出相同结果。
2. 具体地，`fib(1)` 时 `while (n > 1)` 一次都不执行，`f` 从未被赋值，`return f;` 读的是**未初始化变量**。
3. 三个数字分别对应三个优化级别下那块栈/寄存器位置的残留内容：
   - `-O0`：`f` 在栈上，读到某个残留值 `134513905`
   - `-O1`：读到 `9`（可能是某个局部量的残留）
   - `-O3`：编译器可能把 `f` 放进寄存器或直接常量折叠成 `0`

**关键推论**：**结果的「不一致」比任何单个错误值都更有信息量**。它把「这个 bug 依赖编译器内部决定」这件事直接摆出来了。

**下一步最省力的动作**：

```
gcc -Wall -Werror -O3 -o badfib badfib.c
```

`-Wall` 会直接报：

```
badfib.c:12:5: error: 'f' may be used uninitialized in this function
     return f;
     ^
```

**一步定位**，不需要科学调试法。

**顺序上的教训**：讲义 p29 的时间盒把 `-Wall` + Valgrind 放在「**0 分钟**」那一档——**先做零成本的检查，再考虑动脑**。很多人一上来就 `printf` 或 `gdb`，浪费了最便宜的信号。

</details>

**题 2**：你怀疑「`sum()` 的循环边界写错了」。请按科学调试法写出假设、预测、实验，并说明这个实验为什么必须「只改一个条件」。

<details><summary>参考答案</summary>

**假设（hypothesis）**：

> `sum()` 的循环条件是 `i < n`，但正确应为 `i <= n`（漏掉了最后一个元素），这解释了「结果总是比预期小最后一个元素」这个失效。

**关键**：假设必须包含两部分——**缺陷是什么** + **为什么它能解释观察到的失效**。只说「循环有问题」不算假设。

**预测（prediction）**：

> 若假设成立，则：
> - 输入 `n = 3`、数组 `{1,2,3}`，当前返回 `1+2 = 3`（缺 3）；
> - 把条件改成 `i <= n` 后，返回 `1+2+3 = 6`；
> - 且**对于所有**输入，改后结果都应比改前大 `a[n]`。

注意预测必须是**可检验的具体数值**，不是「应该会变好」。

**实验（experiment）**：

> 在与之前**完全相同**的条件下（同一份输入 `{1,2,3}`、同一编译选项、同一运行环境），**只把 `i < n` 改成 `i <= n`**，重新编译运行。

**为什么必须只改一个条件**：

1. **归因**：若你同时改了循环条件和数组起始下标，结果变对了，你无法知道是哪个改动起的作用——两个都可能是真凶，也可能一个真凶一个巧合。
2. **可重复**：科学调试法要求「实验条件与之前某次运行相同，除了一处改动」。这样每次观察都对应一个明确的因果假设。
3. **避免「修好又修坏」**：同时改两处，可能一处修好、一处引入新 bug，净效果是「看起来好了」，但你在代码里埋了第二颗雷。
4. 讲义 p27 的追问也是这个道理：**「若你修了多个疑似缺陷，哪一个才是真正修好这个失效的？」**

**若预测失败怎么办**（讲义 p24）：假设被推翻 → **基于新输入精炼假设**，重新进入循环。不要「顺手再改一处试试」——那是试错，不是调试。

</details>

**题 3**：为什么 `gcc -g -O3` 后 Valgrind 找不到未初始化变量的错误，而 `-O0` 能找到？这说明了什么？

<details><summary>参考答案</summary>

**机制**：

- **Valgrind Memcheck 追踪的是「内存的已定义性」**：它为每个字节维护一个「defined / undefined」影子位，并在值被复制、运算时**传播**这个标记；当某个未定义值第一次被用于**必须确定值的场合**（条件跳转、系统调用参数、输出）时报错。
- **`-O0`**：局部变量 `f` 分配在**栈上**，`return f;` 真的执行「从栈读 8 字节」——Memcheck 看到「读了一块未定义内存」，标记传播到返回值，最终在 `printf` → `vfprintf` 里被用于格式化时报出：

```
Conditional jump or move depends on uninitialised value(s)
   at 0x4E988DA: vfprintf (vfprintf.c:1642)
   by 0x4EA0F25: printf (printf.c:33)
```

- **`-O3`**：编译器把 `f` 分配到**寄存器**，或者更激进地直接常量折叠/消除「未初始化」这条路径。**整个过程不再有「从未定义内存读取」这个动作**，Memcheck 的影子位机制没有东西可追踪 → **零报告**。

**这说明了什么**：

1. **工具的有效性依赖于代码形态。** Valgrind 对「内存错误」强，对「寄存器级未定义值」弱。优化改变了代码形态，也就改变了工具的能力边界。
2. **「工具没报错」≠「没有 bug」。** 讲义 p18 的原话是「**Valgrind is not perfect**」。
3. **所以讲义 p17 要求「`-O3` 和 `-O0` 都跑」**——两个级别的工具覆盖范围不同，合起来才接近完备。
4. **更根本的教训**：这类 bug 的**首选工具不是 Valgrind，而是 `-Wall`**。`-Wall` 在**编译期**基于数据流分析发现「`f` 可能未初始化」，不依赖运行时是否真的读了内存，因此**不受优化级别影响**。这就是讲义把它排在「0 分钟」而 Valgrind 排在其后的原因。
5. **顺序纪律**（讲义 p17）：**只在所有警告都消失之后才跑 Valgrind**。否则编译器警告 + Valgrind 噪音混在一起，你分不清哪个是真信号。

</details>

**题 4**：下面这段代码有三处「坏味道」和一个命名问题，请指出并改写。

```c
int calc(int *d, int n) {
    int r = 0;
    int t;
    for (int i = 0; i < n; i++) {
        t = d[i];
        r += t;
    }
    return r;
    printf("done\n");
}
```

<details><summary>参考答案</summary>

**三处坏味道**：

| # | 坏味道 | 位置 | 说明 |
|---|---|---|---|
| 1 | **使用未初始化变量** | `int t;` | `t` 在循环里总会被赋值，所以这里**实际不构成 bug**，但声明时不初始化是危险习惯——一旦循环不执行（`n <= 0`），`t` 就是垃圾。更严重的是它没有任何存在理由（见 #2） |
| 2 | **未使用的值** | `t` 整个变量 | `t` 只是中转，`r += t` 可以直接写 `r += d[i]`。多出的变量增加了读者负担，且是「未初始化」警告的来源 |
| 3 | **不可达代码** | `printf("done\n");` | 在 `return r;` 之后，**永远不会执行**。`gcc -Wall` 会报 `unreachable code` |

**命名问题**：

- `calc`：**无信息**。计算什么？讲义 p51 第 1 条要求「从含义与意图出发」。
- `d`：**单字母**（讲义 p53），且不暗示「数组/输入」。
- `n`：可接受但不够精确（是元素个数还是字节数？）。
- `r`、`t`、`i`：`i` 是**允许的例外**（循环计数器）；`r`/`t` 不是。

**改写后**：

```c
/* 返回 values[0..count-1] 之和；count <= 0 时返回 0
   前置：values 非 NULL 且 count <= 0 或 values 可读 count 个元素
   后置：不修改 values */
long sum_values(const int *values, int count) {
    long total = 0;
    for (int i = 0; i < count; i++) {
        total += values[i];
    }
    return total;
}
```

**改动说明**：

1. `calc` → `sum_values`：说明意图。
2. `d` → `values`，`n` → `count`：可搜索、有含义。
3. 删掉 `t`：消除未初始化与未使用值两个坏味道。
4. 删掉 `printf`：消除不可达代码。
5. `int r` → `long total`：**顺带修了一个潜在 bug**——`int` 累加 10 万个 `int` 会溢出；`long` 更安全。
6. 加 `const`：**用类型表达契约**（「我不改你的数组」）。这正是讲义 p43 说的「契约是可执行的文档」。
7. 加注释说明**前置/后置条件与边界行为**（`count <= 0` 时返回 0）——回答「什么时候该用/不该用」，而不是「这段代码在做什么」。

**验证**：

```
$ gcc -Wall -Wextra -Werror -c sum_values.c    # 无警告
$ valgrind --leak-check=full ./test             # 无泄漏
```

**题 5**：讲义最后说「好的设计让推理更容易，有效的调试用推理组织调查」。请用一个具体例子说明：**一个设计缺陷如何直接导致调试困难**。

<details><summary>参考答案</summary>

**例子：一个 300 行、什么都做的 `process()` 函数**

```c
/* 反例：设计坏了 */
int process(char *filename, int mode, int verbose) {
    FILE *f = fopen(filename, "r");        /* 职责 1：I/O */
    if (!f) return -1;
    char line[256];
    int total = 0;
    while (fgets(line, 256, f)) {          /* 职责 2：解析 */
        int v = atoi(line);
        if (mode == 1) v *= 2;             /* 职责 3：业务逻辑 */
        else if (mode == 2) v = -v;
        if (verbose) printf("%d\n", v);    /* 职责 4：输出 */
        total += v;
    }
    fclose(f);
    /* 职责 5：统计 */
    if (total > 1000) total = 1000;
    return total;
}
```

**症状**：某个输入文件返回 `-1`。到底是「文件打不开」、「`atoi` 遇到非数字」、「`total` 溢出」，还是「`mode` 传错了」？

**设计缺陷如何造成调试困难**：

| 设计问题 | 对调试的具体伤害 |
|---|---|
| **没有关注点分离** | 一个返回值 `-1` 有**四种**可能来源。你连「哪个假设最可能」都排不出优先级——违反奥卡姆剃刀的前提（你得先能列出假设） |
| **没有清晰契约** | 函数没说明「`mode` 只接受 0/1/2」。传入 `mode = 3` 时静默走「不加不减」分支，你**根本不会想到去检查它** |
| **状态全在一个作用域** | `f`、`line`、`v`、`total` 全在一个函数里，`gdb` 里 `print total` 得到的值可能已经过了三次修改——**你无法判断哪一步出的错** |
| **无法构造隔离实验** | 想验证「`atoi` 遇到 `"abc"` 返回 0」这个假设？你必须造一个完整输入文件、跑完整个 `process()`，然后**从结果反推**——因为解析逻辑没有独立入口 |
| **副作用纠缠** | `printf` 会改输出流状态，`fgets` 会推进文件位置。**加一个 `printf` 调试可能改变 bug 的表现**（讲义 p24 的「不要干扰」） |

**重构后（好设计）**：

```c
/* 每个函数一件事，各有清晰契约 */
int parse_line(const char *line);           /* 契约：非数字返回 0 */
int apply_mode(int value, int mode);        /* 契约：mode 只能是 0/1/2 */
long accumulate(const int *values, int n);  /* 契约：n >= 0，返回和 */
int clamp_total(long total, int limit);     /* 契约：limit >= 0 */
```

**重构带来的调试能力**：

1. **每个假设都有对应的实验**：「`parse_line` 对 `"abc"` 返回什么？」——写一行测试，立刻得到答案。**这正是讲义 p43 说的「清晰的契约 → 调试时可以放置假设的锚点」。**
2. **错误可以被二分定位**：返回值 `-1` 现在只可能来自 `open_input()`（因为其它函数不再返回 `-1`）。**假设空间从 4 个缩到 1 个。**
3. **实验可以只改一个条件**：测试 `parse_line("abc")` 时，没有任何 I/O、没有任何全局状态——观察完全干净（讲义 p24 的「不要干扰」）。
4. **测试变成可复用的资产**：每个边界用例（空行、负数、超长行）都成为回归测试（讲义 p28「每个成功的条件都加入测试集」）。

**结论**：

讲义 p69 那句话的实质是：**设计的每一个决策，都在改变「调试时你能提出什么假设、能做什么实验」的空间。** 关注点分离让你能隔离变量；契约给你判断对错的参照；好名字让你能搜索到相关代码；说明「为什么」的注释让你不用反推意图。

**反过来看**：当你发现一个 bug「怎么调都调不出来」时，值得问一句——**是不是设计让我无法构造一个能区分假设的实验？** 如果是，修设计比修 bug 更根本。
