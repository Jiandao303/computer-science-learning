# Trie（前缀树）

> 覆盖 `01-知识点目录.md` 中的「树」组知识点 **Trie**。
> 本篇为原创笔记，不逐页翻译任何讲义；课程与教材见 [02-权威课程与资料](02-权威课程与资料.md)。

## 一句话总结

Trie（前缀树 / 字典树，读作 "try"）把每个字符串拆成一条从根出发的字符路径，前缀相同的串共享同一条路径。它用空间换掉了「比较」：查找代价只与串长 L 有关，与集合里存了多少个串无关。代价是每个节点的固定开销很大，朴素实现在内存上可能贵得离谱，所以工程里真正用的是压缩 Trie。

## 核心概念

### 节点表示「读到一个字符后往哪走」，根为空

Trie 是一棵有根树，**根节点不携带字符**。除根以外，每个节点对应一个字符，也对应「从根走到该节点的路径拼成的那个前缀」。节点上只有两类信息：转移（读到字符 c 后去哪个孩子）和终止标记（这个节点拼出的串是不是一个被插入的 key）。

关键认知：**节点不是 key，路径才是 key**。节点只是路径上的一个位置。所以同一个节点可以同时是 "car" 的终点和 "card" 的中间点——这正是前缀共享的来源，也是 Trie 与「每个 key 占一个格子」的哈希表最根本的结构差异。

根为空带来一个直接推论：所有 key 的第一层分支都挂在根上，根的孩子数最多等于字母表大小 Σ。小写英文 Σ = 26，二进制 Σ = 2，Unicode 码点 Σ ≈ 15 万。这个 Σ 会反复出现，是空间分析的主角。

代价是：每个节点都必须回答「孩子怎么找」。这个存储方式的选择决定了整个结构的空间与常数，是 Trie 实现里唯一真正重要的工程决策。

### 两种节点实现：定长数组 vs 哈希表

**定长数组**：每个节点开一个 `child[Σ]`，`child[c]` 直接存孩子指针，没有就是 null。一步查找是「数组下标 + 判空」，一次内存访问，没有哈希、没有字符比较、没有不可预测的分支。缺点是**每个节点都为整个字母表付费**：只有一个孩子的节点，也要占满 26 个指针的位置。

**哈希表**：每个节点存一个「字符 → 孩子指针」的映射。空间与**实际孩子数 d** 成正比，而不是与 Σ 成正比。一步查找是「算哈希 + 探测 + 解引用」，期望 O(1)，但常数更大，而且是多次内存访问。

取舍可以压成一句：**字母表小且节点稠密 → 数组；字母表大或节点稀疏 → 哈希**。26 个小写字母的词典，数组通常赢；Unicode 文本、稀疏 ID 前缀，哈希更合适。

还有第三种常用做法：**有序数组 + 线性/二分查找**。节点存 `(char, child)` 对并按 char 排序，孩子少时线性扫描比哈希还快，内存连续、没有哈希计算。很多真实实现（包括一些存储引擎的索引）走这条路。

定量的账放在「例子二」里算。

### 三个操作：insert / search / startsWith

三个操作共用同一个动作：**沿字符走路径**。

`insert(word)` 从根出发逐字符走，孩子不存在就新建，走完在最后一个节点打终止标记。`search(word)` 同样逐字符走，中途孩子缺失就返回 false，走完**还必须检查终止标记**。`startsWith(prefix)` 与 search 完全一样，只是走完直接返回 true，不看终止标记。

三者都是 O(L)，区别只在最后一步的判断，以及 insert 会写。

这里有个极常见的 bug：`search` 忘了检查终止标记。如果只插入过 "card"，`search("car")` 会走通整条路径然后错误地返回 true。**路径存在 ≠ key 存在**，这是「前缀」和「词」的分界线。

另一个容易忽略的点：`startsWith` 是 Trie 天然支持的，而哈希表根本不支持——哈希把整个串压成一个桶号，前缀信息在哈希之后已经不可恢复。这不是实现水平问题，是信息层面的损失。

### 空间代价：为什么定长数组会浪费

设字母表大小 Σ，key 个数 n，所有 key 的总字符数 N = Σ L_i。

**节点数**：Trie 的节点数等于「所有 key 的所有前缀（含空前缀）中互不相同的那些」的个数。上界是 N + 1（每个字符都新开节点、完全不共享）。所以节点数是 **O(N)**——注意，它由总字符数决定，**不由 key 个数决定**。

**每节点空间**：定长数组实现是 Θ(Σ) 个指针，与这个节点实际有几个孩子无关。

两者相乘，得到**最坏空间 O(N·Σ)**，也就是「总字符数 × 字母表大小」。对 26 个小写字母、8 字节指针，每个字符要摊 **208 字节**，而字符本身只有 1 字节。

**浪费的精确来源**：树里绝大多数节点是叶子或只有一个孩子。叶子节点的 26 个槽位全是 null，却一个不少地占着 208 字节。典型英文词典里叶子占比常在 30%–50%，这部分内存几乎全空。

**代价的性质**：不是「慢」，而是「装不下」。10 万个平均 8 字母的词，朴素数组节点要上百 MB（推导见例子二），同样的词用哈希集合只要几 MB。这就是压缩 Trie 存在的全部理由。

### 压缩 Trie：radix tree 与 Patricia trie

观察：Trie 里大量节点只有**一个孩子**。这种节点不提供任何分支信息，唯一作用是「把路径延长一个字符」。既然如此，为什么不用一条边直接跨过这串字符？

**压缩 Trie（compressed trie）**把每个「非终止且只有一个孩子」的节点链合并成一条边，边上存这串字符（通常是「原串起始下标 + 长度」，不复制字符）。合并后，每个内部节点至少两个孩子，每个叶子是一个 key。

**radix tree** 与 **Patricia trie** 通常指同一类结构（Patricia 是 "Practical Algorithm To Retrieve Information Coded in Alphanumeric" 的缩写，最初针对二进制串）。严格区分时，radix tree 是通用的压缩 Trie，Patricia trie 特指对二进制串压缩、用「跳过位数」记录边长的变体。**待核实**：不同文献对这两个名字的用法并不统一，有的直接当同义词。

**节点数的关键结论**：n 个两两不为前缀的 key，压缩 Trie 节点数 ≤ 2n − 1（证明见例子三）。这意味着空间从 **O(N·Σ) 降到 O(n)**——与总字符数无关，只与 key 个数有关。这是量级改进，不是常数优化。

代价有三条：插入/删除要分裂边、合并边，代码复杂度明显上升；边存的是原串切片引用，原串必须一直保留；单次查找仍是 O(L)，但要额外处理「边上部分匹配」——走到一半失配就要立刻返回 false，否则会误判。

### 应用：为什么恰好是这些场景

**自动补全（autocomplete）**：给定前缀要枚举所有以它开头的词。Trie 走完前缀后，剩下就是「子树里的全部 key」，一次 DFS 收完。哈希表做不到，因为前缀信息已丢失。

**拼写检查**：判断词是否在词典里是 search；找「编辑距离 ≤ 1 的候选」，可以沿 Trie 做带剪枝的 DFS——前缀一旦偏离超阈值，整棵子树都能剪掉。这是 Trie 相对哈希集合的核心优势：**能按前缀批量剪枝**。

**IP 路由的最长前缀匹配（longest prefix match）**：IPv4 地址是 32 位，看成 32 个二进制字符。从根按位走，一路记录「最近一次遇到被标记为路由前缀的节点」，走到不能走为止，最后记下的就是最长匹配。深度最多 32，与路由表大小无关。

**词典与词频统计**：Trie 的 DFS 天然按字典序输出（按字符顺序遍历孩子），所以它同时是一个有序容器，哈希表完全没有这个能力。

**字符串排序**：全部插入后按字典序 DFS 输出，就是一次**基数排序（radix sort）**，时间 O(N)，不受比较排序 Ω(N log N) 下界约束——因为它消费的信息单位是字符，不是比较。

## 推导 / 例子

### 例子一：三个操作的伪代码与逐步推演

（伪代码，非官方，仅用于说明概念）

```text
结构 Node:
    child:  map from char -> Node   # 或 child[Σ] 定长数组
    is_end: bool

insert(root, word):
    node = root
    for ch in word:
        if node.child[ch] is missing:
            node.child[ch] = new Node()
        node = node.child[ch]
    node.is_end = true

search(root, word):
    node = root
    for ch in word:
        if node.child[ch] is missing:
            return false
        node = node.child[ch]
    return node.is_end          # 关键：不能直接 return true

startsWith(root, prefix):
    node = root
    for ch in prefix:
        if node.child[ch] is missing:
            return false
        node = node.child[ch]
    return true
```

推演：依次 `insert("cat")`、`insert("car")`、`insert("card")`、`insert("dog")`、`insert("do")`。

（结构示意图，非官方，仅用于说明概念）

```text
root
├─ c
│  └─ a
│     ├─ t *              (cat)
│     └─ r *              (car)
│        └─ d *           (card)
└─ d
   └─ o *                 (do)
      └─ g *              (dog)
```

节点计数：root、c、a、t、r、d(card)、d(dog 分支)、o、g = **9 个**。
插入的总字符数 = 3+3+4+3+2 = 15。不共享前缀需要 15 个节点，实际只用了 8 个（不含根），**省了 7 个**。

逐个查询：

| 查询 | 走到的节点 | is_end | 结果 | 说明 |
| --- | --- | --- | --- | --- |
| `search("ca")` | c→a | false | **false** | 路径存在但不是 key |
| `startsWith("ca")` | c→a | 不检查 | **true** | 有 3 个词以 ca 开头 |
| `search("car")` | c→a→r | true | **true** | |
| `search("card")` | c→a→r→d | true | **true** | 同一节点既是 key 终点又是更长 key 的中间点 |
| `search("carp")` | c→a→r→p | — | **false** | p 缺失，第 4 步失败 |
| `search("do")` | d→o | true | **true** | |
| `search("d")` | d | false | **false** | 又一个「路径存在但非 key」 |

复杂度推导：`insert` 的循环执行 L 次，每次做「一次映射查找 + 最多一次节点分配」。映射查找在数组实现下是 O(1)（下标访问），哈希实现下期望 O(1)、最坏 O(d)（d ≤ Σ）；节点分配按摊还算 O(1)。于是

T_insert(L) = Σ_{i=1..L} O(1) = **O(L)**。

`search` / `startsWith` 同样是 L 次迭代、每次 O(1)，得 **O(L)**。空间上 insert 最多新建 L 个节点，数组实现每节点 O(Σ)，一次插入最坏新增 **O(L·Σ)** 空间。

这里「O(1)」的前提是：字符比较与数组下标为 O(1)。对定长编码（ASCII、UTF-32）成立；对变长编码（UTF-8）严格说取决于编码长度，通常按「码点」计。

### 例子二：空间代价的定量分析（真的算一遍）

设定：Σ = 26，每个孩子指针 8 字节，则每节点 `child[26]` = **26 × 8 = 208 字节**（`is_end` 与对齐再算几字节，忽略）。

**节点数上界推导**：深度 d 上的节点数不能超过「深度 d 的所有可能前缀数」Σ^d，也不能超过「key 个数」n（每个 key 在每层最多贡献一个节点）。所以

nodes ≤ 1 + Σ_{d=1..L_max} min(Σ^d, n)。

**情形 A：n = 10,000 个 key，每个长 10，共 N = 100,000 字符。**

朴素上界 N+1 = 100,001（假设完全不共享）在 Σ=26 时达不到——26 个首字母装不下 10,000 个互不相同的前缀。用公式逐层算：

| 深度 d | Σ^d = 26^d | min(26^d, 10000) |
| --- | --- | --- |
| 1 | 26 | 26 |
| 2 | 676 | 676 |
| 3 | 17,576 | 10,000 |
| 4 | 456,976 | 10,000 |
| 5…10 | ≥ 1.1×10^7 | 10,000（每层） |

节点数 ≤ 1 + 26 + 676 + 10,000 + 7×10,000 = **80,703**。

内存 = 80,703 × 208 B = 16,786,224 B ≈ **16.8 MB**。

如果 key 是随机的（每层均匀分布），实际节点数是每层「被占用前缀数」之和，期望为 Σ^d·(1 − (1 − 1/Σ^d)^n)：

- d=1：26·(1 − (25/26)^10000) ≈ 26
- d=2：676·(1 − e^(−10000/676)) ≈ 676
- d=3：17,576·(1 − e^(−10000/17576)) = 17,576 × 0.4339 ≈ 7,626
- d=4：456,976·(1 − e^(−0.02188)) ≈ 456,976 × 0.02164 ≈ 9,891
- d=5：≈ 9,996；d≥6：≈ 10,000

合计 ≈ 1 + 26 + 676 + 7,626 + 9,891 + 9,996 + 5×10,000 = **78,216** 个节点，与上界 80,703 只差 3%。内存 ≈ 78,216 × 208 ≈ **16.3 MB**。

**对照：同一批 key 存哈希集合。** 字符本身 100,000 B；每条目结构开销按 24 B 算（指针 + 头部）→ 240,000 B；桶数组按负载因子 0.5、每槽 8 B → 2×10,000×8 = 160,000 B。合计约 **500 KB**。

比值 16.8 MB / 0.5 MB ≈ **34 倍**。

**情形 B：指针换成 4 字节下标。** 每节点 26×4 = 104 B，上面 16.8 MB 直接减半到 **8.4 MB**。这说明「指针宽度」在 Trie 里被放大了 26 倍，是个容易被忽略的优化点。

**为什么说是最坏 O(N·Σ)**：节点数 ≤ N+1（每个字符最多一个新节点），每节点 Θ(Σ)，相乘即 O(N·Σ)。Σ 是常数（26）时它是 O(N)，但这个「常数」是 26 个指针，这才是真正的痛点。如果字母表是 Unicode（Σ ≈ 15 万），O(N·Σ) 直接变成灾难，必须换哈希节点。

### 例子三：压缩 Trie 的压缩比（证明 + 数字）

**先证节点数上界**：n 个两两不为前缀的 key 构成压缩 Trie。

1. 每个 key 对应唯一叶子，叶子数 = n。
2. 每个内部节点至少 2 个孩子——否则「只有一个孩子且不是 key 终点」的节点会被合并进边里。
3. 设内部节点数 I，总节点数 = n + I，边数 = n + I − 1（树中边数 = 节点数 − 1）。
4. 另一方面，边数 = 所有节点的孩子数之和 ≥ 2I（内部节点至少 2 个孩子，叶子 0 个）。
5. 于是 n + I − 1 ≥ 2I，即 **I ≤ n − 1**。
6. 总节点数 ≤ n + (n−1) = **2n − 1**。

**数字例子**：1,000 个 key，每个长 1,000 字符，共享前 900 字符，之后各自分叉。

- 标准 Trie：共享段 900 个节点 + 分叉后 1,000 × 100 = 100,000 个节点 + 根 = **100,901** 个节点。
- 压缩 Trie：根 + 1 个分叉节点 + 1,000 个叶子 = **1,002** 个节点。

压缩比 = 100,901 / 1,002 ≈ **100.7 倍**。key 越长、共享前缀越长，比值越大——标准 Trie 的节点数随 N 增长，压缩 Trie 只随 n 增长。

**内存对照**（沿用 208 B/节点）：标准 Trie 100,901 × 208 ≈ **21.0 MB**；压缩 Trie 1,002 × 208 ≈ 208 KB，再加每条边的「下标 4 B + 长度 2 B」× 1,001 条 ≈ 6 KB，合计约 **214 KB**。比值 ≈ 98 倍。

**压缩比的本质**：压掉的是「一元链」的节点数，一元链长度 = 该位置到下一个分叉点（或 key 终点）的距离，所以压缩比 ≈ 平均一元链长度。英文单词的一元链不长（压缩比通常 1.5–3 倍）；IP 前缀、长 ID、URL、文件路径这类 key 的一元链可以极长，压缩比能到几十上百倍。

**短 key 的反例**：key 集合 {car, card, care, cat, dog}。标准 Trie 有 root、c、a、r、d、e、t、d、o、g = **10** 个节点；压缩 Trie 有 root、[ca]、[car]、card、care、cat、dog = **7** 个节点，压缩比只有 **1.43**。这提醒我们：key 短、分叉密时压缩收益很小，而代码复杂度照涨。

### 例子四：IP 路由的最长前缀匹配（真的算一遍）

把 IPv4 地址看成 32 个二进制字符，构建**二进制 Trie**（Σ = 2），节点上可带「这里是一个路由前缀，下一跳是 X」的标记。

（伪代码，非官方，仅用于说明概念）

```text
lookup(root, addr):                 # addr 是 32 位
    node = root
    best = null
    for i in 0..31:
        if node.marked: best = node.next_hop     # 记录，不返回
        b = bit_i(addr)
        if node.child[b] is missing: break
        node = node.child[b]
    if node.marked: best = node.next_hop         # 别漏最后一个节点
    return best
```

**复杂度**：循环最多 32 次、每次 O(1) → **O(32) = O(W)**，W 为地址宽度。**与路由表大小 n 完全无关**。

对照线性扫描：n = 500,000 条前缀，最坏比较 500,000 次，每次最多 32 个 bit → 1.6×10^7 次操作；Trie 只要 32 次。比值 500,000/32 = **15,625 倍**。

**内存的代价**（很多笔记只讲时间不讲这个）：深度 d 的节点数 ≤ min(2^d, n)，n = 500,000 时

- d = 1…18：Σ 2^d = 2^19 − 2 = 524,286
- d = 19：2^19 = 524,288 > 500,000，从此层起取 n = 500,000
- d = 19…32：14 层 × 500,000 = 7,000,000

节点数上界 = 524,286 + 7,000,000 + 1 ≈ **7.52×10^6**。

每节点 2 个 4 字节指针 = 8 B，加 4 B 标记/下一跳 → 12 B。内存 ≈ 7.52×10^6 × 12 B ≈ **90 MB**。

**这就是真实路由器不用朴素二进制 Trie 的原因**：32 步查询很漂亮，但 90 MB 的 SRAM 太贵，且 32 次指针追逐在现代 CPU 上等于 32 次潜在 cache miss。工程解法是**多比特 Trie（multibit trie）**：一次看 s 个 bit，节点开 2^s 个槽，树高降到 32/s；代价是每节点 2^s 个槽（s=8 时 256 个槽，树高只剩 4 层）。s 的选取就是「内存 vs 层数」的直接权衡。**待核实**：真实路由器里 s 的典型取值与 LC-trie 等具体实现细节。

### 例子五：自动补全的两种实现与代价

需求：给定前缀 P（长 L），返回词频最高的 k 个补全。

**做法 A：走完前缀，再 DFS 整棵子树。** 走前缀 O(L)；DFS 访问子树全部节点，代价 O(S)，S 为子树节点数；若前缀下有 100,000 个补全、平均还要再走 5 个字符，则 S ≈ 500,000，最后用 [[15-122-25-Priority-Queues]] 里的小顶堆选 top-k，O(S log k)。总代价 O(L + S log k)，**S 可能远大于 k**。

**做法 B：每个节点预存「本子树 top-k 列表」。** 查询走前缀 O(L)，直接读该节点列表 O(k)。插入一个词后要更新它路径上 L 个祖先的列表，每层判断新词是否进前 k 并插入 → 每层 O(k)，一次插入 **O(L·k)**。

**空间实算**（用例子二的 78,216 个节点，k = 10，每条记录 12 B）：
78,216 × 10 × 12 B = 9,385,920 B ≈ **9.4 MB**。
基础 Trie 是 16.3 MB，缓存 top-k 让内存增加约 **58%**。这就是「查询快」的直接价格。

结论：A 适合写入多、查询少；B 适合查询多、写入少。搜索引擎的自动补全用 B，因为查询量比索引更新量高几个数量级。

## 容易混淆的概念

| 对比 | 哈希表 | Trie |
| --- | --- | --- |
| 单 key 查找 | 期望 O(1)，但哈希要读完整个串，实际是 Θ(L) | 最坏 O(L) |
| 最坏情况 | 碰撞退化到 O(n)（除非随机化哈希） | 恒为 O(L)，没有碰撞概念 |
| 前缀查询 | 做不到（前缀信息已被哈希破坏） | O(L) 走完前缀，再枚举子树 |
| 有序遍历 | 需额外排序 O(n log n) | DFS 直接按字典序，O(N) |
| 空间 | O(N + n)，紧凑 | 数组节点 O(N·Σ)，压缩后 O(n) |

| 对比 | 二叉搜索树（含 AVL） | Trie |
| --- | --- | --- |
| 深度由什么决定 | key 个数 n（平衡后 ≈ log n） | key 长度 L |
| 每次比较的代价 | 比较两个完整字符串，最坏 O(L) | 只看一个字符，O(1) |
| 总查找代价 | O(L log n) | O(L) |
| 原因 | 每层重新比较前缀，前缀被反复扫描 | 前缀只扫一次，每层消化一个字符 |
| 空间 | O(n)，与 L 无关 | O(N)，压缩后 O(n) |

| 对比 | 定长数组 child[Σ] | 哈希表 child |
| --- | --- | --- |
| 每节点空间 | 恒为 Σ × 指针宽（26×8 = 208 B） | 正比于实际孩子数 d |
| 一步查找 | 1 次数组下标，最快 | 算哈希 + 探测，常数更大 |
| 稀疏节点 | 极度浪费（1 个孩子也占 208 B） | 几乎不浪费 |
| 适用字母表 | 小且固定（ASCII 小写、二进制） | 大或不确定（Unicode、任意字节） |
| 缓存友好性 | 好（连续内存） | 差（多次指针追逐） |

| 对比 | 标准 Trie | 压缩 Trie（radix / Patricia） |
| --- | --- | --- |
| 节点数 | ≤ N + 1，随总字符数增长 | ≤ 2n − 1，只随 key 个数增长 |
| 边 | 一条边一个字符 | 一条边一串字符（存下标 + 长度） |
| 插入 / 删除 | 简单 | 要分裂 / 合并边，复杂 |
| 单次查找 | O(L) | O(L)，且要做边上部分匹配 |
| 适用 | key 短、实现简单优先 | key 长、内存敏感（路由表、索引） |

## 和已有知识的连接

- [[15-122-12-Hashing]] 与 [[15-122-13-Hash-Dictionaries]]：这是 Trie 最直接的对照组。连接点在「查找代价由什么决定」——哈希字典说期望 O(1)，但那是把「算哈希」当成了 O(1)；对字符串，算哈希本身就要读 L 个字符。把这一点补上，两者才能公平比较。另外哈希字典的负载因子/扩容讨论，对应 Trie 的「每节点固定开销」讨论，都是「每个元素摊多少固定成本」的问题。
- [[15-122-15-Binary-Search-Trees]]：BST 深度 O(log n)，Trie 深度 O(L)。连接点是**比较成本被重新分配了**——BST 每层比较两个完整字符串，前缀被反复扫描；Trie 每层只消费一个字符。用 BST 的递归查找框架去理解 Trie，会自然发现 Trie 是把「一次长度 L 的比较」拆成了 L 次「长度 1 的比较」。
- [[15-122-16-AVL-Trees]]：AVL 用旋转把深度压到 O(log n)，解决 BST 退化。Trie 完全不需要平衡——它的深度被 key 长度天然锁死。连接点：**平衡是为了控制深度，而 Trie 的深度根本不由 n 决定**，所以平衡技术在 Trie 上没有用武之地。这是「问题结构决定工具选择」的好例子。
- [[15-122-21-Graph-Representation]]：Trie 就是一棵有根树，节点实现的选择（定长数组 vs 哈希表）与图表示里的「邻接矩阵 vs 邻接表」是同一个取舍：稠密用矩阵/数组，稀疏用表/哈希。`child[26]` 本质上就是出边表，26 叉数组就是一个小型邻接矩阵。
- [[15-122-05-Big-O]]：这里最容易犯错——把 O(L) 和 O(1)、O(log n) 直接比大小。它们的参数不同：n 是 key 个数，L 是 key 长度，N 是总字符数。正确说法是「以总输入规模 N 计，Trie 查找最坏 O(N)，哈希期望 O(N)」。真正拉开差距的是最坏情况保证和前缀查询能力，不是渐进阶。
- [[15-122-11-Unbounded-Arrays]]：那篇的摊还分析（扩容总代价除以操作数）在这里对应「节点分配的摊还成本」，以及「每个元素摊多少固定开销」的思路。连接点：无界数组是「为容量付费」，Trie 数组节点是「为字母表付费」，两者都是**用固定开销换 O(1) 访问**，代价结构同源。
- [[15-122-22-Graph-Search]]：自动补全里「走完前缀后枚举子树」就是一次 DFS。若 L 很大（例如 10,000 字符的路径），递归会爆栈，需要用 [[15-122-09-Stacks-and-Queues]] 里的显式栈改成迭代。连接点：树的遍历可以递归也可以显式栈，深度大时只有后者安全。
- [[15-122-24-Union-Find]]：术语撞车警告——并查集里的「路径压缩（path compression）」和压缩 Trie 里的「路径压缩」**不是一回事**。并查集压缩的是查找路径上的父指针，为的是摊还 O(α(n))；压缩 Trie 压缩的是一元链节点，为的是省内存。同名不同义，读文献时要小心。
- [[15-122-07-Quicksort]]：比较排序有 Ω(n log n) 下界，而把字符串插进 Trie 再按字典序 DFS 输出是 O(N)，看似违反下界。连接点：**下界只约束「比较」模型**，Trie 消费的是字符而不是比较，属于基数排序一族，跳出了决策树模型。这与 [04-算法设计范式](04-算法设计范式.md) 里「比较排序下界」的讨论是同一知识点的两面。
- [[15-445-08-Indexes-and-Filters-I]]：B+ 树索引对 key 做前缀压缩，是为了让一个页装下更多 key；radix tree 索引则是把 Trie 直接搬进存储引擎。连接点：**两者都在解决「key 的前缀冗余」**——B+ 树用页内前缀截断，Trie 用路径共享，一个在页级别，一个在字符级别。
- [[15-445-11-Sorting-and-Aggregation]]：外部排序与聚合里，字符串排序是真实瓶颈。Trie 的 DFS 输出等价于 MSD 基数排序，O(N) 且天然按前缀分组，对「按前缀分组聚合」特别顺手。连接点：排序不一定靠比较，字符结构本身就能提供顺序。
- [[15-445-17-Query-Optimization-II]]：`LIKE 'abc%'` 这类前缀谓词，普通 B+ 树索引只能用范围扫描近似；radix 索引能直接定位前缀。连接点：**索引结构决定了优化器能识别哪些谓词**，这是「数据结构影响查询计划」的具体例子。

<summary>参考答案（先自己做，再看）</summary>

**1.** 标准 Trie：

（示意图，非官方，仅用于说明概念）

```text
root
├─ a *                  (a)
│  └─ n *               (an)
│     ├─ t *            (ant)
│     └─ d *            (and)
└─ d
   └─ o *               (do)
      └─ g *            (dog)
```

节点：root、a、n、t、d、d(root 的)、o、g = **8 个**。
压缩 Trie：root、"a"→节点*（a 是 key，必须保留）、"n"→节点*（an 是 key，必须保留）、"t"→ant、"d"→and、"do"→节点*、"g"→dog，共 **7 个**。压缩比 8/7 ≈ **1.14**。
低的原因：一元链长度只有 1——a→n 看着是两步，但中间的 'a' 本身是 key 终点，不能被合并。压缩只对长度 ≥ 2 的一元链有效，短 key 几乎没有可压空间。

**2.** 每个 key 对应唯一叶子 → 叶子数 = n。压缩后每个内部节点至少 2 个孩子（否则会被合并进边）。设内部节点数 I，总节点 = n + I，边数 = n + I − 1；又边数 = Σ孩子数 ≥ 2I。于是 n + I − 1 ≥ 2I → I ≤ n − 1 → 总节点 ≤ 2n − 1。
「两两不为前缀」用在这一步：它保证**每个 key 都对应一个叶子**，不会有 key 终止在内部节点上。允许前缀关系时，终止在内部的 key 也要占节点，最坏每条 key 多 1 个，上界变成 **2n**（n 个叶子 + 至多 n 个内部节点）。

**3.** 例子里插入了 "card" 与 "car"。`search("ca")` 会走 c→a，路径存在，若不检查 `is_end` 就返回 true——但 "ca" 从未被插入。更隐蔽的情形：只插入 "card" 而没插 "car" 时，`search("car")` 也会错误返回 true。**路径存在只说明「它是某个 key 的前缀」，不说明「它是 key」。**

**4.** 深度 d 节点数 ≤ min(26^d, 10^5)：d=1 取 26；d=2 取 676；d=3 取 17,576；d=4 取 min(456,976, 10^5) = 100,000；d=5…8 各 100,000。
节点数 ≤ 1 + 26 + 676 + 17,576 + 100,000 + 4×100,000 = **518,279**。
内存 = 518,279 × 208 B = 107,802,032 B ≈ **107.8 MB**。
哈希集合：字符 10^5×8 = 800,000 B；条目开销 10^5×24 = 2,400,000 B；桶数组（负载因子 0.5）2×10^5×8 = 1,600,000 B，合计 **4.8 MB**。比值 107.8/4.8 ≈ **22 倍**。

**5.** 正查找（key 存在）：两者都是 Θ(L)——哈希必须读完 L 个字符算哈希，Trie 必须走 L 层。Trie 的优势在常数：数组节点是一次下标访问，哈希是「算函数 + 取模/掩码 + 探测 + 解引用」，长 key 还要完整扫描一遍。
负查找（key 不存在）：Trie 在**第一个失配字符**处就返回，代价 O(d)，d 为失配深度；随机数据、大字母表下 d 期望很小（约 1–2 层）。哈希必须先把**整个 L 字符**读完算出桶号，才能发现桶里没有。所以负查找可以是 O(1) vs O(L)。这就是 Trie 在拼写检查、路由查表这类「绝大多数查询都是负的」场景里真正赢的地方。
另外两条不进渐进复杂度但很重要：Trie 有最坏情况保证（哈希可能被对抗性 key 打退化），Trie 支持前缀查询（哈希根本不支持）。

**6.** 每个节点预存「本子树按词频排序的 top-k 列表」，存 key 的 ID 与分数，不存完整字符串。
查询：走前缀 O(L) + 读列表 O(k)。插入：路径上 L 个祖先各要合并一次新 key，每层 O(k)，共 **O(L·k)**。
空间：78,216 × 10 × 12 B = 9,385,920 B ≈ **9.4 MB**，比基础 Trie 的 16.3 MB 多约 58%。

**7.** IPv4 是 32 位，最大深度 **32**（IPv6 是 128）。
节点数上界 = Σ_{d=1..32} min(2^d, 5×10^5)：d=1…18 求和 = 2^19 − 2 = 524,286；d=19 时 2^19 = 524,288 > 500,000，故 d=19…32 共 14 层各取 500,000 = 7,000,000。合计 ≈ 524,286 + 7,000,000 + 1 ≈ **7.52×10^6**。
内存 = 7.52×10^6 × 12 B ≈ **90 MB**。
这说明：查询 32 步确实快，但 90 MB 的 SRAM 对路由器太贵，且 32 次指针追逐 ≈ 32 次潜在 cache miss。多比特 Trie 一次消费 s 个 bit，把树高降到 32/s，用「每节点 2^s 个槽」换「层数减少」，从而压低内存访问次数。
