# 15-445 L20：时间戳排序（Timestamp Ordering）

> **重要说明**：截至 2026-11-10，Fall 2026 官网**尚未发布**本讲的 slides 与 notes（课表日期 Nov 11）。因此本篇第 5 节及之后的技术内容**以下为通用知识整理，非依据 2026 官方讲义**，仅按数据库教材的标准知识框架组织，供预习与对照使用。官方材料发布后须逐条核对并重写。
>
> 本讲在课程中的定位：第 19 讲的 2PL 用**锁**强制冲突顺序；本讲改用**时间戳**——事务开始时领取一个单调递增的时间戳，DBMS 强制「所有冲突操作按时间戳顺序生效」，从而**无需等待、无需死锁检测**。代价是**冲突即中止**，以及需要维护读写时间戳的元数据。这一讲通常还覆盖**乐观并发控制（OCC）** 作为第三个流派。

## 1. 本节学习目标

学完本讲，你应该能够：

1. 解释**基于时间戳的并发控制**的基本思想：用事务开始时刻的时间戳定义一个**串行顺序**，并强制所有冲突操作遵守它。
2. 说明**基本时间戳排序（Basic T/O）** 的两条规则（过晚读、过晚写），以及它为什么保证冲突可串行化、为什么**无死锁**。
3. 指出基本 T/O 的致命弱点：**不可恢复（non-recoverable）**——事务可能读到尚未提交的数据，且写者回滚后读者已提交。
4. 描述 **Thomas Write Rule（托马斯写规则）** 如何通过「忽略过晚写」放宽规则，以及它产生的调度**不是冲突可串行化而是视图可串行化**。
5. 说明 **乐观并发控制（OCC）** 的三阶段：**读阶段（read phase）**、**验证阶段（validation phase）**、**写阶段（write phase）**，以及为什么它适合**低冲突**负载。
6. 对比 **2PL / T/O / OCC** 三种协议在阻塞、死锁、中止率、元数据开销上的差异。
7. 说明时间戳分配方式（系统时钟、逻辑计数器、混合）及其在分布式环境下的问题。

## 3. 核心概念

> 以下概念定义为通用教材口径，待 2026 官方 slides 发布后核对术语与侧重。

### 3.1 Timestamp（时间戳）

每个事务在 `BEGIN` 时获得的唯一、单调递增的数值 `TS(Ti)`。它定义了事务在**逻辑串行顺序**中的位置：`TS(Ti) < TS(Tj)` 意味着 Ti 在串行顺序中排在 Tj 之前。

### 3.2 Timestamp Ordering（时间戳排序）

一类并发控制协议：不阻塞事务，而是**检查每个操作是否违反时间戳顺序**；若违反则中止该事务（并通常用**同一时间戳**重启）。

### 3.3 Read Timestamp / Write Timestamp（读时间戳 / 写时间戳）

每个数据对象 X 维护两个元数据：`R_TS(X)` = 读过 X 的最大事务时间戳；`W_TS(X)` = 写过 X 的最大事务时间戳。

### 3.4 Basic Timestamp Ordering（基本时间戳排序）

两条规则：

- **读规则**：若 `TS(Ti) < W_TS(X)`，说明 X 已被一个「更晚」的事务写过，Ti 读到的将是「未来」的值 → **Ti 中止**。否则执行读，并令 `R_TS(X) = max(R_TS(X), TS(Ti))`。
- **写规则**：若 `TS(Ti) < R_TS(X)`，说明 X 已被一个「更晚」的事务读过，Ti 的写会让那个事务读到错误的值 → **Ti 中止**。若 `TS(Ti) < W_TS(X)`，说明有更晚的事务已写过 X → **Ti 中止**（或用 Thomas 规则忽略）。否则执行写，令 `W_TS(X) = TS(Ti)`。

### 3.5 Thomas Write Rule（托马斯写规则）

对写规则的一处放宽：若 `TS(Ti) < W_TS(X)`，**直接忽略这次写**（不写、不中止），因为后面那个事务的写已经覆盖了它，Ti 的写在最终结果中不可见。产生的调度**不是冲突可串行化的，但是视图可串行化的**。

### 3.6 Optimistic Concurrency Control（乐观并发控制，OCC）

假定冲突很少，先让事务**无阻塞地执行**并把写暂存在**私有工作区（private workspace）**，提交前做**验证**，通过才真正写入数据库。

### 3.7 Read Phase / Validation Phase / Write Phase（读阶段 / 验证阶段 / 写阶段）

OCC 的三个阶段：读阶段执行事务并把读写集记录下来；验证阶段检查本事务的读写集是否与并发事务冲突；写阶段把私有修改**原子地**应用到数据库。

### 3.8 Validation（验证）

对事务 Ti 与其之前已提交的事务 Tj 检查：是否存在「Ti 读了 Tj 后来写的数据」或「Ti 写了 Tj 读过/写过的数据」的冲突。常用**向后验证（backward validation）**：只与已提交的并发事务比较。

## 4. 通俗理解

**2PL 像「排队借书」**：书被借走了就等，等到为止。**T/O 像「按编号办事」**：每个人进门领一个号，所有操作必须按号的顺序生效；如果发现「号小的人来得太晚」（该他先做的事被号大的人抢先做了），那这个人就**作废重来**（拿原来的号重新排队）。

**为什么 T/O 不会死锁**：因为没有人**等**——要么立刻做，要么立刻死。死锁的前提是「互相等待」，而 T/O 里根本没有等待这个状态。

**为什么 T/O 有个大坑**：号小的 Ti 读了号大的 Tj 写的值（在 T/O 里这是允许的，只要 Ti 的号不小于 W_TS），但 Tj 还没提交。如果 Tj 后来回滚了，Ti 读的就是「从未存在过」的数据——而 Ti 可能已经提交。这就是**不可恢复**。

**OCC 像「先在家把作业写完，交之前检查有没有和同学撞题」**：读阶段在自己的草稿纸上算，不碰公共数据；验证阶段检查「我算的过程中，我用的数据有没有被别人改过」；写阶段才一次性抄到黑板上。冲突少的时候极快（几乎无阻塞），冲突多的时候大量作废重算。

## 5. 原理与推导

> **以下为通用知识整理，非依据 2026 官方讲义。**

### 5.1 时间戳从哪来

三种做法：

1. **系统时钟（system clock）**：直接用 `clock_gettime`。问题：同一毫秒内多个事务会拿到相同时间戳；时钟回拨会破坏单调性。
2. **逻辑计数器（logical counter）**：一个全局原子计数器，每次 `BEGIN` 加一。单调但成为**争用热点**（高并发下 cache line 抖动）。
3. **混合（hybrid）**：每台机器一个计数器 + 机器 ID 拼接（`(counter << 16) | machine_id`），分布式下保证全局唯一但不保证全局单调。

**分布式下的难点**：无法低成本获得全局单调时间戳，这是后来 Google Spanner 用 **TrueTime**（原子钟 + GPS，给出时间区间而非点）的动机。

### 5.2 基本 T/O 的正确性论证

**不变式**：对任意对象 X，`R_TS(X)` 与 `W_TS(X)` 单调不减，且始终反映「已成功执行的操作中最大的时间戳」。

**关键推论**：若 Ti 成功读了 X，则此后任何 `TS < TS(Ti)` 的事务都不能再写 X（会被写规则中止，因为 `TS < R_TS(X)`）。同理，若 Ti 成功写了 X，此后任何 `TS < TS(Ti)` 的事务既不能读（读规则）也不能写（写规则）。

因此**所有成功的操作都按时间戳顺序生效**——这正是一个「按 `TS` 排序的串行调度」，所以是**冲突可串行化**的。

**无死锁**：协议里没有「等待」这个动作，事务要么立即执行要么立即中止。**死锁需要等待环，而这里没有等待**。

**代价**：冲突率高时**中止率极高**（长事务几乎必然被短事务「挤掉」），而且中止的工作全部浪费。

### 5.3 不可恢复问题

基本 T/O 只保证**可串行化**，不保证**可恢复**。反例：

```
TS(T1) = 10, TS(T2) = 20
T1: W(A)                       ← W_TS(A) = 10
T2: R(A)                       ← TS(T2)=20 > W_TS(A)=10，允许读（脏读！）
T2: COMMIT                     ← T2 已提交
T1: ABORT                      ← T1 回滚，A 恢复到旧值
```

T2 读到的是 T1 未提交的写，T1 回滚后 T2 的读「基于从未存在的数据」，但 T2 已经提交，无法回滚 → **数据库不一致**。

**修法**：把 T/O 与 **Strict 2PL 的思想**结合——延迟写操作直到写者提交（**写缓冲 / 提交时写入**），或要求读操作只读已提交版本（这就滑向了 **MVCC**，见 [[15-445-21-MVCC]]）。教材里的标准解法是 **Strict Timestamp Ordering**：事务的写先记在本地，提交时才真正写入并检查冲突。

### 5.4 Thomas Write Rule

规则：若 `TS(Ti) < W_TS(X)`，**跳过这次写**（既不写也不中止）。

**为什么可以跳过**：X 的当前值由 `W_TS(X)` 对应的事务写入，那个事务在串行顺序中排在 Ti **之后**，所以它的写会覆盖 Ti 的写——Ti 的写在最终结果里本来就看不见。

**正确性级别**：Thomas 规则产生的调度**不是冲突可串行化的**（因为丢弃了一个冲突操作），但**是视图可串行化的**——最终写值仍然正确。这也解释了为什么「视图可串行化」在实践中偶尔会被用到（仅限这种可判定的特例）。

**注意**：Thomas 规则**只放宽写-写冲突**，不改读规则，因此**不可恢复问题依然存在**。

### 5.5 OCC 的三阶段

| 阶段 | 做什么 | 关键点 |
|---|---|---|
| **Read Phase** | 执行事务的所有读与写；写只作用于**私有工作区**（或本地临时副本） | 数据库不受影响，因此**无阻塞** |
| **Validation Phase** | 检查本事务的**读集**与**写集**是否与并发事务冲突 | 通常用**向后验证**，只与已提交的并发事务比较 |
| **Write Phase** | 把私有修改**原子地**写入数据库 | 需要短临界区（通常用 latch 保护） |

**验证规则（教材口径）**：对 Ti 与其之前已进入验证阶段的 Tj，要求满足以下之一：

1. `TS(Tj) < TS(Ti)` 且 **Tj 在 Ti 开始读之前已完成写阶段**（无重叠）；
2. `TS(Tj) < TS(Ti)` 且 **Tj 的写集与 Ti 的读集不相交**；
3. `TS(Tj) < TS(Ti)` 且 **Tj 在 Ti 开始写之前已完成写阶段**。

不满足则 Ti 中止。

**适用性**：OCC 在**冲突率低**时性能极好（几乎无阻塞、无死锁），在**冲突率高**时因为大量重做而性能崩溃。经典结论是：**OCC 适合读多写少、事务短小、资源争用低**的场景；高争用下 2PL 更稳。

### 5.6 三种协议对比

| 维度 | 2PL（含 SS2PL） | Basic T/O | OCC |
|---|---|---|---|
| 冲突时行为 | **等待**（阻塞） | **中止** | **中止**（验证失败） |
| 死锁 | 有，需检测/预防 | 无 | 无 |
| 饿死 | 有（受害者选择） | 有（长事务被反复中止） | 有 |
| 元数据开销 | 锁表 | 每对象的 `R_TS`/`W_TS` | 每事务的读写集 |
| 高冲突负载 | 较好（等待而非重做） | 差（中止率高） | 差（重做率高） |
| 低冲突负载 | 一般（锁开销） | 好 | 最好 |
| 可恢复性 | SS2PL 天然可恢复 | 需额外机制 | 写阶段原子，较易做到 |
| 典型实现 | MySQL InnoDB（SERIALIZABLE） | 少数内存数据库 | 内存数据库、部分研究系统 |

### 5.7 为什么现代 DBMS 大多不用纯 T/O

1. **中止代价高**：T/O 的中止是「全部白干」，而 2PL 的等待只是「慢一点」。
2. **长事务天然吃亏**：时间戳小的长事务只要被一个短事务抢了先，就要重来；在混合负载（OLTP + 报表）下几乎不可用。
3. **不可恢复**：需要额外机制，反而增加了复杂度。
4. **MVCC 更优**：MVCC 把「读」变成读快照，读不阻塞写、写不阻塞读，同时避免了 T/O 的中止风暴——它本质上吸收了 T/O 的「多版本 + 时间戳」思想，但用版本链代替了中止。

**但 T/O 的思想没有消失**：MVCC 的版本可见性判定（`begin_ts <= version_ts`）、快照隔离、Spanner 的 TrueTime 排序，全都是时间戳排序的直接后裔。

### 6.2 Agent 自行编写的教学示例

> 以下代码**非官方，仅用于说明概念**。

基本时间戳排序的读/写检查（示意）：

```cpp
// 非官方示例：Basic T/O 的读规则与写规则
struct ObjectMeta {
  uint64_t read_ts{0};   // R_TS(X)
  uint64_t write_ts{0};  // W_TS(X)
};

enum class Status { kOk, kAbort };

Status Read(ObjectMeta &m, uint64_t ts) {
  if (ts < m.write_ts) return Status::kAbort;   // 想读"未来"的值 → 中止
  m.read_ts = std::max(m.read_ts, ts);
  return Status::kOk;
}

Status Write(ObjectMeta &m, uint64_t ts, bool thomas_rule) {
  if (ts < m.read_ts) return Status::kAbort;    // 有人已经读过"我的未来"
  if (ts < m.write_ts) {
    if (thomas_rule) return Status::kOk;        // 忽略这次写，不中止
    return Status::kAbort;
  }
  m.write_ts = ts;
  return Status::kOk;
}
```

OCC 的三阶段骨架（示意）：

```cpp
// 非官方示例：OCC 事务生命周期
struct Txn {
  uint64_t ts;
  std::unordered_set<Key> read_set;
  std::unordered_set<Key> write_set;
  std::unordered_map<Key, Value> workspace;  // 私有工作区
};

bool Validate(const Txn &ti, const std::vector<Txn> &committed) {
  for (const auto &tj : committed) {
    if (tj.ts >= ti.ts) continue;                        // 只与更早的事务比较
    if (tj.write_set == ti.read_set) return false;        // 写-读冲突
    if (Overlaps(tj.write_set, ti.write_set)) return false;
  }
  return true;
}
```

一个违反时间戳顺序的最小场景（示意）：

```text
TS(T1)=10, TS(T2)=20
T2: W(A)  → W_TS(A)=20
T1: R(A)  → 10 < 20，违反读规则 → T1 中止（否则 T1 会读到"未来"的值）
```

## 7. 容易混淆的概念

| 概念 A | 概念 B | 关键差别 |
|---|---|---|
| 2PL | T/O | 前者用**等待**强制冲突顺序，会死锁；后者用**中止**强制冲突顺序，不死锁但中止率高 |
| 基本 T/O | Thomas Write Rule | 前者过晚写即中止；后者**忽略**过晚写，得到视图可串行化（非冲突可串行化） |
| 冲突可串行化 | 视图可串行化 | Thomas 规则产生的调度属于后者不属于前者 |
| T/O | MVCC | 都用时间戳，但 T/O 单版本 + 中止；MVCC 多版本 + 快照读，读不阻塞写 |
| OCC 的「乐观」 | 「不检查」 | OCC 只是**推迟**检查到验证阶段，检查本身很严格 |
| 时间戳 | LSN | 时间戳标识**事务的逻辑顺序**；LSN 标识**日志记录的物理顺序**（第 22 讲） |

- 能说明 Thomas Write Rule 放宽了什么、得到的调度属于哪一级可串行化。
- 能描述 OCC 三阶段，并说出它适合什么样的负载。
- 能列表对比 2PL / T/O / OCC 在死锁、中止、元数据上的差异。
- 能解释为什么 MVCC 是时间戳排序思想的「进化版」。

## 11. 自我检查

**Q1.** 设 `TS(T1)=10`、`TS(T2)=20`，初始 `R_TS(A)=0`、`W_TS(A)=0`。执行序列 `W2(A), R1(A)` 在 Basic T/O 下会怎样？在 Thomas Write Rule 下会怎样？

<details><summary>参考答案</summary>

**Basic T/O**：

- `W2(A)`：`TS(T2)=20 >= R_TS(A)=0` 且 `>= W_TS(A)=0` → 允许，`W_TS(A) = 20`。
- `R1(A)`：`TS(T1)=10 < W_TS(A)=20` → 违反读规则 → **T1 中止**。

理由：T1 在串行顺序中应排在 T2 之前，但现在 T2 已经写了 A。若让 T1 读，T1 读到的就是「未来」的值，等价于 T1 看到了本不该看到的数据。

**Thomas Write Rule**：Thomas 规则**只放宽写规则**，不改读规则，所以 `R1(A)` 依然会中止 T1。**结果相同**。

要观察 Thomas 规则的差异，需要构造「过晚写」：`R2(A), W1(A)`（`TS(T1)=10 < R_TS(A)=20`）。此时 Basic T/O 会中止 T1，Thomas 规则**也会**中止 T1（因为 `TS(T1) < R_TS(A)` 是**读**规则的镜像，属于「写规则第一条」）。真正体现 Thomas 规则的是 `W2(A), W1(A)`：Basic T/O 因 `TS(T1)=10 < W_TS(A)=20` 中止 T1；Thomas 规则**忽略 W1(A)**，T1 继续执行。

</details>

**Q2.** 为什么说「时间戳排序不会死锁」？这个结论有没有前提？

<details><summary>参考答案</summary>

**结论成立的理由**：死锁的定义是「事务之间存在一个**等待环**」——每个事务都在等另一个事务释放资源。Basic T/O 中事务**从不等待**：每个操作要么立即执行（更新元数据），要么立即中止。既然没有「等待」这个状态，就不可能形成等待环，因此**不可能死锁**。

**前提与注意事项**：

1. 这个结论只对**纯 T/O**（无阻塞版本）成立。**Strict T/O** 若在提交时争用写锁，仍可能出现短暂的等待，需要仔细设计才能保持无死锁。
2. **无死锁不等于无饥饿**：一个长事务可能因为反复被「过晚」判定而无限次中止重启（虽然用原始时间戳重启可以缓解优先级问题，但不能完全消除饥饿）。
3. 若 T/O 与**闩锁（latch）**混用，latch 层面的死锁仍然可能发生（那是编码纪律问题，与协议无关）。
4. 在**分布式** T/O 中，若跨节点需要等待消息，也可能出现分布式死锁。

所以更准确的说法是：**纯 T/O 在单机、不引入额外等待机制的前提下不会死锁**。

</details>

**Q3.** OCC 在什么负载下会表现得比 2PL 差？为什么？

<details><summary>参考答案</summary>

**OCC 在高冲突、长事务、写密集的负载下明显更差**，原因有三：

1. **重做成本**：OCC 的冲突处理方式是**中止并重做整个事务**，而 2PL 只是**等待**。在冲突率 30% 的负载下，OCC 的有效吞吐可能只剩 70%，而 2PL 只是延迟增加。
2. **验证阶段成为瓶颈**：验证需要把本事务的读写集与所有并发提交事务比较，复杂度与并发度成正比；高并发时验证本身的开销可能超过执行。
3. **长事务窗口大**：事务越长，读阶段跨越的时间越久，与别人冲突的概率越高，被中止的概率也越高——形成「越长越容易被杀」的正反馈。

**适合 OCC 的负载**：读多写少、事务短、并发度高但**访问的数据不重叠**（如按用户分片的 OLTP、内存数据库的主键点查）。

**实践中的折中**：很多系统用 **MVCC + 短临界区**代替纯 OCC——读走快照（无阻塞），写用行锁（短等待），既避免了 OCC 的中止风暴，也避免了 2PL 的长等待。

</details>

**Q4.** Thomas Write Rule 产生的调度「不是冲突可串行化但是视图可串行化」，请用一个具体例子说明。

<details><summary>参考答案</summary>

设 `TS(T1)=10`、`TS(T2)=20`，初值 `A=100`，执行序列：

```
W1(A, 200)    ← TS=10，W_TS(A)=0，允许，W_TS(A)=10
W2(A, 300)    ← TS=20，允许，W_TS(A)=20
W1(A, 400)    ← TS=10 < W_TS(A)=20 → Thomas 规则：忽略
```

**冲突可串行化分析**：冲突操作对是 `W1(A)`（第一次）与 `W2(A)` → 边 `T1 → T2`；`W2(A)` 与 `W1(A)`（第三次，若执行）→ 边 `T2 → T1`。若第三次写**被执行**，优先图成环，**不可冲突可串行化**。

**Thomas 规则的做法**：忽略第三次写，于是只有 `T1 → T2`，无环——等等，这样它**就是**冲突可串行化的了？

关键在于：**忽略操作本身就改变了调度**。若我们把「原始调度」（含第三次写）拿来判定，它不可冲突可串行化；Thomas 规则把它**改写成**了一个冲突可串行化的调度。严格说，Thomas 规则的正确性论证是**视图等价**：在原始调度中，A 的最终值是 300（`W2` 最后写），在串行调度 `T1, T2` 中最终值也是 300，**最终写相同**，且没有读操作受影响——所以两者**视图等价**。而原始调度本身不可冲突可串行化，因此 Thomas 规则**接受了冲突不可串行化的调度**，只是通过丢弃写让它变得安全。

**一句话总结**：Thomas 规则之所以能接受「优先图有环」的调度，是因为环中的一条边对应一个**blind write（不看原值直接写）**，而 blind write 不影响任何读，只影响最终写值——只要最终写值对得上，视图等价就成立。

</details>

**Q5.** 既然 MVCC 性能更好，为什么还有系统（如部分内存数据库）选择时间戳排序？

<details><summary>参考答案</summary>

MVCC 的优势建立在**多版本存储**的代价之上，T/O 在以下场景反而更合适：

1. **内存数据库**：没有磁盘 I/O，版本链的额外内存开销成为主要成本；单版本 + 时间戳校验的内存占用小得多（如早期 VoltDB 的思路、部分研究型内存引擎）。
2. **极短事务**：事务只做一两次点查时，MVCC 的版本链遍历与垃圾回收开销可能超过事务本身。
3. **确定性数据库（deterministic DB）**：如 Calvin、Bohm，用确定性排序代替并发控制，本质是「预定义时间戳顺序」，比 T/O 更激进。
4. **只读分析型负载 + 单写者**：如 HyPer、Kudu 的部分模式，写者唯一时时间戳排序几乎零冲突。
5. **教学与可证明性**：T/O 的正确性证明极简洁（一个不变式），在需要形式化验证的场景有优势。

**反过来说**，通用 OLTP 系统（PostgreSQL、MySQL、Oracle、SQL Server）几乎全部选择 **MVCC**，因为混合负载下的读不阻塞写带来的吞吐优势远大于版本存储成本。这是「工作负载决定协议」的典型案例。

</details>
