# 15-445 L17：查询规划与优化 II（Query Planning & Optimization II）

> 上一讲解决「搜索空间怎么走」，这一讲解决「怎么给一条计划打分」。核心链条是：**统计信息 → 选择率 → 基数估计 → 代价模型 → 计划选择**。链条上任何一环估错，优化器都会挑错计划——这就是真实数据库里「明明有索引却走了全表扫描」的根本原因。

## 1. 本节学习目标

学完本讲，你应该能够：

1. 区分**物理代价（physical cost）**与**逻辑代价（logical cost）**，并说明为什么逻辑代价（中间结果大小）是优化器必须估计的量。
2. 说明统计信息存在哪里、由谁更新（后台任务 / 维护窗口 / 手动命令），以及「统计信息过期」会带来什么后果。
3. 比较四种**数据摘要（statistical summary）**：直方图、草图、采样、机器学习模型，说出各自的空间复杂度与误差特性。
4. 区分**等宽直方图（equi-width）**与**等深直方图（equi-depth）**，并说明为什么等深直方图的误差更小。
5. 用 **Count-Min Sketch** 估计频次、用 **HyperLogLog** 估计 distinct 值，并解释前者为什么只会高估。
6. 用**选择率（selectivity）**公式估算等值、范围、否定、合取、析取谓词的选择率，并说明三条假设（均匀、独立、包含）在什么情况下失效。
7. 估算两表连接的结果大小，并解释**误差传播（error propagation）**为什么会让多表连接的估计差出几个数量级。

## 3. 核心概念

### 3.1 Cost Model（代价模型）

把物理计划映射成一个可比较的数值，用来预测计划的运行时间。单位可以是 CPU 周期、I/O 次数、内存字节、网络消息数——但**整个模型必须用同一种单位**，否则无法相加比较。

### 3.2 Physical Cost vs Logical Cost（物理代价 vs 逻辑代价）

**物理代价**：CPU cycles、磁盘 I/O、cache miss、RAM 使用、网络消息——依赖具体硬件与实现。**逻辑代价**：每个算子的**估计输出大小**（行数 × 行宽）——与算法无关，只与数据和谓词有关。优化器必须先算逻辑代价，才能代入物理代价公式。

### 3.3 Statistical Summary（统计摘要）

DBMS 在 catalog 里维护的、对数据分布的**有损压缩表示**。它必须同时满足两个矛盾的要求：**空间小**（不能和表一样大）、**误差可控**（估计不能离谱）。

### 3.4 Histogram（直方图）

把属性值域切成若干**桶（bucket）**，每桶记录计数或范围。四种变体：精确计数（exact）、等宽、等深、端偏（end-biased）。

### 3.5 Equi-Width Histogram（等宽直方图）

每个桶覆盖**相同宽度的值域**（如 `[1,5]`、`[6,10]`、`[11,15]`）。实现简单，但对**倾斜数据**很差：高频值可能和一堆低频值挤在同一个桶里，桶内计数完全失真。

### 3.6 Equi-Depth Histogram（等深直方图）

每个桶内的**计数近似相等**（值域宽度可变）。因为桶是「按行数切」而非「按值域切」，它对倾斜数据的**最坏误差与平均误差都更好**，是多数系统的默认选择。

### 3.7 End-Biased Histogram（端偏直方图）

用 **N−1 个桶存最频繁的键的精确计数**，最后一个桶存其余所有值的**平均频率**。它把「有限的统计预算」优先花在最可能被查询命中的高频值上，对 Zipf 分布（真实数据最常见的分布）特别有效。

### 3.8 Sketch（草图）

一类**概率数据结构**，用远小于精确统计的空间给出近似答案。常见三种：**Count-Min Sketch**（频次）、**HyperLogLog**（distinct 值个数）、**t-digest**（分位数）。

### 3.9 Sampling（采样）

对表的**随机样本**执行谓词，用样本上的选择率估计全表选择率。优点是不依赖任何分布假设、能处理相关性；缺点是样本小时方差大。

### 3.10 Cardinality Estimation（基数估计）

估计一个算子会输出多少行。需要三类估计：**选择条件的选择率**、**连接结果大小**、**distinct 值个数**（用于后续连接与聚合）。

### 3.11 Selectivity（选择率）

满足谓词的行数占输入行数的比例，取值 `[0, 1]`。`sel(P) = |σ_P(R)| / |R|`。它是基数估计的基本积木。

### 3.12 Containment Principle（包含假设）

估计连接大小时假设**连接键的值域重叠**：内表的每个键值在外表中都能找到匹配。这条假设让 `R ⋈ S` 的估计变成一个简单公式，但对「外键指向不存在的主键」这类数据会高估。

## 4. 通俗理解

把优化器想成一个**要预测明天客流量的店长**。

- **统计摘要** = 他手头的报表。**精确计数** = 逐笔流水（准，但占地方）；**直方图** = 「每小时客流柱状图」；**草图** = 「凭经验估个大概」；**采样** = 「随机抽查 100 个人问一问」。
- **等宽直方图** = 把一天按**每两小时**切段统计。问题是：如果下午 3 点有个高峰，它和旁边冷清的时段挤在同一格里，这一格的平均值就完全误导人。
- **等深直方图** = 不按时间切，而是**按人数切**：每格装差不多同样多的人。高峰那一格自然变窄，细节被保留下来。
- **端偏直方图** = 把大部分格子留给**最热门的几个时段**（如午餐、晚餐），剩下的冷门时段合并成一格估个平均。因为店长知道，查报表的人 90% 都在问高峰时段。

**选择率**就是「这个条件能筛掉多少人」。店长估「明天会来多少人」时，先估「下雨的概率」（选择率），再乘上「总客流量」（基数）——一步估错，后面全错。

**误差传播**就像传话游戏：第一个人把「100 人」听成「1,000 人」，后面每个环节都基于这个错数字再放大，传到第十个人就变成「一亿人」。

## 5. 原理与推导

### 5.1 代价模型的组成

物理代价公式的典型形式（以顺序扫描为例）：

```
cost(SeqScan) = N_pages × c_io + N_tuples × c_cpu
```

其中 `c_io` 是读一页的代价（磁盘或缓存未命中）、`c_cpu` 是处理一个元组的 CPU 代价。**Postgres 的做法**是用「magic constants」把 CPU 与 I/O 加权：

- 默认假设数据**在磁盘上**（不是全在内存里）；
- 内存中处理一个元组比从磁盘读一个元组快约 **400 倍**；
- **顺序 I/O 比随机 I/O 快约 4 倍**。

Postgres 官方文档自己承认：**没有确定最优常数的方法**，这些比例是经验值，与硬件强相关。这就是代价模型最大的软肋——它必须用一组固定常数去近似一个随硬件剧烈变化的现实。

### 5.2 统计信息的存储与更新

统计信息存在 **system catalog**（如 Postgres 的 `pg_statistic`），更新时机有四类：

1. **后台任务**：Postgres 的 **autovacuum** 在表变化超过阈值时自动 `ANALYZE`。
2. **维护窗口**：Oracle 在夜间维护窗口收集统计信息。
3. **修改阈值触发**：某些系统在「自上次统计以来修改行数 > X%」时触发。
4. **手动**：`ANALYZE`（Postgres）、`UPDATE STATISTICS`（SQL Server / DB2）。

**统计信息过期**的后果：优化器用旧分布估新数据，可能把「现在只剩 100 行」的表当成「还有 100 万行」，于是选择错误的连接顺序与连接算法。这是生产环境最常见的「计划突然变差」原因之一。

### 5.3 四种直方图的对比推导

设一张 45 个元组、15 个不同值的表，`equi-width` 的桶计数是 `9, 4, 15, 3, 14`。

| 类型 | 桶的含义 | 空间 | 对倾斜数据 |
|---|---|---|---|
| 精确计数 | 每个不同值一个计数器 | ∝ distinct 值数（可能极大） | 完美 |
| 等宽 | 每桶**相同值域宽度** | 固定桶数 | 差（高频值被平均掉） |
| 等深 | 每桶**计数近似相等** | 固定桶数 | 较好 |
| 端偏 | N−1 桶存最高频键的**精确**计数，最后 1 桶存其余值的平均频率 | 固定桶数 | 最好（对 Zipf） |

端偏的具体计算：若 45 个元组、15 个不同值、最高频的键出现 17 次，则最后一桶存剩余 `45 − 17 = 28` 个元组、`15 − 1 = 14` 个不同值，平均频率 = `28 / 14 = 2`；而某条资料里给出的 `17/10 = 1.7` 是另一种划分方式下的结果，**具体数字以讲义图为准**。

> 待核实：notes 第 3 页 Figure 2 的端偏示例给出「最后一桶 17/10 = 1.7」，与 slides 第 72 页的示意口径可能不同（不同值个数或最高频键的取法不同），引用时请以 PDF 原图为准。

### 5.4 Count-Min Sketch 为什么只会高估

结构：`d` 个独立哈希函数、`d` 行 × `w` 列计数器。

- **插入 x**：对每行 `i`，把 `count[i][hash_i(x) mod w]` 加一。
- **查询 x**：返回 `min_i count[i][hash_i(x) mod w]`。

推导：某个计数器 `count[i][j]` 的值 = 「哈希到该格的所有元素的真实频次之和」≥ 「x 的真实频次」。因为哈希碰撞只会**把别人的计数加进来**，永远不会把 x 的计数减掉。所以每行都是**高估**，取 `d` 行的**最小值**就是最紧的上界。

例：查 `ODB` 得到四个计数器 `2, 3, 6, 3`，取 `min = 2`，即估计频次为 2（真实值 ≤ 2，通常等于 2）。

### 5.5 HyperLogLog 的推导

目标：估计 distinct 值个数，空间只要 KB 级。

1. 取 `m = 2^b` 个计数器（桶）。
2. 对元素 `x` 求哈希 `h(x)`；用**末 b 位**选择桶号；用**剩余位**中「最左边 1 出现在第几位」作为该桶的观测值。
3. 每个桶维护**观测到的最大值**（`max`）。
4. 估计值 = 调和平均数 × 修正常数。

直觉：如果见过 `n` 个不同元素，那么「最左 1 出现在第 k 位」的期望最大值约为 `log2(n)`。取最大值的调和平均是为了**抑制离群桶**（某个桶恰好抽到极端值）的影响。

例：`hash(ODB) = 9022`，末两位选桶 2，剩余位中 1 在第 3 位 → 桶 2 的值更新为 `max(0, 3) = 3`。

### 5.6 选择率公式

维护两个基础统计量：

- `N_R`：关系 R 的元组数
- `V(A, R)`：R 中属性 A 的**不同值个数**

导出：`SC(A, R) = N_R / V(A, R)`，即「A 每个取值平均对应多少行」。

**等值谓词** `sel(A = c)`：

- 有精确计数时：`sel = count(A = c) / |R|`。例：`sel(age = 9) = 4/45 ≈ 0.088`。
- 只有等深直方图时：桶 `[9,13]` 有 9 个元组、5 个不同值 → 每值 `9/5 = 1.8` → `sel ≈ 1.8/45 ≈ 0.04`。

**范围谓词** `sel(A ≥ a)`：

```
sel = (A > a 的元组数 + A = a 的元组数) / |R|
```

例：`age ≥ 7`。桶 `[9,13]` 的 9 个、`[14,15]` 的 12 个全部满足；桶 `[6,8]` 有 12 个元组、3 个不同值，其中 7、8 两个值满足 → 约 `2 × (12/3) = 8` 个。总计 `9 + 12 + 8 = 29` → `sel ≈ 29/45 ≈ 0.644`。

**否定谓词** `sel(not P) = 1 − sel(P)`。例：桶 `[1,5]` 有 12 个元组、5 个不同值 → `sel(age = 2) ≈ (12/5)/45 ≈ 0.053` → `sel(age ≠ 2) ≈ 0.95`。

**合取**（假设独立）：`sel(P1 ∧ P2) = sel(P1) × sel(P2)`。例：`age = 2 AND name LIKE 'A%'` → `0.053 × 0.1 ≈ 0.0053`。

**析取**：`sel(P1 ∨ P2) = sel(P1) + sel(P2) − sel(P1) × sel(P2)`。同例 → `0.053 + 0.1 − 0.0053 ≈ 0.1477`。

### 5.7 三条假设及其失效场景

- **假设 #1：均匀数据（Uniform Data）**——桶内除 heavy hitter 外分布均匀。失效场景：数据高度倾斜（如「国家」列 90% 是中国），等值选择率会被严重低估。
- **假设 #2：独立谓词（Independent Predicates）**——多个谓词互不相关。失效场景：`make = 'Honda' AND model = 'Accord'`。设 10 种 make、100 种 model，独立假设估 `1/10 × 1/100 = 0.001`；但 Accord 只有 Honda 生产，实际选择率是 `1/100 = 0.01`——**差 10 倍**。多列统计（SQL Server 对索引内共现列自动建、DB2 的 column group statistics、Oracle 的 extended statistics）可缓解。
- **假设 #3：包含原则（Containment Principle）**——连接键值域重叠。失效场景：外键指向的主键被删除、或两个表的时间范围不重叠，会严重高估。

**乘积收缩过快**：合取时把多个选择率直接相乘，谓词一多，估计值会趋近于 0（例如 10 个各 0.1 的谓词相乘 = 1e-10）。有些系统对「额外谓词」做**降权**（如取 `sel^0.5`）来缓解。

### 5.8 连接大小估计

设 R、S 共享一个非主键属性 A：

```
estSize(R ⋈ S) ≈ (N_R × N_S) / max(V(A, S), V(A, R))
```

推导：连接结果的每个元组对应「R 的一行 + S 的一行且 A 值相同」。若假设值域重叠（包含原则），匹配对数 ≈ `N_R × N_S / V(A)`，其中 `V(A)` 取两表中**较大**的不同值个数（分母越大，估计越保守）。实践中会**两个方向各算一次，取较小者**，进一步避免高估。

若 A 是 R 的主键：`V(A, R) = N_R`，公式退化为 `N_S`（外键连接不放大行数）——这也解释了为什么「主键-外键连接」的估计通常很准。

### 5.9 误差传播

考虑 `A ⋈ B ⋈ C`（都按 `id` 连接），且对 `B` 加了过滤 `B.id > 100`：

1. `|B'| = |B| × sel(B.id > 100)`。若真实选择率是 0.5，优化器估成 0.05（错 10 倍）。
2. `A ⋈ B'` 的估计 = `|A| × |B'| / max(V(id,A), V(id,B))`，**继承了那 10 倍误差**。
3. `(A ⋈ B') ⋈ C` 的估计又继承上一层误差。

结论：**误差沿计划树向上累积**，join 越多，估计越离谱。Leis 等人在 IMDB 真实数据集上的研究（PostgreSQL、HyPer 与三个商业 DBMS）发现：**随着 join 数量增加，估计持续变差，且通常表现为低估，可差几个数量级**。低估会让优化器倾向于选择「嵌套循环连接」这类在小数据上快、在大数据上灾难的算法——这是真实系统里最危险的估计错误方向。

### 6.2 Agent 自行编写的教学示例

> 以下代码**非官方，仅用于说明概念**。

Count-Min Sketch 的最小实现（示意）：

```cpp
// 非官方示例：Count-Min Sketch
class CountMinSketch {
 public:
  CountMinSketch(size_t d, size_t w) : d_(d), w_(w), table_(d * w, 0) {}

  void Insert(uint64_t x) {
    for (size_t i = 0; i < d_; i++) table_[i * w_ + Hash(i, x) % w_]++;
  }

  // 只会高估，不会低估
  size_t Estimate(uint64_t x) const {
    size_t best = SIZE_MAX;
    for (size_t i = 0; i < d_; i++)
      best = std::min(best, table_[i * w_ + Hash(i, x) % w_]);
    return best;
  }

 private:
  size_t Hash(size_t i, uint64_t x) const { return std::hash<uint64_t>{}(x + i * 0x9e3779b9); }
  size_t d_, w_;
  std::vector<size_t> table_;
};
```

HyperLogLog 的「最左 1 的位置」计算（示意）：

```cpp
// 非官方示例：取剩余位中最左边 1 的位置（1-based）
int LeftmostOnePosition(uint64_t remaining_bits) {
  if (remaining_bits == 0) return 64;
  return __builtin_clzll(remaining_bits) + 1 - (64 - kRemainingWidth);
}
```

选择率估算（示意）：

```cpp
// 非官方示例：合取与析取选择率
double SelConjunction(double s1, double s2) { return s1 * s2; }                 // 独立假设
double SelDisjunction(double s1, double s2) { return s1 + s2 - s1 * s2; }       // 容斥
// 连接大小估计（取两个方向较小者）
double EstimateJoinSize(double n_r, double n_s, double v_a_r, double v_a_s) {
  return (n_r * n_s) / std::max(v_a_r, v_a_s);
}
```

## 7. 容易混淆的概念

| 概念 A | 概念 B | 关键差别 |
|---|---|---|
| 物理代价 | 逻辑代价 | 前者依赖硬件（CPU/I/O/RAM），后者只估**输出大小**、与算法无关 |
| 等宽直方图 | 等深直方图 | 前者按**值域**等分，后者按**行数**等分；后者对倾斜数据误差更小 |
| 直方图 | 草图 | 前者给**确定但可能失真的桶统计**；后者是**概率结构**，空间更小、有可控误差 |
| Count-Min Sketch | HyperLogLog | 前者估**频次**（只会高估）；后者估 **distinct 值个数**（双向误差） |
| 选择率 | 基数 | 前者是**比例** `[0,1]`；后者是**行数**（= 选择率 × 输入行数） |
| 假设 #1 均匀 | 假设 #2 独立 | 前者描述**桶内分布**；后者描述**多个谓词之间的关系**；两者失效的后果不同 |

## 11. 自我检查

**Q1.** 一张表有 1,000,000 行，`city` 列有 100 个不同值且分布均匀，`age` 列有 80 个不同值且分布均匀。估算 `WHERE city = 'Beijing' AND age = 30` 的选择率与结果行数。如果实际上北京人口占全国 10%、且 30 岁的人有 30% 在北京，真实结果是多少？误差倍数是多少？

<details><summary>参考答案</summary>

**独立假设下的估计**：

- `sel(city = 'Beijing') = 1/100 = 0.01`
- `sel(age = 30) = 1/80 = 0.0125`
- `sel(合取) = 0.01 × 0.0125 = 0.000125`
- 估计行数 = `1,000,000 × 0.000125 = 125` 行。

**真实情况**：

- 北京占 10% → `city = 'Beijing'` 有 100,000 行。
- 30 岁的人有 30% 在北京 → 北京人口中 30 岁的占 `0.3 / 0.1 = 3` 倍于平均（因为「30 岁的人 30% 在北京」意味着北京人口里 30 岁的比例是 `0.3 × (1/80) / 0.1 = 0.0375`）。
- 真实行数 ≈ `100,000 × 0.0375 = 3,750` 行。

**误差倍数**：`3,750 / 125 = 30` 倍（严重低估）。原因是两个谓词**强相关**（年龄结构与城市高度相关），独立假设完全失效。这类低估会让优化器误以为结果很小，从而选择嵌套循环连接，实际执行时性能崩塌。

</details>

**Q2.** 为什么 Count-Min Sketch 取 `d` 行的**最小值**而不是平均值？如果取平均值会怎样？

<details><summary>参考答案</summary>

**取最小值**：每个计数器都是「真实频次 + 碰撞进来的噪声」，噪声只增不减，所以每行都是真实值的**上界**。`d` 个独立哈希的噪声彼此独立，取最小值就取到了**最紧的上界**——噪声最小的那一行。误报概率随 `d` 指数下降（`d` 越大越准）。

**取平均值**：平均会把「噪声大的行」和「噪声小的行」混在一起，结果既不是上界也不是无偏估计——它可能**低于**真实值（当某几行噪声为 0、另几行噪声为正时，平均仍在真实值之上；但若用更复杂的组合就可能低估）。更关键的是，平均值**无法保证「永不高估」**这个性质，而「永不高估」正是 Count-Min 在流量统计、频繁项挖掘中可用的根本原因（宁可高估也不能漏报）。

严格地说，取平均仍然是真实值的上界（因为每行都是上界，上界的平均还是上界），但它比最小值**松得多**，误差更大。所以正确做法是最小值。

</details>

**Q3.** 一个 5 表连接的查询，优化器估计结果只有 100 行，实际执行却有 1,000 万行，导致选了嵌套循环连接跑了 20 分钟。你会怎么排查和缓解？

<details><summary>参考答案</summary>

**排查步骤**：

1. 看执行计划里每个节点的 `estimated rows` 与 `actual rows`（Postgres 的 `EXPLAIN ANALYZE`、SQL Server 的实际执行计划），找出**第一个偏差最大**的节点——误差是从那里开始传播的。
2. 检查该节点涉及的列**是否有统计信息**、是否过期（`pg_statistic` 的 `last_analyze`）。
3. 检查谓词之间是否**强相关**（如「城市」与「省份」、「品牌」与「型号」），独立假设必然失效。
4. 检查是否用了**函数包裹列**（`WHERE date_trunc('day', ts) = ...`），这会让优化器只能用默认选择率（通常是 0.5% 之类的魔法数）。

**缓解手段**：

- 对该列**建多列统计**（Postgres 的 `CREATE STATISTICS ... (dependencies)`），或建**表达式索引**让谓词 sargable。
- 手动 `ANALYZE` 刷新统计。
- 用 **CTE + `MATERIALIZED`** 或临时表把中间结果物化，切断误差传播链，让优化器基于真实行数重新规划。
- 必要时用 hint / `pg_hint_plan` 强制连接算法与顺序。
- 长期方案：升级到支持**自适应执行（adaptive execution）**或 **learned optimizer** 的版本。

</details>

**Q4.** 为什么「统计信息过期」在 OLTP 系统里比在 OLAP 系统里更容易造成严重后果？

<details><summary>参考答案</summary>

**OLTP 的查询是高频、短小、对延迟极敏感的**：一条点查从 1 ms 劣化到 100 ms，乘以每秒上万次请求，就是整个服务的雪崩。而 OLTP 的数据变化**持续且零散**（每秒都在增删改），统计信息更容易偏离真实分布；同时 OLTP 系统为了不影响事务延迟，往往**降低 autovacuum/ANALYZE 的频率**，进一步加剧过期。

**OLAP 的查询是低频、长时、可容忍分钟级延迟的**：即使选错计划，代价是「这条报表跑了 5 分钟而不是 2 分钟」，影响面小；而且 OLAP 数据通常是批量导入的，导入后有明确的维护窗口可以重建统计。

此外 OLTP 的表往往**数据量不大但访问极热**，一旦计划从「索引查找」退化为「全表扫描」，缓存会被瞬间打穿，影响所有并发查询——这就是所谓的「计划翻转（plan flip）」事故。

</details>

**Q5.** 讲义说 Postgres 假设「内存处理元组比磁盘读快 400 倍」。如果一台机器的数据**全部缓存在内存里**（如内存数据库），这个常数会带来什么偏差？

<details><summary>参考答案</summary>

**偏差**：代价模型会**系统性高估 I/O 的代价、低估 CPU 的代价**。

具体后果：

1. **过度偏好「少读页」的计划**：模型认为「多读一页」极其昂贵，于是宁愿选「索引扫描 + 大量随机回表」（页数少但 CPU 分支多），也不选「顺序全表扫描」（页数多但每页处理便宜）。在全内存场景下，顺序扫描其实非常快，选择被扭曲。
2. **低估哈希连接/聚合的 CPU 成本**：模型把 CPU 看得太便宜，可能选择「哈希连接 + 大表 build」这类 CPU 密集但 I/O 友好的方案，在纯内存场景下反而不如排序归并。
3. **并行度判断失真**：并行主要省 CPU 时间，若 CPU 权重被压低，优化器会低估并行的收益。

缓解：内存数据库（如 SAP HANA、MemSQL）会**重新标定代价常数**，把 I/O 权重降到接近 0、把 CPU 与内存带宽权重提高；Postgres 也有 `effective_cache_size`、`random_page_cost`（SSD 上应从 4.0 降到 1.1 左右）等参数供人工校准。

</details>
