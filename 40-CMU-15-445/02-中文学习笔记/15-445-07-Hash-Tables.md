# 15-445 L07：哈希表（Hash Tables）

> 从本讲开始进入「访问方法（access methods）」层：DBMS 的执行引擎要读写页里的数据，就需要索引结构。两类基本结构是**无序的哈希表**与**有序的树**。哈希表在 DBMS 内部无处不在——页表、页目录、连接用的临时表、锁表，甚至某些 key-value 存储的整个数据模型。

3. 区分哈希表的两个组成部分（哈希函数 vs 哈希方案），并说明各自的权衡。

5. 描述线性探查（linear probe）的插入/查找/删除流程，说明墓碑（tombstone）为什么必需，并解释 load factor 与扩容策略。
6. 说明 Robin Hood Hashing 如何通过「劫富济贫」均衡探查距离。

## 3. 核心概念

### 3.1 Hash Table（哈希表）

实现**无序关联数组**（unordered associative array）的抽象数据类型，把键映射到值。平均 O(1) 查找、最坏 O(n)，空间 O(n)。关键限制：**不保留键的顺序**，无法按某种顺序遍历元素。

### 3.2 Hash Function（哈希函数）

把大键空间映射到小定义域的函数，输出确定性整数（通常 32 或 64 位）。DBMS 只关心两件事：**快**与**冲突率低**。不需要密码学哈希（如 SHA-256），因为键的内容不需要保密。

### 3.3 Hashing Scheme（哈希方案）

哈希之后如何处理冲突。权衡是「分配更大的表以减少冲突」vs「冲突发生时执行额外指令」。

### 3.4 Linear Probe Hashing（线性探查哈希）

最基础也通常最快的方案：单个巨大的定长槽数组，冲突时线性向后找下一个空槽，到末尾则回绕到开头。必须在槽里存键，否则无法判断「扫描该停在哪」。

### 3.5 Tombstone（墓碑）

线性探查中删除条目的标记：不能直接清空槽（会让后续查找提前停止而找不到原本被挤到后面的键），于是把槽标记为「逻辑删除」，查找时继续扫描，插入时可复用。

### 3.6 Robin Hood Hashing（罗宾汉哈希）

线性探查的变体，目标是**均衡探查距离**。插入时记录自己已探查的距离；若在某槽发现「原住民的探查距离比我短」，就把它赶走、由自己占位，让原住民继续向后探查——劫富济贫。

### 3.7 Cuckoo Hashing（布谷鸟哈希）

用**多个哈希函数**为每个键计算多个候选位置。插入时若有空位就放入；若全满则随机驱逐一个已有条目，把被驱逐者重新哈希到它的另一个候选位置。查找与删除只需检查固定的几个位置，因此是 O(1)。

### 3.8 Chained Hashing（链地址法）

最常见的**动态**哈希方案：每个槽维护一个桶（bucket）的链表，哈希到同一槽的键都插进该链表。查找时先哈希到桶，再扫链表。

### 3.9 Extendible Hashing（可扩展哈希）

链地址法的改进：桶满时**分裂桶**而不是让链表无限增长。维护一个全局目录（global table），多个目录槽可以指向同一个桶；分裂时只搬动被分裂桶中的数据，其他桶不受影响。

### 3.10 Global Bit Count / Local Bit Count（全局位计数 / 局部位计数）

可扩展哈希的两个元数据。**全局位计数**是确定「哈希属于哪个桶」需要检查的最大有效位数；**局部位计数**是判断「哈希是否属于本桶」需要检查的位数。局部位计数 ≤ 全局位计数，差值正体现在「多个目录槽指向同一桶」。

### 3.11 Linear Hashing（线性哈希）

用**分裂指针（split pointer）**记录下一个要分裂的桶。任何一个桶溢出，都分裂指针所指的桶（不一定是溢出的那个）。表因此**增量增长**，避免一次性重建。

### 3.12 Split Pointer（分裂指针）

线性哈希中指向「下一个待分裂桶」的指针。分裂后指针前进一格；到达末尾后丢弃旧哈希函数、指针回到开头，进入下一轮。

### 3.13 Load Factor（装载因子）

活跃键数 / 槽数。线性探查用它判断表是否过满（经验上槽数取期望元素数的两倍）；超过阈值就分配两倍大的新表并 rehash 全部条目。

## 4. 通俗理解

哈希表像**没有编号规则的储物柜**。

- **线性探查 = 挨个试柜子**：你的柜号被占了，就试下一个，再下一个。取东西时如果试到一个空柜子，说明你的东西肯定不在后面（因为插入时也是这么找的），可以放弃。但如果有人退租时**把柜子清空**，中间就出现了一个「假空位」，后面的人取东西会误以为到此为止——所以退租只能贴个「已退租」的标签（墓碑），不能真清空。
- **罗宾汉 = 谁住得近谁让位**：你从 0 号柜一路试到 5 号，而 5 号柜的主人本来只该在 4 号柜（只被挤了 1 格）。你被挤了 5 格，比他惨，于是让他搬走继续找，你占了 5 号。结果是所有人的「被挤格数」趋于平均，最长的那条查找路径变短。
- **布谷鸟 = 有两个备用柜**：每个人有 2 个（或更多）候选柜。都满了就把某个人拎出来，让他去自己的另一个候选柜；若那里也满，继续拎人。偶尔会陷入「A 抢 B、B 抢 C、C 抢 A」的死循环，此时只能换柜号规则（改哈希种子）或换更大的柜区。
- **可扩展哈希 = 目录 + 房间**：目录是一张「前 3 位比特 → 房间号」的表，多个目录项可以指向同一个房间。某个房间满了，就隔出一间新房，只把该房间的人按**下一位比特**分到两间，目录里对应的两项改成指向两间房。其他房间一个人都不用动。
- **线性哈希 = 排队搬家**：不等到某间房爆掉才搬它，而是维持一个「下一个要搬的房间」指针。任何房间爆了，都按指针顺序搬下一间。这样搬家成本被摊平，不会某次插入突然卡住。

具体数字：一个有 1000 万条记录的哈希表，若用线性探查且装载因子 0.5，平均成功查找约 1.5 次探查、失败查找约 2.5 次；若装载因子升到 0.9，成功查找升到约 5.5 次、失败查找约 50 次——这就是「数据库在意常数因子」的量化含义。

## 5. 原理与推导

### 5.1 为什么 DBMS 要自己实现哈希表

标准库的 `std::unordered_map` 不能满足 DBMS 的需求：

- 它按**节点**分配（每个元素一次 malloc），缓存局部性差，而 DBMS 需要把数据放进**页**里、按页管理。
- 它不暴露**内存布局**，DBMS 无法控制溢出到磁盘、无法与缓冲池协作。
- 它没有为 DBMS 的访问模式（大表扫描式构建、然后只做点查）做优化。
- 它不提供细粒度的**并发控制**钩子。

所以讲义说「We must build our own」（下一讲预告里也强调「Data Structures: Hash Tables! → We must build our own…」）。

**四类用途**：

| 用途 | 说明 | 例子 |
|---|---|---|
| Internal Meta-Data | 数据库与系统状态的元信息 | 页表（page table）、页目录（page directory） |
| Core Data Storage | 存实际元组的数据结构 | key-value 存储把整库放在哈希表里 |
| Temporary Data Structures | 查询执行时临时构建 | 哈希连接（hash join）的构建侧、去重、分组 |
| Table Indices | 加速定位元组的附加结构 | `CREATE INDEX ... USING HASH` |

### 5.2 两个设计决策与「常数因子」

**决策一：数据组织（data organization）**。布局如何影响性能。讲义特别指出一个反直觉之处：**对内存读不友好的结构，在磁盘型 DBMS 里可能反而更好**，因为磁盘型系统里顺序访问才是关键。

**决策二：并发（concurrency）**。多个线程必须能同时访问而不破坏正确性。这一条在第 10 讲（索引并发控制）会展开成 latch 与 crabbing。

**为什么「常数因子」重要**：哈希表平均 O(1)、最坏 O(n)，但真实系统里 O(1) 的常数可能是 1 次缓存命中，也可能是 20 次缓存缺失。若每次查找多花 50 ns，一张表每秒 1000 万次查找就多花 0.5 秒——在 OLTP 里是灾难。因此讲义强调 "Databases care about constants!"。

### 5.3 静态哈希的三个不现实假设

```
Assumption #1: 元素数量事先已知且固定
Assumption #2: 每个键唯一
Assumption #3: 完美哈希函数保证无冲突（key1 ≠ key2 ⇒ hash(key1) ≠ hash(key2)）
```

三条在现实中全不成立：表会增长；同一个键可以对应多个值（非唯一索引、连接的多对多）；完美哈希的构造代价太高（需要知道全部键集合，且计算慢）。于是必须同时选好**哈希函数**与**哈希方案**。

若表满了，静态方案只能**重建**一个更大的表（通常是原大小的 2 倍），代价极高——这正是动态方案的动机。

### 5.4 哈希函数的选型

讲义列出的演进（`07-hashtables.pdf` 第 16–17 页）：

| 函数 | 年份 | 特点 |
|---|---|---|
| CRC-64 | 1975 | 源自网络错误检测 |
| MurmurHash | 2008 | 快速通用 |
| Google CityHash | 2011 | 对短键（<64 字节）更快 |
| Facebook XXHash | 2012 | 出自 zstd 压缩的作者 |
| Google FarmHash | 2014 | CityHash 的新版，冲突率更好 |
| RapidHash | 2019 | 快，且不依赖特定架构指令 |

选型原则：**快 + 低冲突率**。不需要抗碰撞攻击能力（键的内容不对外泄漏），因此不用 SHA-2 之类的密码学哈希——它们慢几个数量级。

> 待核实：notes 第 2 页称「当前最先进的哈希函数是 Facebook XXHash3」，而 slides 第 17 页把 "State-of-the-art" 箭头标在列表末尾（对应 RapidHash）。两处表述不一致，需人工核对讲义原文的箭头指向。

### 5.5 线性探查：为什么删除必须用墓碑

**插入**：从 `hash(key) % N` 开始，线性向后找第一个空槽（到末尾回绕）。**查找**：从同一位置开始线性扫描，若遇到**空槽**或已遍历全部槽则键不存在；因此槽里必须存键以便比较。

**删除的两种方案**：

- **方案一：移动（movement）**。删除后把后续条目重新哈希回填，直到遇到第一个空槽。问题：可能波及**整张表**，代价 O(n)。slides 第 35 页明确写 "No DBMS does this"。
- **方案二：墓碑（tombstone）**。用一个独立的位图标记「该槽逻辑上已删除」。查找时把墓碑当作「继续扫描」的信号（而不是终止信号）；插入时**可以**复用墓碑槽。

墓碑的代价是会累积，导致查找路径变长，因此需要**周期性垃圾回收（GC）**——通常在重建表时顺带完成。

**扩容**：装载因子 = 活跃键数 / 槽数。超过阈值时分配两倍大的表并 rehash 全部条目。为减少无谓比较，槽数通常取期望元素数的**两倍**。

**为什么线性探查快**：连续内存访问，缓存友好，且不需要存指针（相比链地址法省内存）。缺点是装载因子高时出现**主聚集（primary clustering）**——连续的占用段越来越长，插入与查找都退化成线性扫描。

### 5.6 Robin Hood Hashing 的均衡原理

设键 k 从 `h(k)` 起被挤了 d 个槽，称 d 为它的**探查距离**。标准线性探查里，先来的键占好位置，后来的键承受长距离，分布严重不均。

Robin Hood 的规则：插入时维护自己的探查距离 d_self；在槽 i 遇到原住民，其距离为 d_other。若 `d_self > d_other`，就**交换**——原住民拿走当前槽（? 不，是你占这个槽），原住民带着它的键继续向后探查。

效果：**所有键的探查距离方差变小**，最坏查找长度显著下降；查找与删除逻辑与线性探查完全相同（因为交换时不改变「同一键的所有候选位置都在其哈希位置之后」这一不变量）。这也解释了为什么讲义说查找/删除「与线性探查相同」。

### 5.7 Cuckoo Hashing 的 O(1) 保证与成环

**结构**：多个哈希表（实践中常是**一张表 + 多个哈希函数**），哈希函数用**同一算法不同种子**产生不同结果。

**插入**：

1. 检查该键的所有候选位置，有空位就放入（多个空位时可比较装载因子，或更常见地随机选一个）。
2. 全满则随机选一个位置，驱逐原条目。
3. 把被驱逐的条目重新哈希到**它的另一个**候选位置，重复步骤 1–2。

**为什么查找是 O(1)**：一个键只可能在固定的 k 个位置（k = 哈希函数个数，典型 2），逐个检查即可，与表内元素数量无关。

**成环**：驱逐链可能回到起点形成环（A 抢 B 的位置、B 抢 C 的、C 又抢 A 的）。处理方式：

- 用**新的哈希种子**重建全部表（较少用）；
- 重建为**更大的表**（较常用）。

**插入代价**：可能触发长驱逐链，因此插入比查找贵。讲义还给出一个「教授注」：实践中多哈希函数映射到**同一张表**的不同槽；且由于哈希本身不总是严格 O(1)（要看键长），查找与删除的实际代价可能高于 O(1)。

### 5.8 链地址法与「桶过滤器」优化

**结构**：`hash(key) % N` 定位到槽，槽里是一个桶链表的头指针。冲突的键都挂在同一链表上。

**优点**：删除简单（直接从链表摘除，不需要墓碑）；桶数固定时不会因为装载因子升高而退化到「全表扫描」，只是链表变长。
**缺点**：指针追逐导致缓存不友好；每个条目额外存指针。

**优化（讲义重点）**：每个**桶指针可以附带一个过滤器**（如布隆过滤器），用于快速判断「这个键**可能**在不在此桶」。过滤器允许假阳性（false positive）但**绝不允许假阴性**（false negative）——即「说不存在就一定不存在」。这样大多数不存在的键可以在扫链表**之前**被挡掉。

这与第 5 讲的 SSTable key filter 是同一思想：**用极小空间换取「不必访问慢结构」的概率**。

### 5.9 可扩展哈希的完整推导

**结构**：

```
全局目录（global table）：2^G 个槽，G = global bit count
每个槽 → 指向某个桶
每个桶维护 local bit count L（L ≤ G）
```

因为 L ≤ G，**多个目录槽可以指向同一个桶**——这正是「增量分裂」的空间来源。

**查找**：取哈希值的前（或后）G 位作为目录下标，进入对应桶，再在桶内比较键。

**分裂（bucket full）**：

1. 该桶的局部位计数 L 加 1。
2. 按第 L 位把桶内条目分成两组，形成两个新桶。
3. 更新目录中指向该桶的所有槽，让它们按第 L 位分别指向两个新桶。

**关键性质**：只有**被分裂的桶**中的数据被移动，其他桶完全不受影响。这就是「数据移动是局部的（localized to just the split chain）」。

**目录翻倍（L > G）**：若某桶的 L 已经等于 G（没有更多位可用），就必须先把 **G 加 1**、目录规模翻倍（每个旧槽复制成两个指向同一桶的槽），然后才能分裂该桶。

**讲义示例推导**（slides 第 97–119 页）：

```
初始：G = 2，目录 4 项（00, 01, 10, 11），3 个桶（两个槽共享一个桶）
Put A, hash(A) = 01110…  → 前缀 01 → 桶 X
Put B, hash(B) = 10111…  → 前缀 10 → 桶 Y
Put C, hash(C) = 10100…  → 前缀 10 → 桶 Y 已满 → Overflow!
```

分裂桶 Y：L 从 2 增到 3，按第 3 位分离：

```
hash(B) = 101|11…  → 第 3 位 = 1
hash(C) = 101|00…  → 第 3 位 = 0
```

由于 L（3）> G（2），必须先翻倍目录：G 变为 3，目录变成 8 项（000, 001, 010, 011, 100, 101, 110, 111）。分裂后 `100` 与 `101` 分别指向两个新桶，其余 6 项仍指向原来的 3 个桶（此时 8 个槽对应 4 个桶）。

**代价**：目录翻倍是 O(2^G)，但只在必要时发生，且翻倍是**几何增长**，摊还后每次插入仍是常数代价。桶分裂只搬一个桶的数据。

### 5.10 线性哈希：为什么「分裂的不是溢出的桶」还能正确

**两个哈希函数**：

```
hash1(key) = key % n        （n = 初始桶数）
hash2(key) = key % 2n       （表翻倍后的桶数）
```

**插入与分裂协议**：

1. 用适当哈希定位桶并插入。
2. 若**任何**桶溢出：在末尾**新增一个槽**（编号 n, n+1, …），启用 hash2。
3. **分裂 split pointer 所指的桶**（不一定是刚溢出的那个），用 hash2 把它的键重新分配到「原桶」与「新桶」。
4. split pointer 前进一格。

**为什么这样正确**：关键在于「表的前半部分用 hash1、后半部分用 hash2」这一阶段性事实。当指针位于位置 p 时：

- 编号 < p 的桶已经分裂过，其中的键按 hash2 分布；
- 编号 ≥ p 的桶还没分裂，其中的键仍按 hash1 分布。

**查找规则**：先用 hash1 计算位置。若该位置 **≥ split pointer**（还没分裂），就是它；若 **< split pointer**（已分裂），说明该键可能已被搬到新桶，必须再用 hash2 算一次。

**讲义示例推导**（slides 第 121–139 页）：

```
初始 n = 4，hash1(key) = key % 4，split pointer 指向 bucket 0
Put 17 → hash1(17) = 17 % 4 = 1 → 桶 1 溢出
  → 新增槽 4，启用 hash2(key) = key % 8
  → 分裂指针所指的桶 0：用 hash2 重哈希其中的 8 和 12
      hash2(8) = 8 % 8 = 0  → 留在桶 0
      （12 → 12 % 8 = 4 → 搬到新桶 4）
  → 指针前进到桶 1
Get 20 → hash1(20) = 20 % 4 = 0 → 0 < split pointer（桶 0 已分裂）
       → 改用 hash2(20) = 20 % 8 = 4 → 实际在桶 4  ✓
```

**收尾**：指针走到原表最后一个槽后，所有桶都已改用 hash2，此时**丢弃 hash1**，指针回到开头，进入下一轮（n 变为 2n）。

**删除与收缩**：若删除导致 split pointer **之前**的某个桶变空，可以移除该桶并把指针**反向**移动一格——表因此能增量收缩。

**溢出判据**：讲义说「留给实现决定」，可用**空间利用率**或**平均溢出链长度**。这与可扩展哈希「桶满即分裂该桶」形成对比：线性哈希把分裂时机与位置**解耦**。

### 5.11 三种动态方案的对比

| 维度 | 链地址法 | 可扩展哈希 | 线性哈希 |
|---|---|---|---|
| 增长方式 | 链表变长（不增长表） | 桶分裂，必要时目录翻倍 | 增量分裂，指针顺序推进 |
| 分裂对象 | 无分裂 | 溢出的那个桶 | 指针所指的桶（未必溢出） |
| 数据移动量 | 无 | 仅被分裂桶 | 仅指针所指桶 |
| 查找代价 | 桶内扫链表 | 目录 + 桶内查找 | 可能需要两次哈希 |
| 空间开销 | 指针 | 目录（可能 2^G） | 极小（仅指针） |
| 主要缺点 | 链过长时退化 | 目录翻倍瞬间开销大 | 短期存在溢出链 |

### 6.2 补充示例（非官方，仅用于说明概念）

**线性探查的查找伪代码**（非官方）：

```
def get(key):
    i = hash(key) % N
    scanned = 0
    while scanned < N:
        slot = table[i]
        if slot.state == EMPTY:
            return None                 # 真空槽 → 终止
        if slot.state == OCCUPIED and slot.key == key:
            return slot.value
        # TOMBSTONE 或键不匹配 → 继续
        i = (i + 1) % N
        scanned += 1
    return None
```

注意墓碑在这里的处理：它**不终止**扫描，但也不返回值。若把墓碑当空槽，被挤到其后的键就会查不到。

**Robin Hood 的交换逻辑**（非官方）：

```
def put(key, value):
    i = hash(key) % N
    dist = 0                            # 我已探查的距离
    while True:
        if table[i] is EMPTY or table[i] is TOMBSTONE:
            table[i] = (key, value, dist); return
        if table[i].key == key:
            table[i].value = value; return
        if table[i].dist < dist:        # 原住民比我幸运 → 劫富济贫
            swap((key, value, dist), table[i])
        i = (i + 1) % N
        dist += 1
```

交换后继续用**被换出的那个键**（此时在 `(key, value, dist)` 里）向后探查，`dist` 也随之递增。

**可扩展哈希的分裂伪代码**（非官方）：

```
def split(bucket):
    bucket.local_bits += 1
    if bucket.local_bits > global_bits:
        global_bits += 1
        directory = [d for d in directory for _ in (0, 1)]   # 每槽复制一份
    # 按新的局部位把条目分到两个桶
    new_bucket = Bucket(local_bits=bucket.local_bits)
    for entry in bucket.entries:
        if bit(entry.hash, bucket.local_bits - 1) == 1:
            new_bucket.entries.append(entry)
        # 否则留在原桶
    # 更新目录中所有指向旧桶的槽
    for idx, target in enumerate(directory):
        if target is bucket and bit(idx, bucket.local_bits - 1) == 1:
            directory[idx] = new_bucket
```

**代价对比估算**（非官方，仅说明概念）：

```
重建整表（静态方案的扩容）:  O(n) 一次性，n = 1000 万 → 可能数百毫秒
可扩展哈希的单次分裂:        O(桶大小 + 目录翻倍)，目录翻倍仅在 L > G 时发生
线性哈希的单次分裂:          O(桶大小)，且与插入解耦
→ 动态方案把「最坏一次的停顿」换成「多次小停顿」
```

## 7. 容易混淆的概念

| 概念对 | 区别 | 记忆要点 |
|---|---|---|
| Hash Function vs Hashing Scheme | 前者决定「键落到哪个槽」；后者决定「撞了怎么办」 | 一个管映射，一个管冲突 |
| 静态 vs 动态哈希 | 静态表大小固定，满了必须整体重建；动态可增量调整 | 一个重建，一个增量 |
| 线性探查 vs 链地址法 | 前者开放寻址（数据都在数组里）；后者用链表挂桶外 | 一个数组内找空位，一个挂链 |
| 墓碑 vs 空槽 | 墓碑「继续扫描但不返回」；空槽「终止查找」 | 一个不停，一个停 |
| Robin Hood vs 标准线性探查 | 前者交换以均衡探查距离；查找/删除逻辑相同 | 一个劫富济贫，一个先到先得 |
| Cuckoo vs 链地址法 | Cuckoo 每键固定 k 个位置、无链表；链地址法位置唯一但链可无限长 | 一个多位置，一个长链 |
| 可扩展哈希 vs 线性哈希 | 前者「桶满就分裂该桶」；后者「任何桶满都分裂指针所指桶」 | 一个分裂当事人，一个分裂排队者 |
| Global vs Local Bit Count | 全局决定目录规模；局部决定桶的归属判定 | 全局管目录，局部管桶 |
| 哈希表 vs B+ 树索引 | 哈希只支持等值查询（无序）；B+ 树支持范围与排序 | 一个无序，一个有序 |

## 11. 自我检查

**Q1.** 线性探查哈希中，为什么删除不能直接把槽清空？两种删除方案各是什么，为什么讲义说其中一种「没有 DBMS 会用」？

<details><summary>参考答案</summary>

**不能直接清空的原因**：线性探查的查找靠「遇到空槽就停止」来判断键不存在。若删除时把槽清空，那些因为冲突被挤到该槽**之后**的键，在查找时会在空槽处提前终止，从而**查不到实际存在的键**。空槽成了「假的终止信号」。

**两种方案**：

1. **移动（movement）**：删除后把后续条目重新哈希回填，直到遇到第一个空槽，把这个「洞」填上。问题是一次删除可能波及**整张表**（最坏 O(n) 次重新哈希），代价极高，slides 第 35 页直接写 "No DBMS does this"。
2. **墓碑（tombstone）**：用一个独立的位图标记该槽逻辑上已删除。查找时墓碑**不终止**扫描（继续往后找），插入时**可以复用**墓碑槽。代价是墓碑会累积、拉长查找路径，因此需要周期性垃圾回收——通常在重建表时顺带清理。

哈希表的典型用途是查询执行中的临时结构（哈希连接构建侧、分组去重），生命周期短、删除少，因此墓碑的开销可以接受；而移动方案在任何负载下都可能触发全表重排，所以现实中不用。

</details>

**Q2.** 可扩展哈希中，全局位计数与局部位计数分别控制什么？当某桶满了且 `local == global` 时，需要做什么？

<details><summary>参考答案</summary>

**全局位计数（global bit count）G**：确定「哈希属于哪个目录槽」需要检查的最大有效位数，因此目录规模为 2^G 项。

**局部位计数（local bit count）L**：判断「哈希是否属于本桶」需要检查的位数。因为 L ≤ G，**多个目录槽可以指向同一个桶**（2^(G−L) 个槽共享一个桶），这是增量分裂的空间来源。

**当桶满且 L == G 时**：

1. 没有更多位可用来区分桶内条目，无法直接分裂。
2. 先把 **G 加 1**，目录规模**翻倍**（每个旧槽复制成两个指向同一桶的槽）。
3. 此时 L（= 旧的 G）< 新的 G，于是按第 L+1 位把桶一分为二，并更新目录中指向旧桶的槽，让它们分别指向两个新桶。

翻倍是 O(2^G) 的开销，但因为表按几何级数增长，摊还到每次插入仍是常数；且分裂只搬动被分裂桶里的数据，其他桶完全不受影响。

</details>

**Q3.** 线性哈希中，`Put 17` 使桶 1 溢出，但实际被分裂的是指针所指的桶 0。为什么这样仍然是正确的？查找 20 时如何决定用 hash1 还是 hash2？

<details><summary>参考答案</summary>

**为什么正确**：线性哈希维持的核心不变量是「**指针之前（< split pointer）的桶已按 hash2 分布，指针及其之后的桶仍按 hash1 分布**」。

- 溢出只说明「该桶需要更多空间」，但表增长必须**按顺序**进行——只有指针所指的桶分裂后，指针才能前进，前半/后半的分界线才一致。若允许任意桶分裂，就会出现「中间某桶用了 hash2、而它前面的桶还用 hash1」的混乱状态。
- 溢出桶 1 的溢出条目可以临时挂在**溢出链（overflow chain）**上，等指针推进到桶 1 时再正式分裂解决。讲义说「按 split pointer 分裂，最终会覆盖所有溢出的桶」，就是这个意思。
- 分裂桶 0 时新增了一个槽（编号 n），并用 hash2 把桶 0 中的键重新分配：留在桶 0 或搬进新桶。数据移动只涉及一个桶。

**查找 20 的规则**：

1. 先用 `hash1(20) = 20 % 4 = 0`。
2. 因为 0 **小于** split pointer（桶 0 已分裂），说明该键可能已被搬到新桶，必须再用 `hash2(20) = 20 % 8 = 4` 定位 → 实际在桶 4。
3. 反之，若 `hash1` 的结果 **≥ split pointer**（该桶尚未分裂），直接用这个位置即可。

**删除与收缩**：若删除使指针**之前**的某个桶变空，可移除该桶并把指针**反向**移动一格，表因此能增量收缩。

</details>

**Q4.** 为什么 DBMS 不使用 `std::unordered_map`，而要自己实现哈希表？请从内存布局、与缓冲池的协作、访问模式、并发四个角度说明。

<details><summary>参考答案</summary>

1. **内存布局**：标准库容器按节点逐个分配（每个元素一次堆分配），缓存局部性差，且无法把数据布局到 DBMS 的**页**里。DBMS 需要控制布局（开放寻址的连续数组、桶页、溢出页），以便顺序访问与 SIMD 式批量比较。
2. **与缓冲池协作**：DBMS 的哈希表可能大到溢出到磁盘（哈希连接的两侧、分组聚合），必须通过**缓冲池**按页读写、受替换策略与 pin 管理。标准库容器对「数据可能在磁盘上」一无所知，也不暴露页级接口。
3. **访问模式**：DBMS 的典型模式是「先批量构建、再大量点查」，且构建期可以预留精确容量、避免 rehash；查询执行还要求能在构建完成后**只读共享**（无需加锁）。标准库容器没有为这种两阶段模式优化，也不保证构建后不再改动内部结构。
4. **并发控制**：DBMS 需要把 latch 粒度做到桶级甚至槽级（第 10 讲），并与其他结构（页、索引）统一加锁顺序。标准库不提供内部结构的并发钩子，只能整体加锁，成为瓶颈。

此外，DBMS 还需要**可预测的最坏情况**（避免单次 rehash 造成长停顿）与**内存核算**（把哈希表内存计入查询的内存上限、必要时溢写磁盘），这些都是通用容器不提供的。

</details>

**Q5.** 比较链地址法、可扩展哈希、线性哈希在「增长方式」与「数据移动量」上的差别。为什么讲义最后说「哈希表通常不是你想要的表索引」？

<details><summary>参考答案</summary>

| 维度 | 链地址法 | 可扩展哈希 | 线性哈希 |
|---|---|---|---|
| 增长方式 | 不增长表，链表变长 | 桶满 → 分裂该桶；local > global 时目录翻倍 | 任何桶满 → 分裂指针所指桶，指针顺序推进 |
| 数据移动量 | 无 | 仅被分裂的桶 | 仅指针所指的桶 |
| 查找代价 | 桶内扫链表（可能很长） | 目录定位 + 桶内查找 | 可能需两次哈希 |

三者都把「一次性重建整表」换成局部操作：链地址法完全不动已有数据；可扩展哈希把移动限制在被分裂桶；线性哈希把分裂时机与位置解耦，使增长平稳可预测。

**为什么哈希表不适合做表索引**：

1. **不支持范围查询**。哈希打散了顺序，`WHERE age BETWEEN 20 AND 30`、`ORDER BY`、`LIKE 'And%'` 都无法用哈希索引加速，只能全表扫描。而 B+ 树因为键有序，范围查询是一次叶子链扫描。
2. **不支持排序输出与前缀匹配**，也无法为 `ORDER BY` 省掉排序算子。
3. **动态哈希的空间开销**：可扩展哈希的目录可能远大于数据量（2^G），链地址法要存指针。
4. **并发与分裂代价**：桶分裂/目录翻倍需要协调并发访问（第 10 讲的 latch 问题），实现复杂度高。

因此讲义给出三种语法并强调默认是 B+ 树：

```sql
CREATE INDEX ON xxx USING BTREE (val);   -- 显式 B+ 树
CREATE INDEX ON xxx (val);               -- 默认即 B+ 树
CREATE INDEX ON xxx USING HASH (val);    -- 哈希索引，仅等值查询
```

哈希索引的正当用途是**只做等值查找**的场景（如内存数据库的索引、key-value 存储）。不过哈希表在 DBMS **内部**仍然无处不在：页表、页目录、锁表、哈希连接的构建侧、去重与分组。

</details>
