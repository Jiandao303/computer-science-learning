# 15-445 L21：多版本并发控制（Multi-Version Concurrency Control）

> **重要说明**：截至 2026-11-10，Fall 2026 官网**尚未发布**本讲的 slides 与 notes（课表日期 Nov 16）。因此本篇第 5 节及之后的技术内容**以下为通用知识整理，非依据 2026 官方讲义**，仅按数据库教材的标准知识框架组织，供预习与对照使用。官方材料发布后须逐条核对并重写。
>
> 本讲在课程中的定位：前两讲的 2PL 与 T/O 都建立在**单版本**存储之上——一个对象只有一个当前值，所以读必须阻塞写（2PL）或中止（T/O）。**MVCC** 换了个思路：保留对象的**多个历史版本**，让读事务去看「它开始时的那个快照」，于是**读不阻塞写、写不阻塞读**。这是今天几乎所有主流 DBMS（PostgreSQL、MySQL InnoDB、Oracle、SQL Server）的实际方案。代价是存储膨胀、版本链维护、以及**快照隔离并不等于可串行化**（写偏斜）。

## 1. 本节学习目标

学完本讲，你应该能够：

1. 解释 MVCC 的核心思想：**写不覆盖旧值，而是追加新版本**；读按**快照（snapshot）**选择可见版本。
2. 说明 MVCC 如何实现**读写互不阻塞**，以及它为什么仍需要**写-写冲突处理**（通常靠锁或 first-updater-wins）。
3. 描述**版本链（version chain）** 的两种组织方式：**追加到表尾（append-only）** 与 **时间戳排序（time-travel / delta）**，并说明各自的优缺点。
4. 定义**快照隔离（Snapshot Isolation, SI）**，说明它如何避免脏读、不可重复读、幻读，但**不能避免写偏斜（write skew）**。
5. 用「两个医生同时值班」的例子解释**写偏斜**，并说明它为什么是 **R-W 冲突环**的产物。
6. 区分 **SI 与可串行化快照隔离（Serializable Snapshot Isolation, SSI）**，说明 SSI 如何用**读写依赖跟踪**检测危险结构。
7. 说明 MVCC 的**垃圾回收（GC / vacuum）** 问题：旧版本何时可以删除，长事务如何阻止回收。
8. 说明 MVCC 下**索引**的处理方式（指向版本链头 / 索引项也版本化）以及带来的额外复杂度。

## 3. 核心概念

> 以下概念定义为通用教材口径，待 2026 官方 slides 发布后核对术语与侧重。

### 3.1 Multi-Version Concurrency Control（多版本并发控制，MVCC）

DBMS 为每个逻辑对象维护**多个物理版本**，每个版本带时间戳区间；读事务按自己的**快照**选择可见版本，写事务**追加**新版本而非覆盖旧版本。

### 3.2 Snapshot（快照）

事务开始时（或每条语句开始时）确定的**可见版本集合**，通常用一个时间戳 `read_ts` 表示：「所有 `commit_ts <= read_ts` 的版本对我可见」。

### 3.3 Version Chain（版本链）

同一逻辑对象的所有版本串成的链表（或索引），通常**新版本在前**（head 是最新）。每个版本含 `begin_ts`（创建它的事务）与 `end_ts`（删除/覆盖它的事务）。

### 3.4 Snapshot Isolation（快照隔离，SI）

一个隔离级别：事务读**开始时的快照**；提交时检查**写-写冲突**（若它要写的对象已被并发事务改过，则中止）。SI 保证不出现脏读、不可重复读、幻读，但**允许写偏斜**。

### 3.5 Write Skew（写偏斜）

两个事务读**重叠**的数据集、各自写**不相交**的部分，两者都基于「对方不会改我要写的部分」的假设，结果合起来违反了不变量。SI 下**允许**发生，因为 SI 只检查写-写冲突。

### 3.6 First-Updater-Wins / First-Committer-Wins（先更新者胜 / 先提交者胜）

MVCC 处理写-写冲突的两种策略：前者在**写时**检查（若对象已被并发事务修改则等待或中止）；后者在**提交时**检查（若写集与并发提交事务的写集相交则中止）。

### 3.7 Serializable Snapshot Isolation（可串行化快照隔离，SSI）

在 SI 基础上增加**读写依赖（rw-dependency）跟踪**，检测「危险结构」（两个连续 rw 冲突），发现则中止其中一个事务。PostgreSQL 9.1+ 的 `SERIALIZABLE` 就是 SSI。

### 3.8 Vacuum / Garbage Collection（清理 / 垃圾回收）

删除不再被任何活跃事务需要的旧版本。若存在**长事务**（快照很老），它之后的版本都不能删——这是 MVCC 存储膨胀的主因。

### 3.9 Watermark（水位线）

所有活跃事务中**最小**的 `read_ts`。小于水位线的版本不再被任何事务需要，可以安全回收。

## 4. 通俗理解

**单版本 = 一块白板**：一个人写的时候别人不能看，看完才能擦掉重写。这就是 2PL 的困境——**读和写抢同一块白板**。

**MVCC = 一叠透明胶片**：每次修改都**加一张新胶片**在最上面，旧胶片不擦。每个读者拿到的是一份「截止到某个时刻的胶片集合」，他看到的永远是那一刻的样子。写者往上加新胶片，不影响任何已经在看的读者。

**快照隔离 = 「我进门时看到的账本就是我的账本」**：你进会议室时拍了张照，之后别人怎么改白板都跟你无关，你始终看你的照片。好处是**绝对不会看到别人改到一半的状态**；坏处是**你的照片可能已经过期**。

**写偏斜 = 「两个医生都请假」**：医院规定「值班医生至少 2 人」。Alice 和 Bob 都在值班，两人同时觉得不舒服。Alice 查了一下：「现在有 2 人值班，我走还剩 1 人……不对，剩 1 人违反规定，但我看的是当前状态，Bob 还在，那我走的话……」。实际发生的是：Alice 看到「Bob 在值班」，于是放心请假；Bob 看到「Alice 在值班」，也放心请假。两人各自的操作**单独看都合规**（走之前还有 2 人），合起来变成 **0 人值班**。

这个例子的关键：**两人读的是同一份数据（值班表），写的是不同的行（各自的请假状态）**——没有写-写冲突，所以 SI 放行了。

## 5. 原理与推导

> **以下为通用知识整理，非依据 2026 官方讲义。**

### 5.1 从「读写互斥」到「多版本」

在单版本存储下，读与写必须互斥，因为「读」需要一个稳定的值。2PL 用锁实现互斥（读等写、写等读），T/O 用中止实现（冲突就重来）。两者都把**并发度**献祭给了**正确性**。

MVCC 的洞察：**读需要的不是「最新值」，而是「某个一致的值」**。如果保留历史版本，读可以拿一个旧版本，完全不需要等写者。于是：

- **读不阻塞写**：读者读旧版本。
- **写不阻塞读**：写者追加新版本。
- **写-写仍需协调**：两个写者改同一对象必须选一个（否则更新丢失）。

这就是 MVCC 的全部核心。它把「读写冲突」这个最频繁的冲突类型**彻底消除**，只留下相对少见的「写写冲突」。

### 5.2 版本的元数据

每个版本需要两个时间戳：

- **`begin_ts`**：创建该版本的事务的提交时间戳（或事务 ID）。
- **`end_ts`**：删除/覆盖该版本的事务的时间戳；若尚未被删除，为 `∞`（或特殊值）。

**可见性判定**（对一个 `read_ts` 的快照）：版本 V 对事务 T 可见，当且仅当

```
V.begin_ts <= T.read_ts  AND  V.end_ts > T.read_ts
```

直觉：**版本在我拍照之前就已存在，且在我拍照时还没被删掉**。

在 PostgreSQL 的实现里，这两个字段叫 `xmin`（创建事务）与 `xmax`（删除事务），判定还要结合事务状态（`committed` / `aborted` / `in progress`）。

### 5.3 版本链的两种组织

| 方式 | 结构 | 优点 | 缺点 |
|---|---|---|---|
| **Append-only（追加式）** | 新版本追加到表尾，旧版本留在原处；索引指向版本链头 | 写入快（顺序追加）、旧版本可直接读 | 需要额外索引（如 tuple id → 版本链）；表膨胀快 |
| **Time-travel / delta（时间戳排序）** | 新版本**覆盖**旧位置（head 最新），旧版本作为 **undo log** 存在别处 | 主表紧凑、当前值读取快 | 读旧版本要走 undo 链（多次 I/O）；写要维护 undo |

- **Append-only** 典型：PostgreSQL（堆表 + `ctid` 链）、SAP HANA 的部分模式。
- **Delta / undo** 典型：MySQL InnoDB（undo log + rollback segment）、Oracle（undo tablespace）。

**InnoDB 的读流程**：索引项指向最新版本，若最新版本对本事务不可见，沿 **undo log** 回溯到可见版本。回溯长度取决于版本链长度——长事务会让回溯变慢。

### 5.4 写-写冲突的两种处理

| 策略 | 时机 | 行为 | 代表 |
|---|---|---|---|
| **First-Updater-Wins** | 写时 | 若对象已被并发事务修改（`end_ts` 已设置），则**等待**或**中止** | InnoDB（行锁 + 版本检查） |
| **First-Committer-Wins** | 提交时 | 提交时检查写集是否与并发提交事务相交，相交则中止 | PostgreSQL（`READ COMMITTED` 下是「更新时重新检查」） |

两种策略都保证**同一对象同一时刻只有一个写者**，从而避免丢失更新。

### 5.5 快照隔离能防什么、不能防什么

| 异常 | SI 是否允许 | 原因 |
|---|---|---|
| 脏读（dirty read） | ❌ 不允许 | 只读已提交的版本 |
| 不可重复读（unrepeatable read） | ❌ 不允许 | 整个事务读同一快照 |
| 幻读（phantom read） | ❌ 不允许（对同一快照） | 快照固定，新插入的行不在快照里 |
| 丢失更新（lost update） | ❌ 不允许 | 写-写冲突检查会中止后提交者 |
| **写偏斜（write skew）** | ✅ **允许** | 写集不相交，无写-写冲突 |
| **只读事务异常（read-only anomaly）** | ✅ 允许 | 只读事务看到的是旧快照 |

**关键结论**：**SI 不是可串行化**。ANSI SQL 标准把 `REPEATABLE READ` 定义为「不允许不可重复读」，而各家的 SI 实现满足这个定义，但**比标准允许的更强**（还消除了幻读）——然而仍**弱于 `SERIALIZABLE`**。

### 5.6 写偏斜的形式化分析

**场景**：医院要求「值班医生 ≥ 2 人」。当前 Alice、Bob 都在值班。

```
T1 (Alice 请假):  读值班表 → 看到 2 人（Alice, Bob）→ 判断 "我走后还有 1 人? 不, 还有 Bob, 但只有 1 人了" 
                  实际逻辑: SELECT COUNT(*) WHERE on_call = true → 2 > 1，可以请假
                  写: UPDATE doctor SET on_call = false WHERE name = 'Alice'
T2 (Bob 请假):    同上，看到 2 人 → 可以请假
                  写: UPDATE doctor SET on_call = false WHERE name = 'Bob'
```

**优先图**：

- T1 读「Bob 在值班」的行，T2 写「Bob 不在值班」→ R-W 冲突，`T1 →rw T2`。
- T2 读「Alice 在值班」的行，T1 写「Alice 不在值班」→ R-W 冲突，`T2 →rw T1`。

**环 `T1 → T2 → T1` 成立，不可串行化**。但**没有写-写冲突**（T1 写 Alice 行、T2 写 Bob 行，不相交），所以 SI 的写-写检查放行，两者都提交，最终 **0 人值班**。

**SI 的盲点**：它只检查「同一对象的写-写」，而写偏斜的冲突是**跨对象的读写环**——写集不相交，读集重叠。

### 5.7 SSI：在 SI 上补上可串行化

**SSI（Serializable Snapshot Isolation）** 的核心：跟踪事务间的**读写依赖（rw-antidependency，记作 `T1 →rw T2`，表示 T1 读了 T2 后来写的值）**。

**危险结构（dangerous structure）**：两个连续的 rw 冲突 `T1 →rw T2 →rw T3`，且 T3 先于 T1 提交。Cahill 等人证明：**SI 下任何不可串行化的执行都包含这样的结构**。

**SSI 的做法**：

1. 为每个事务记录它读过的对象与被读过的时间。
2. 提交时检查是否形成危险结构；若形成，中止其中一个事务。
3. 优化：**只读事务**与**只写事务**可以豁免大部分检查（只读事务不产生 `→rw` 出边，只写事务不产生入边）。

**代价**：额外的元数据（每个事务的读写集摘要）与误报（false positive）——SSI 可能中止一些实际可串行化的事务。

**实现**：PostgreSQL 9.1+ 的 `SERIALIZABLE` 就是 SSI（基于 Ports & Grittner 的论文），这是学术界成果落地工业界的经典案例。

### 5.8 垃圾回收与长事务

**问题**：旧版本在「没有事务需要它」之前不能删。判定标准是**水位线（watermark）** = 所有活跃事务中最小的 `read_ts`。小于水位线的版本可回收。

**长事务的灾难**：一个开了 3 小时的只读事务会让水位线停在 3 小时前，这 3 小时内产生的所有旧版本都无法回收——表膨胀、索引膨胀、查询变慢。

**对策**：

- **`idle_in_transaction_session_timeout`**（PostgreSQL）：强制杀掉长时间空闲的事务。
- **`old_snapshot_threshold`**（PostgreSQL 9.6+，后废弃）：允许删除超出阈值的旧版本，代价是长事务可能报错。
- **InnoDB 的 purge 线程**：后台清理 undo log，但同样被最老的活跃 read view 阻塞。
- **应用层约束**：避免长事务、避免在事务里做网络调用。

### 5.9 索引在 MVCC 下的复杂度

**问题**：索引项指向「逻辑对象」，但一个对象有多个版本。索引怎么处理？

三种方案：

1. **索引指向版本链头**（PostgreSQL）：索引项只指向最新版本（`ctid`），读旧版本时沿链回溯。**问题**：索引可能包含「对当前快照不可见」的项（如已删除的行），需要**回表检查可见性**（index-only scan 因此需要 visibility map）。
2. **索引项也版本化**（InnoDB）：二级索引项含主键，回表时通过 undo log 判断可见性。**问题**：索引膨胀。
3. **只索引当前版本**（部分内存数据库）：需要额外的旧版本索引结构。

**共同难点**：**索引扫描必须做可见性过滤**，所以「索引覆盖扫描」在 MVCC 下并不总是更快。

### 5.10 MVCC 与日志/恢复的关系

MVCC 与 WAL 是**正交**的两件事，但会互相影响：

- MVCC 的旧版本也需要写日志（否则崩溃后无法恢复历史版本）。
- **undo log**（InnoDB）与 **WAL 的 undo 记录**是两套东西：前者服务 MVCC 读，后者服务事务回滚。
- 检查点必须记录「哪些版本可以回收」，否则重启后无法判断。

### 6.2 Agent 自行编写的教学示例

> 以下代码**非官方，仅用于说明概念**。

版本与可见性判定（示意）：

```cpp
// 非官方示例：带时间戳区间的版本
struct Version {
  Value value;
  timestamp_t begin_ts;   // 创建此版本的事务提交时间戳
  timestamp_t end_ts;     // 删除/覆盖此版本的事务时间戳，未删除为 MAX
};

bool IsVisible(const Version &v, timestamp_t read_ts) {
  return v.begin_ts <= read_ts && read_ts < v.end_ts;
}
```

沿版本链找可见版本（示意）：

```cpp
// 非官方示例：新版本在前的链表，找对本快照可见的版本
const Version *FindVisible(const Version *head, timestamp_t read_ts) {
  for (const Version *v = head; v != nullptr; v = v->next) {
    if (IsVisible(*v, read_ts)) return v;   // 命中
  }
  return nullptr;                            // 该对象在快照中不存在
}
```

写偏斜的复现（SQL 示意）：

```sql
-- 非官方示例：两个会话在 REPEATABLE READ（SI）下同时执行
-- 会话 1
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT COUNT(*) FROM doctors WHERE on_call = true;   -- 返回 2
UPDATE doctors SET on_call = false WHERE name = 'Alice';
COMMIT;

-- 会话 2（与上面几乎同时）
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT COUNT(*) FROM doctors WHERE on_call = true;   -- 也返回 2（各自的快照）
UPDATE doctors SET on_call = false WHERE name = 'Bob';
COMMIT;
-- 结果：两人都请假成功，值班人数 0，违反约束
```

PostgreSQL 下的修法（示意）：

```sql
-- 非官方示例：改用 SERIALIZABLE（SSI），其中一个事务会收到
-- ERROR: could not serialize access due to read/write dependencies among transactions
BEGIN ISOLATION LEVEL SERIALIZABLE;
```

## 7. 容易混淆的概念

| 概念 A | 概念 B | 关键差别 |
|---|---|---|
| MVCC | 快照隔离 | MVCC 是**实现技术**（多版本存储）；SI 是**隔离级别**（可用 MVCC 实现，也可用其他方式） |
| 快照隔离 | 可串行化 | SI 允许写偏斜；可串行化不允许。SI ⊊ 可串行化 |
| 快照隔离 | SSI | SSI = SI + 危险结构检测，达到可串行化 |
| 写偏斜 | 丢失更新 | 前者写集**不相交**（无 W-W 冲突）；后者写**同一对象**（有 W-W 冲突） |
| `begin_ts` | `end_ts` | 前者是版本**诞生**时刻；后者是版本**失效**时刻；可见性要求 `begin_ts <= read_ts < end_ts` |
| Append-only | Delta/undo | 前者新版本追加、旧版本原地不动；后者新版本覆盖、旧版本进 undo log |
| Vacuum | Rollback | vacuum 删的是**不再需要的旧版本**（正常回收）；rollback 撤销的是**未提交事务的修改**（异常路径） |
| MVCC 的 `xmin`/`xmax` | WAL 的 LSN | 前者是**事务时间戳**（逻辑顺序）；后者是**日志位置**（物理顺序） |

## 11. 自我检查

**Q1.** 快照隔离已经消除了脏读、不可重复读、幻读，为什么 PostgreSQL 的 `REPEATABLE READ` 仍不等于 `SERIALIZABLE`？

<details><summary>参考答案</summary>

因为**「不出现这三类异常」不等于「可串行化」**。ANSI SQL 标准用「禁止哪些异常」来**定义**隔离级别，这是一个**必要条件式的定义**——它列举了已知的异常，但没有覆盖所有可能的不可串行化执行。

**写偏斜**就是漏网之鱼：两个事务读同一份数据（读集重叠）、写不同的行（写集不相交），各自都满足「无脏读、无不可重复读、无幻读」，合起来却违反全局不变量。

PostgreSQL 的 `REPEATABLE READ` 实际实现是 **SI**，它满足 ANSI 对 `REPEATABLE READ` 的要求（甚至更强，连幻读也消除了），但**仍弱于 `SERIALIZABLE`**。要在 PostgreSQL 中真正获得可串行化，必须显式写 `SERIALIZABLE`（它启用 SSI）。

**一句话**：SI 保证「每个事务看到一致的快照」，但不保证「整体等价于某个串行顺序」——前者是**局部一致性**，后者是**全局一致性**。

</details>

**Q2.** 版本链是「新版本在前」还是「旧版本在前」，会影响什么？

<details><summary>参考答案</summary>

影响**读路径的遍历长度**与**写路径的插入位置**：

**新版本在前（head = 最新）**：

- 优点：读**最新值**（最常见的情况）只需看第一个节点，O(1)。
- 缺点：读**旧快照**要沿链走很多步，链越长越慢。
- 典型：InnoDB（索引项指向最新版本，旧版本在 undo log 里反向回溯）、PostgreSQL（`ctid` 链）。

**旧版本在前（tail = 最新）**：

- 优点：读旧版本（靠近头部）快。
- 缺点：读最新值要走到链尾，O(n)。
- 实践：**很少用**，因为绝大多数读都要最新值。

**结论**：几乎所有实现都选「新版本在前」，因为**读最新值的频率远高于读历史版本**。代价是长事务（快照很旧）的读会退化为 O(链长)——这也是「长事务拖慢整个系统」的另一个原因。

此外，「新版本在前」还影响**可见性剪枝**：一旦遇到一个 `begin_ts <= read_ts` 的版本，就可以停止（因为更早的版本必然也满足 `begin_ts` 条件，但可能已被 `end_ts` 覆盖）——需要仔细处理 `end_ts` 才能安全剪枝。

</details>

**Q3.** 请构造一个写偏斜的例子（不要用医生值班），并说明为什么快照隔离放行它。

<details><summary>参考答案</summary>

**例子：银行的两个账户 + 透支保护规则**

规则：**两个账户的余额之和不能为负**（即至少有一个账户余额 ≥ 0）。初始：A = 100，B = 100。

```
T1: 读 A = 100, 读 B = 100 → 判断 A + B = 200 >= 0，取款安全
    UPDATE A = A - 150   → A = -50

T2: 读 A = 100, 读 B = 100 → 判断 A + B = 200 >= 0，取款安全
    UPDATE B = B - 150   → B = -50
```

**结果**：A = -50，B = -50，总和 -100，**违反「和不能为负」的规则**。

**为什么 SI 放行**：

1. **没有写-写冲突**：T1 写 A、T2 写 B，对象不相交，SI 的 first-committer-wins 检查发现写集无交集 → 都通过。
2. **读的是各自快照**：两者都读到 `A=100, B=100`，都认为「总和 200 是安全的」。
3. **冲突在优先图里是 R-W 环**：T1 读 B（值 100），T2 后来写 B → `T1 →rw T2`；T2 读 A（值 100），T1 后来写 A → `T2 →rw T1`。环成立，**不可串行化**。

**修法**：

- 用 `SERIALIZABLE`（SSI 会检测到两条 rw 边构成危险结构，中止一个）。
- 或显式加锁：`SELECT ... FOR UPDATE` 把两行都锁住（退化为 2PL）。
- 或把不变量物化成一行（如「总余额」行），让两个事务都更新它——这样就有写-写冲突了。

</details>

**Q4.** 一个系统跑了 3 小时的只读事务，会对 MVCC 造成什么影响？如何缓解？

<details><summary>参考答案</summary>

**影响链条**：

1. 只读事务的 `read_ts` 停留在 3 小时前。
2. **水位线（watermark）** = 所有活跃事务的最小 `read_ts`，因此水位线也停在 3 小时前。
3. 这 3 小时内所有被更新/删除的旧版本**都不能回收**（因为那个只读事务可能还需要它们）。
4. 后果：
   - **表膨胀**：死元组堆积，表扫描要跳过大量不可见行。
   - **索引膨胀**：索引项指向死元组，索引扫描变慢。
   - **版本链变长**：读旧快照要回溯更多步。
   - **vacuum/purge 无法推进**：清理线程被阻塞。
   - **磁盘与内存压力**：缓存里塞满死数据，挤掉热数据。
5. 极端情况下，可能导致**事务 ID 回卷（transaction ID wraparound）**（PostgreSQL 特有风险，需要 `VACUUM FREEZE`）。

**缓解手段**：

- `idle_in_transaction_session_timeout`：杀掉长时间空闲的事务（最常见的原因是应用忘了 `COMMIT`）。
- `statement_timeout`：限制单条语句的执行时间。
- 应用层：**避免长事务**，把只读分析放到副本上跑，不要在事务里做网络/文件 I/O。
- 监控 `pg_stat_activity` 里的 `xact_start`，对超过阈值的事务告警。
- PostgreSQL 14+ 的 `idle_session_timeout` 可以清理空闲会话。

**根本矛盾**：MVCC 用「保留历史」换「无阻塞读」，代价就是「历史必须有人负责清理」。长事务把这个代价放大到不可接受。

</details>

**Q5.** 为什么说「索引覆盖扫描（index-only scan）在 MVCC 下并不总是更快」？

<details><summary>参考答案</summary>

因为**索引项本身不携带完整的可见性信息**（在多数实现中）：

1. 索引通常只存**键值 + 指向堆表的指针**（如 PostgreSQL 的 `ctid`、InnoDB 的主键）。它**不知道**这个项对应的行版本对当前快照是否可见。
2. 因此「索引覆盖扫描」仍需**回表**（或访问 visibility map）判断可见性——如果可见性信息不在索引里，就必须读堆页，**覆盖扫描的意义就没了**。
3. 更糟的是，索引里可能包含**已删除但尚未 vacuum 的项**，扫到后必须逐个检查并跳过，产生大量无效 I/O。

**各家的对策**：

- **PostgreSQL**：用 **visibility map**（每页一位，标记「所有元组对所有事务可见」）；若页面被标记为 all-visible，index-only scan 可以跳过回表。但**页面一旦有更新就会被清除标记**，所以写多的表上 index-only scan 收益有限。
- **InnoDB**：二级索引项含主键，回表后还要走 undo log 判断可见性；所以 InnoDB 的「覆盖索引」优化只在**不需要判断可见性**（即索引里含所有需要的列，且 MVCC 判定可以通过索引本身完成）时有效。
- **部分新系统**（如 HyPer、Umbra）用**版本化的索引**或**delta 存储**，把可见性信息编码进索引，但代价是索引膨胀与写放大。

**结论**：MVCC 把「可见性判断」的成本从**锁等待**转移到了**索引访问路径**上。这是「无阻塞」的隐性代价。

</details>
