## 3. 核心概念

> 以下概念定义为通用教材口径，待 2026 官方 slides 发布后核对术语与侧重。

### 3.1 Replication（复制）

把**同一份数据**存放在多个节点上。目的：**容错**（一个节点挂了还有别的）、**读扩展**（读请求分散）、**地理就近**（降低延迟）。

### 3.2 Partitioning / Sharding（分区 / 分片）

把**不同数据**分散到不同节点。目的：**写扩展**（写请求分散）、**存储扩展**（单机装不下）。

### 3.3 Primary-Replica Replication（主从复制）

一个节点是 **primary（主）**，接受所有写；其他是 **replica（从）**，异步或同步地应用主节点的日志。读可以打到从节点（可能读到旧数据）。

### 3.4 Multi-Leader Replication（多主复制）

多个节点都能接受写，彼此同步。好处是**写延迟低**（就近写）；坏处是**写冲突**需要解决（最后写入者胜、版本向量、应用层合并）。

### 3.5 Quorum（法定人数）

N 个副本中，写需 W 个确认、读需 R 个确认。若 **`R + W > N`**，则读集合与写集合必有交集，读能读到最新写。

### 3.6 Two-Phase Commit（两阶段提交，2PC）

分布式原子提交协议：**准备阶段（prepare / vote）** 协调者问所有参与者「能否提交」，参与者回复 yes/no；**提交阶段（commit / decide）** 若全部 yes 则协调者广播 commit，否则广播 abort。

### 3.7 CAP Theorem（CAP 定理）

分布式系统在**网络分区（Partition）** 发生时，只能在**一致性（Consistency）** 与**可用性（Availability）** 之间选一个。注意：P 不是「可选」，网络分区**必然会发生**。

### 3.8 PACELC

CAP 的扩展：**P** 时在 **A** 与 **C** 之间选；**E**（Else，正常运行时）在 **L**（Latency）与 **C**（Consistency）之间选。

### 3.9 TrueTime

Google Spanner 用的**不确定时钟 API**：返回一个时间**区间** `[earliest, latest]` 而非一个点，配合「等待不确定窗口过去」（commit-wait）实现**外部一致性（external consistency）**。

### 3.10 Data Locality（数据本地性）

分布式查询优化原则：**把计算搬到数据所在节点**，而不是把数据搬到计算节点（避免网络传输）。

## 4. 通俗理解

**复制 = 同一本书印多份放不同图书馆**：任何一家烧了，别的还有；多个读者可以就近借。但**修改内容时要通知所有馆**，通知有延迟，所以不同馆的版本可能短暂不一致。

**分区 = 一套百科全书分册放不同图书馆**：A–F 在第一家、G–M 在第二家……存储和借阅压力都分散了。但要查「所有以 S 开头的人物」就得跑好几家。

**2PC = 婚礼策划**：「大家都准备好了吗？」（准备阶段）——所有人回答「准备好了」；然后司仪宣布「开始」（提交阶段）。问题在于：**如果司仪在问完「准备好了吗」之后突然晕倒**，所有宾客就只能干等着，不知道婚礼到底办不办——这就是 2PC 的**阻塞**问题。

**CAP = 电话断线时你选「说真话」还是「继续说话」**：网络分区（电话断线）发生时，你要么保证「说的都是最新的真话」（一致性，但可能说不出话——不可用），要么保证「总能说话」（可用性，但可能说的是过时信息）。

## 5. 原理与推导

> **以下为通用知识整理，非依据 2026 官方讲义。**

### 5.1 为什么分布式：三个动机与三个新问题

**动机**：

1. **可扩展性（scalability）**：单机 CPU/内存/磁盘有上限；水平扩展（加机器）比垂直扩展（换更强的机器）便宜且无上限。
2. **容错（fault tolerance）**：单机故障 = 全站不可用；多机可以切换。
3. **地理就近（geo-distribution）**：用户在全球，数据放近处降低延迟、满足数据主权法规（GDPR）。

**新问题**：

1. **部分失败（partial failure）**：一台机器挂了，其他还在跑——系统处于「半死不活」状态，比全挂更难处理。
2. **网络不可靠（unreliable network）**：消息可能丢失、重复、乱序、延迟不定。**无法区分「节点挂了」与「网络慢」**——这是分布式系统的根本困难。
3. **时钟不可靠（unreliable clocks）**：每台机器的时钟有漂移，NTP 同步也有误差；**不能用物理时钟确定事件的全局顺序**。

### 5.2 复制：主从 vs 多主

| 维度 | 主从（Primary-Replica） | 多主（Multi-Leader） |
|---|---|---|
| 写入点 | 只有主节点 | 任意节点 |
| 冲突 | **无**（单点写入天然有序） | **有**，需要解决 |
| 写延迟 | 跨地域写要绕到主节点 | 就近写，延迟低 |
| 故障切换 | 需要选主（leader election） | 无单点，但冲突更多 |
| 一致性 | 容易做强一致 | 通常是最终一致 |
| 典型 | PostgreSQL 流复制、MySQL 主从、Raft 组 | 多数据中心部署、Google Docs 类协作 |

**同步 vs 异步复制**：

- **同步（synchronous）**：主节点等所有（或多数）从节点确认后才返回。强一致，但延迟高、可用性低（从节点慢就拖累主节点）。
- **异步（asynchronous）**：主节点写完本地就返回，后台复制。延迟低、可用性高，但**故障切换可能丢数据**（从节点还没收到最新的写）。
- **半同步（semi-synchronous）**：等**至少一个**从节点确认。折中方案，MySQL 的半同步复制就是这种。

### 5.3 Quorum：`R + W > N`

设 N = 副本数，W = 写需确认的副本数，R = 读需询问的副本数。

**若 `R + W > N`**：由鸽巢原理，读集合与写集合**必有交集**，交集中的副本有最新写 → 读能读到最新值。

**例**：N=3。

- `W=2, R=2`：`2+2=4 > 3` ✔ 强一致（但任一副本挂掉就不可用）
- `W=3, R=1`：`3+1=4 > 3` ✔ 读快写慢（写要全部确认）
- `W=1, R=1`：`1+1=2 < 3` ✘ 可能读到旧值（最终一致）

**权衡**：`W` 大 → 写慢但读快且一致性强；`R` 大 → 读慢但写快。常见配置是 `W = R = majority = ⌈(N+1)/2⌉`。

**注意**：quorum 只保证「读到最新**已确认**的写」，不保证**线性一致性（linearizability）**——因为并发写可能乱序到达不同副本，需要额外的机制（如版本号 + 读修复）。

### 5.4 2PC 详解

**角色**：一个**协调者（coordinator）** + 多个**参与者（participant）**。

**阶段一：Prepare（投票）**

```
协调者 → 所有参与者: PREPARE(T)
每个参与者:
    - 执行事务的所有本地操作（但先不提交）
    - 把 undo/redo 日志刷盘（保证能提交也能回滚）
    - 回复 YES（可以提交）或 NO（不能）
```

**阶段二：Commit / Abort（决定）**

```
若所有参与者都回复 YES:
    协调者 → 所有参与者: COMMIT
    参与者: 提交本地事务，回复 ACK
否则:
    协调者 → 所有参与者: ABORT
    参与者: 回滚本地事务，回复 ACK
协调者收到所有 ACK 后，写 "事务完成" 日志
```

**2PC 的三个致命问题**：

1. **阻塞（blocking）**：参与者在回复 YES 之后，**必须等待协调者的决定**。若协调者崩溃，参与者会**一直持有锁并阻塞**，直到协调者恢复。
2. **协调者单点**：协调者的日志若丢失，参与者无法知道该提交还是回滚。**部分参与者可能提交、部分回滚**——数据库不一致。
3. **性能差**：两次网络往返 + 多次 fsync，跨数据中心时延迟可达几十毫秒到几百毫秒。

**改进方案**：

- ** presumed abort**：协调者没收到决定时默认回滚（减少一种不确定状态）。
- **3PC（三阶段提交）**：加一个「预提交」阶段，减少阻塞窗口，但仍不能完全避免（且在网络分区下仍不安全）。
- **共识协议（Paxos / Raft）代替 2PC**：把协调者的决定做成一个复制状态机，协调者崩溃后新协调者能恢复决定。这是 Spanner、CockroachDB 的做法。
- **避免分布式事务**：把相关数据放在同一分区（**co-location**），让事务变成单机事务。这是很多系统的首选策略。

### 5.5 CAP 定理的精确含义

**常见误解**：「三选二，选 CA 就是单机数据库」——这是错的。

**精确表述**：在网络分区（P）**发生时**，系统不可能同时保证**线性一致性（C）** 与**每个非故障节点都能响应（A）**。

**关键点**：

1. **P 不是可选项**：网络分区是**物理现实**，不是设计选择。所以真正的选择是「分区发生时，牺牲 C 还是牺牲 A」。
2. **C 是线性一致性**，不是 ACID 的 C（一致性）。ACID 的 C 指「满足约束」，与 CAP 的 C 完全不同——这是最常见的混淆。
3. **CAP 只在分区期间适用**：没有分区时，系统可以同时有 C 和 A（但要付出延迟代价，这就是 PACELC 的补充）。

**分类**：

- **CP 系统**：分区时拒绝服务以保证一致（如 HBase、ZooKeeper、etcd、Spanner）。
- **AP 系统**：分区时继续服务但可能返回旧数据（如 Cassandra、DynamoDB、Riak）。

### 5.6 PACELC

**表述**：**If Partition, choose Availability or Consistency; Else, choose Latency or Consistency.**

即：

- **P 时**：A vs C（CAP 的内容）。
- **E（正常运行时）**：L vs C——即使没有分区，**强一致也需要协调**（等待多数派确认），这会增加延迟。

**例**：

- **PC/EC**：Spanner（分区时选 C，正常时也选 C，代价是高延迟）。
- **PA/EL**：Cassandra（分区时选 A，正常时也选低延迟，最终一致）。
- **PC/EL**：部分系统（分区时保守，正常时追求低延迟）。

**价值**：PACELC 解释了为什么「强一致系统即使在没故障时也比最终一致系统慢」——不是实现不好，而是**协调的固有成本**。

### 5.7 全局时间与 Spanner 的 TrueTime

**问题**：分布式事务需要**全局单调的时间戳**来确定顺序。但物理时钟有漂移：

- 两台机器的时钟可能差几十毫秒。
- NTP 同步本身有误差（网络延迟、时钟漂移率）。
- 时钟可能**回拨**（NTP 校正、闰秒）。

**Spanner 的方案**：**TrueTime API** 返回一个区间 `TT.now() = [earliest, latest]`，保证**真实时间**一定在这个区间内。误差 ε 通常 1–7 ms（靠机房里的原子钟 + GPS）。

**如何用它实现外部一致性**：

1. 事务提交时分配时间戳 `s = TT.now().latest`。
2. **commit-wait**：等到 `TT.now().earliest > s` 才真正提交（保证此后任何事务的时间戳都大于 s）。
3. 于是「时间戳顺序」= 「真实时间顺序」，全局一致。

**代价**：每次提交要等 ε（几毫秒），这是 Spanner 写延迟高于单机数据库的原因之一。

**其他方案**：

- **混合逻辑时钟（HLC）**：结合物理时钟与逻辑计数器，CockroachDB 使用。
- **纯逻辑时钟（Lamport clock）**：只保证因果序，不保证与真实时间对应。
- **中心化时间戳服务**：单点分配（如 TSO），但成为瓶颈与单点故障。

### 5.8 分布式查询执行

**核心原则**：**把计算搬到数据旁，而不是把数据搬到计算旁**。

**三个关键决策**：

1. **谓词下推（predicate pushdown）**：把 `WHERE` 条件下推到数据所在节点，减少网络传输。`SELECT * FROM t WHERE x > 100` 应该在每个分区本地过滤后再汇总。
2. **连接策略**：
   - **广播（broadcast）**：小表广播到所有节点，与大表本地连接。适合「一大一小」。
   - **重分区（reshuffle / repartition）**：两表按连接键重新分区，使同键数据落在同一节点。适合「两大」。
   - **半连接（semi-join）**：先传连接键，再传匹配的行，减少传输量。
3. **聚合策略**：
   - **两阶段聚合**：每个节点本地做部分聚合（`SUM` / `COUNT` / `MAX`），再把部分结果汇总。
   - **一阶段聚合**：若聚合函数不可分解（如 `MEDIAN`），必须把数据集中。

**代价模型**：网络传输的代价远高于本地 I/O 与 CPU，所以分布式优化器会给「跨节点传输的字节数」很高的权重。

### 5.9 分布式事务的替代方案

**2PC 太重**，很多系统选择避免它：

| 方案 | 做法 | 适用 |
|---|---|---|
| **单分区事务** | 把相关数据放同一分区（co-location） | 大部分 OLTP（按用户/租户分片） |
| **Saga** | 把长事务拆成一串本地事务 + 补偿操作 | 微服务、跨服务业务流 |
| **TCC（Try-Confirm-Cancel）** | 预留资源 → 确认 → 取消 | 支付、库存 |
| **最终一致 + 幂等** | 允许短暂不一致，靠重试与去重收敛 | 消息队列、事件驱动 |
| **共识复制 + 单机事务** | 每个分区内部用 Raft 保证一致，跨分区尽量避免 | Spanner、CockroachDB、TiDB |

**核心洞察**：**分布式事务的成本来自「跨网络的原子性」**。如果能通过**数据布局**（co-location）把事务限制在单机，就能同时获得原子性与性能。

### 5.10 分布式系统的故障检测

**根本困难**：**无法区分「节点挂了」与「网络慢/分区」**（这就是 FLP 不可能性与 CAP 的根源）。

**实践方案**：

- **心跳 + 超时（heartbeat + timeout）**：超时未收到心跳就认为节点挂了。超时设短 → 误判多（网络抖动就切主）；设长 → 故障恢复慢。
- **故障检测器（failure detector）**：φ accrual failure detector（Cassandra 使用）输出「怀疑度」而非二元判断，让上层按需决策。
- **租约（lease）**：主节点持有「租约」，租约到期前从节点不选举。避免「双主」（split-brain）。
- **fencing token**：给每次选主的任期编号，旧主即使「复活」也会因编号过期而被拒绝写入。

### 6.2 Agent 自行编写的教学示例

2PC 协调者的骨架（示意）：

```cpp
// 非官方示例：2PC 协调者（不含故障恢复）
enum class Vote { kYes, kNo };

bool TwoPhaseCommit(const std::vector<Participant *> &parts) {
  // 阶段一：准备
  std::vector<Vote> votes;
  for (auto *p : parts) {
    votes.push_back(p->Prepare());   // 参与者执行本地操作并刷日志
  }

  bool all_yes = std::all_of(votes.begin(), votes.end(),
                             [](Vote v) { return v == Vote::kYes; });

  // 关键：把决定写进协调者日志（崩溃恢复的依据）
  WriteCoordinatorLog(all_yes ? Decision::kCommit : Decision::kAbort);

  // 阶段二：执行决定
  for (auto *p : parts) {
    if (all_yes) p->Commit(); else p->Abort();
  }
  return all_yes;
}
```

## 7. 容易混淆的概念

| 概念 A | 概念 B | 关键差别 |
|---|---|---|
| 复制 | 分区 | 复制是**同一份数据多副本**（容错 + 读扩展）；分区是**不同数据分开放**（写 + 存储扩展）；两者正交，可组合 |
| 2PC | 2PL | 2PC 是**原子提交协议**（跨节点的 commit/abort）；2PL 是**并发控制协议**（锁的两阶段）。名字像，作用完全不同 |
| CAP 的 C | ACID 的 C | CAP 的 C 是**线性一致性**；ACID 的 C 是**满足约束**。完全不同的概念 |
| CAP | PACELC | CAP 只管**分区时**；PACELC 补充了**正常运行时**的延迟 vs 一致性权衡 |
| 同步复制 | 异步复制 | 前者提交要等从节点确认（强一致、慢）；后者立即返回（快、可能丢数据） |
| 主从复制 | 多主复制 | 前者单点写入无冲突；后者多写点需解决冲突 |
| 共识（Raft/Paxos） | 2PC | 共识解决「**一个值**在多数派上达成一致」；2PC 解决「**一个事务**在多个节点上原子提交」。共识可以**实现** 2PC 的协调者 |
| 分区容错（P） | 分区（partitioning） | CAP 的 P 是**网络分区**（故障）；partitioning 是**数据分片**（设计）。同名不同义 |

## 11. 自我检查

**Q1.** 为什么说「CAP 三选二」是一个误导性的说法？

<details><summary>参考答案</summary>

因为 **P（分区容错）不是可选项**。

**理由**：

1. **网络分区是物理现实**，不是设计选择。交换机故障、网线被挖断、机房断电、GC 停顿导致的超时——这些**必然会发生**。你可以选择「不部署分布式系统」来避免 P，但一旦部署了分布式系统，P 就在那里。
2. 所以真正的选择是：**当分区发生时，牺牲 C 还是牺牲 A**。
   - 牺牲 C（选 A）：继续响应请求，但可能返回旧数据或不一致的数据（AP）。
   - 牺牲 A（选 C）：拒绝部分请求，保证返回的数据一定是最新的（CP）。
3. **「CA 系统」不存在于分布式语境**：所谓「CA 系统」其实是**单机系统**（没有网络分区问题），或者「假设网络永不出错」的系统（这个假设在分布式环境下是错的）。

**另一个常见误解**：把 CAP 的 C 当成 ACID 的 C。CAP 的 C 是**线性一致性（linearizability）**——所有操作看起来像是在某个全局时间点上原子执行的；ACID 的 C 是**约束满足**——事务前后数据满足完整性约束。两者完全不同。

**PACELC 的补充**：即使**没有分区**，强一致也需要协调（等待多数派确认），这会增加延迟。所以正常运行时也要在 L 与 C 之间选。这解释了「为什么 Spanner 即使不故障也比单机 MySQL 慢」。

</details>

**Q2.** 2PC 中，如果协调者在发出所有 PREPARE 之后、发出 COMMIT 之前崩溃，会发生什么？如何缓解？

<details><summary>参考答案</summary>

**会发生「阻塞」**：

1. 所有参与者已经回复 YES，并且**已经执行了本地操作、写了日志、持有锁**。
2. 参与者在等待协调者的决定（COMMIT 或 ABORT）。
3. 协调者崩溃 → 参与者**不知道该怎么办**：
   - 若自行提交：可能其他参与者收到了 ABORT（如果协调者其实决定了 ABORT），导致不一致。
   - 若自行回滚：可能其他参与者收到了 COMMIT，同样不一致。
4. 参与者只能**继续持有锁并等待**，阻塞所有涉及这些数据的其他事务。

**这就是 2PC 的「阻塞问题」**：参与者处于**不确定（uncertain）状态**，无法单方面决定。

**缓解手段**：

1. **协调者持久化决定**：协调者在发出 COMMIT/ABORT **之前**先把决定写入日志并 fsync。协调者恢复后重放日志，重新发送决定。这解决了「协调者临时崩溃」，但解决不了「协调者永久损坏」。
2. **参与者超时后询问其他参与者**：若某个参与者已经收到决定，可以告知其他人。但如果**所有参与者都没收到决定**，仍然无解。
3. **3PC（三阶段提交）**：加一个 pre-commit 阶段，让参与者在超时后可以安全地自行提交（因为进入 pre-commit 意味着所有人都已 YES）。但 3PC 在**网络分区**下仍不安全（可能出现「一部分提交、一部分回滚」）。
4. **用共识协议复制协调者**：把协调者的决定做成 Raft/Paxos 复制的状态机，协调者崩溃后新 leader 能恢复决定。这是 Spanner、CockroachDB 的做法。
5. **避免 2PC**：把相关数据 co-locate 到同一分区，让事务变成单机事务（最优解）。

**结论**：2PC 的阻塞性是**协议本身的性质**，无法在不引入额外假设（同步网络、无故障）的情况下消除。这就是为什么大规模系统倾向于「避免跨分区事务」而不是「优化 2PC」。

</details>

**Q3.** 设 N=3，W=2，R=2。一次读操作询问了副本 A、B，一次并发的写操作写入了副本 B、C。读能读到最新值吗？

<details><summary>参考答案</summary>

**取决于时序，不一定能读到**。

**`R + W > N` 保证的是「读集合与写集合有交集」**：读集合 {A, B}，写集合 {B, C}，交集是 {B}。所以**读一定会询问到 B**——但**能不能读到新值取决于 B 上是否已经应用了这次写**。

**两种时序**：

1. **写先完成，读后发生**：B 上已有新值 → 读在 B 上看到新值，取版本号最大的 → **读到最新值** ✔
2. **读先发生，写后完成**：B 上还是旧值 → 读在 A、B 上都看到旧值 → **读到旧值** ✘

**关键**：`R + W > N` 保证的是**「写完成之后开始的读」能读到最新值**（顺序一致性/线性一致性的一部分），**不保证并发读能读到**。

**要保证并发读也能读到**，需要：

- **读修复（read repair）**：读到旧值时，把新值回写到该副本。
- **写后读一致性（read-your-writes）**：客户端记住自己写的版本号，读时要求版本号 >= 自己的写版本。
- **线性一致性协议**：如 Raft/Paxos，所有读写都经过 leader 或多数派确认，代价是延迟。

**补充**：quorum 还有一个隐含假设——**副本不会「忘记」写过的值**。若某个副本因为故障恢复而丢失了最近的写（异步复制 + 崩溃），quorum 的交集可能落在「丢失了写」的副本上，读到旧值。所以 quorum 通常要配合**反熵（anti-entropy）** 与 **Merkle tree 校验**来修复。

</details>

**Q4.** 为什么说「分布式事务慢」？慢在哪里？

<details><summary>参考答案</summary>

慢在**网络往返 + 持久化 + 协调**三者的叠加：

1. **网络往返（RTT）**：
   - 2PC 需要**两轮**网络往返（prepare 一轮、commit 一轮）。
   - 同机房 RTT 约 0.5 ms，跨地域（如美东到美西）约 30–70 ms。
   - 一个跨地域 2PC 事务的**最小延迟**就是 2 × 60 = 120 ms——比单机事务（<1 ms）慢两个数量级。

2. **持久化（fsync）**：
   - 参与者必须在回复 YES **之前**把日志刷盘（否则崩溃后无法提交）。
   - 协调者必须在发决定**之前**把决定刷盘。
   - 每次 fsync 在 SSD 上约 0.1–1 ms，机械盘 5–10 ms。
   - 一个 2PC 事务至少有 3 次关键 fsync（参与者本地、协调者决定、参与者提交）。

3. **协调开销**：
   - 需要维护事务状态、等待所有参与者、处理超时与重试。
   - 参与者持锁时间长（从 prepare 到 commit），**阻塞其他事务**——这是「延迟的二次放大」。

4. **故障恢复成本**：
   - 协调者崩溃后，参与者阻塞等待；恢复需要重放日志、重新协调。

**对比**：

| 操作 | 延迟量级 |
|---|---|
| 单机事务（无跨节点） | 0.1–1 ms |
| 同机房 2PC | 2–5 ms |
| 跨地域 2PC（同洲） | 50–150 ms |
| 跨洲 2PC | 200–500 ms |

**这就是为什么**：

- Spanner 用 TrueTime 把「跨洲事务」的延迟压到 ~100 ms 已经是工程奇迹。
- 大部分系统选择 **co-location**（把相关数据放同一分区）来**避免**跨节点事务。
- 微服务架构用 **Saga**（本地事务 + 补偿）代替 2PC，用「最终一致」换「低延迟」。

</details>

**Q5.** Spanner 的 TrueTime 为什么能提供「外部一致性」，而普通的 NTP 时钟不能？

<details><summary>参考答案</summary>

**普通 NTP 的问题**：NTP 给你一个**点估计**（「现在大约是 12:00:00.123」），但**不告诉你误差有多大**。两台机器的时钟可能差 50 ms，你不知道该信谁。于是：

- 无法判断「事件 A 是否真的发生在事件 B 之前」。
- 事务 T1 在机器 1 上提交（时钟 12:00:00.100），T2 在机器 2 上开始（时钟 12:00:00.050）——按时间戳 T2 在前，但**真实时间**可能 T1 在前。这违反了「外部一致性」（若 T1 在真实时间上先完成，则任何在 T1 之后开始的事务必须看到 T1 的效果）。

**TrueTime 的解决方案**：返回一个**区间** `TT.now() = [earliest, latest]`，**保证真实时间一定落在这个区间内**（误差 ε 通常 1–7 ms，靠原子钟 + GPS）。

**如何用它实现外部一致性**：

1. 事务 T 提交时分配时间戳 `s = TT.now().latest`（**取区间上界**，保证 s 一定 >= 真实提交时刻）。
2. **commit-wait**：等到 `TT.now().earliest > s`（即「现在的最早可能时间」已经超过 s），才真正让事务对外可见。
3. 这样保证：**任何在 T 提交之后开始的事务，其时间戳一定 > s**。于是「时间戳顺序」与「真实时间顺序」一致。

**为什么普通 NTP 做不到**：即使 NTP 把误差控制在 10 ms，它**不提供误差边界**，所以无法做 commit-wait（你不知道要等多久）。TrueTime 的价值不在于「更准」，而在于**「知道有多不准」**——有了误差上界，就能用「等待」把不确定性消除。

**代价**：

- 硬件成本（每机房需要原子钟 + GPS 接收器）。
- 提交延迟增加 ε（几毫秒）。
- 若时钟误差变大（GPS 失锁），Spanner 会**降低吞吐**（等待更久）而不是牺牲一致性。

**替代方案**：CockroachDB 用 **HLC（混合逻辑时钟）**——物理时钟 + 逻辑计数器，不保证真实时间对应，但保证因果序；跨地域事务用「时钟不确定性窗口」+ 重试来处理。

</details>
