## 3. 核心概念

### 3.1 BusTub（教学数据库）

CMU 数据库组开发的**教学用关系型数据库**，用 C++17 实现。它不是一个生产级数据库，而是**为教学裁剪过的骨架**：磁盘管理器、缓冲池、索引、执行引擎、事务管理都被拆成独立模块，学生按项目逐个实现/补全。

代码库开源在 `https://github.com/cmu-db/bustub`。每学期会开一个新分支（如 `fall2026`），学生从该分支 fork 出**私有仓库**开始工作。

**Fall 2026 的实际任务是 Robin Hood Hash Set（罗宾汉哈希集合）**——一个**定容开放寻址（open addressing）** 哈希集合，而不是传统意义上的「C++ 语法练习」。

## 4. 通俗理解

把 BusTub 想成**一辆被拆散的汽车**：

- **Project #0** 是「先学会用扳手」——不是造车，是确认你会用工具（哈希表 + 并发 + C++ 内存管理）。
- **Project #1** 是「装油箱和油路」——缓冲池是数据库的「内存油箱」，负责把磁盘上的页搬进搬出。
- **Project #2** 是「装变速箱」——B+ 树是索引，决定数据「怎么快速找到」。
- **Project #3** 是「装发动机」——查询执行算子真正把 SQL 变成结果。
- **Project #4** 是「装刹车和安全带」——并发控制保证多个事务同时跑时不出车祸。

每个项目都是**独立的一块**，但装完之后车才能开。这也是为什么课程的顺序是「存储 → 索引 → 执行 → 事务」。

**关于评分**：Autolab/Gradescope 像「自动阅卷机」——你交代码，它跑一堆你看不到的测试，给你一个分数。所以**不能只让公开测试通过**，要按规格实现。

## 5. 原理与推导

> 本节讲「为什么课程这样设计」，帮助你理解项目之间的依赖关系与学习路径。

### 5.1 项目顺序 = 数据库的分层架构

数据库系统的经典分层（自底向上）：

```
┌─────────────────────────────────┐
│  SQL 前端 / 解析器 / 优化器      │  ← 课程 L15–L17（无项目）
├─────────────────────────────────┤
│  查询执行引擎（算子）            │  ← Project #3
├─────────────────────────────────┤
│  事务管理 / 并发控制 / 恢复      │  ← Project #4
├─────────────────────────────────┤
│  索引（B+ 树）                   │  ← Project #2
├─────────────────────────────────┤
│  缓冲池 / 内存管理               │  ← Project #1
├─────────────────────────────────┤
│  磁盘管理器 / 页布局             │  ← 课程 L03–L06（无项目）
└─────────────────────────────────┘
```

项目顺序**自底向上**，因为上层依赖下层：

- 没有缓冲池（P1），B+ 树（P2）无法把节点读进内存。
- 没有 B+ 树（P2），索引扫描算子（P3）无法实现。
- 没有执行算子（P3），事务（P4）没有可保护的对象。

**但注意**：BusTub 的代码库是**预先给了骨架**的——你在 P1 时，B+ 树的接口已经存在（只是未实现或用了简化版）。所以项目之间是**接口依赖**而非「必须严格串行完成」。

### 5.2 为什么 P0 是哈希表而不是「C++ 语法练习」

传统 C++ primer 会让你写 `vector`、`string` 之类的玩具。BusTub 的 P0 选择 **Robin Hood Hash Set**，原因是它同时覆盖了数据库项目需要的**全部核心 C++ 技能**：

| 技能 | 在 Robin Hood Hash Set 中的体现 |
|---|---|
| 手动内存管理 | 用 `new[]` / `delete[]` 或 `std::unique_ptr<T[]>` 管理桶数组 |
| 对象生命周期 | 移动构造/移动赋值后源对象必须处于有效但空的状态（`Capacity()==0`） |
| 模板 | `RobinHoodHashSet<Key, Hasher, KeyEqual>` 三个模板参数 |
| `const` 正确性 | `Contains` / `Size` / `Capacity` 必须是 `const` 成员函数 |
| 异常安全 | `capacity == 0` 抛 `std::invalid_argument`，不能泄漏内存 |
| 并发 | `Insert` / `Remove` / `Contains` 线程安全，且**禁止单把全局锁**（要 > 1.2 倍加速比） |
| 算法 | 开放寻址、线性探测、Robin Hood 交换、tombstone 处理、探测距离统计 |

**为什么强调「禁止全局锁」**：因为数据库的缓冲池、锁管理器、B+ 树全都要求**细粒度并发**。如果学生在 P0 就习惯「一把大锁保平安」，后面三个项目会全线崩溃。P0 用「加速比 > 1.2」这个硬指标强制你写**分片锁（sharded locks）** 或**无锁结构**。

### 5.3 Robin Hood Hashing 的原理（P0 核心算法）

**普通线性探测（linear probing）** 的问题：某些键的探测距离很长（「富者愈富」），导致长尾延迟。

**Robin Hood 的核心思想**：**劫富济贫**——插入时，如果当前槽位的「原住民」的探测距离**小于**新键的探测距离，就把原住民**踢出去**，让新键占这个槽，然后带着原住民继续往后找位置。

**形式化**：

```
insert(key):
  d = 0                       # 新键的当前探测距离
  while true:
    slot = hash(key) + d
    if slot is empty or tombstone:
        place key at slot with distance d; return true
    if slot.key == key:
        return true           # 重复插入，Size 不变
    if slot.distance < d:     # 原住民比新键「更靠近家」
        swap(key, slot.key)   # 劫富济贫
        swap(d, slot.distance)
    d += 1
```

**效果**：

- **探测距离方差大幅降低**——所有键的探测距离趋于平均，长尾消失。
- **查找的平均探测距离**接近理论下界。
- **代价**：插入时有额外的 swap，但 swap 是常数时间。

**删除的难点**：开放寻址不能直接置空（会切断探测链），必须用 **tombstone（墓碑）** 标记「这里曾经有元素」。tombstone 会导致探测链变长，所以需要在合适的时机**重建（rehash）**。

**`MaxProbeDistance()` 的定义陷阱**（官方明确）：

- 只统计 **occupied** 桶的探测距离（tombstone 和 empty 不算）。
- 若集合中没有该键，`MaxProbeDistance()` 应返回 `Capacity()`——这是一个**哨兵值**，表示「找不到」。

### 5.4 为什么 P1–P2 禁 coding agents 而 P3–P4 允许

这是 Fall 2026 的新政策，背后有明确的教学逻辑：

- **P1（缓冲池）与 P2（B+ 树）** 是**「手感型」项目**：核心难点在于**指针操作、并发时序、边界条件**（比如 B+ 树分裂时的 latch 顺序）。这些只能靠**自己调试**学会。让 AI 生成代码，你会得到一个「看起来对但你不懂」的实现，然后在 Debug Check 里翻车。
- **P3（查询执行）与 P4（并发控制）** 是**「结构型」项目**：算子/锁管理器的逻辑相对独立、模式重复（每个算子都是 `Init` / `Next` 两个函数），AI 辅助的价值更高，学习收益损失更小。
- **但都要求 reflection**：写一页说明「你用了什么工具、用它做了什么、你自己做了什么」——这是**元认知训练**。

**对自学者的启示**：即使你不受课程规则约束，也建议**P1/P2 自己写**，因为它们是面试中最常被追问的部分（「B+ 树分裂时你怎么处理 latch？」）。

### 5.5 评分构成与「Debug & Reasoning Check」

Fall 2026 的项目占 40%，其中包含：

1. **自动评分**（Autolab/Gradescope 跑隐藏测试）——大部分分数。
2. **两次 Debug & Reasoning Check**——给一段**有 bug 的代码**，要求你在限定时间内找出并修复，同时解释推理过程。
3. **可选的 Code Reasoning Interview**——口头解释你的实现。

**Debug Check 的意义**：它防止「代码能过测试但作者不懂」。因为隐藏测试可以通过「试错 + 提交次数」蒙过去，但现场调试不能。

**对自学者的启示**：做完项目后，**故意把自己的代码改坏**（删掉一个 latch、把 `<=` 改成 `<`），看测试是否失败、为什么失败。这是最有效的自测方式。

**项目依赖关系示意**（理解分层）：

```cpp
// 非官方示例：三层依赖的最小骨架
class DiskManager {                 // L03–L06：页在磁盘上
 public:
  virtual void ReadPage(page_id_t pid, char *data) = 0;

class BufferPoolManager {           // P1：页在内存里

 private:
  DiskManager *disk_;
  std::vector<Frame> frames_;
  LRUKReplacer replacer_;

class BPlusTree {                   // P2：索引结构，节点是 Page
 public:
  bool Insert(const Key &k, const RID &rid);
  bool GetValue(const Key &k, std::vector<RID> *out);
 private:
  BufferPoolManager *bpm_;          // 依赖 P1
  page_id_t root_pid_;
};
```

**一个「故意写坏」的自测练习**（对应 5.5 节的 Debug Check 训练）：

```cpp
// 非官方示例：这段代码有一个并发 bug，试着找出来
class Counter {
 public:
  void Inc() {
    std::lock_guard<std::mutex> guard(latch_);
    ++value_;
  }
  size_t Get() const {
    return value_;                  // BUG：读没有加锁 → 数据竞争
  }
 private:
  mutable std::mutex latch_;
  size_t value_{0};
};
```

修法：`Get()` 也要加锁（或把 `value_` 改成 `std::atomic<size_t>`）。这类 bug 在 P1 的缓冲池里非常常见——**读也要保护**。

## 7. 容易混淆的概念

| 概念 A | 概念 B | 关键差别 |
|---|---|---|
| Project #0 | 「C++ 语法练习」 | P0 实际是 **Robin Hood Hash Set**（数据结构 + 并发），不是语法玩具 |

## 11. 自我检查

**Q1.** 为什么 Project #0 不计分，却要求「必须满分才能继续课程」？

<details><summary>参考答案</summary>

因为 P0 是**能力门槛（gate）**，不是**评分项**。

**理由**：

1. **后续项目全部依赖 P0 的技能**：P1 的缓冲池需要手动管理页帧（`new`/`delete`、移动语义）；P2 的 B+ 树需要模板与 `const` 正确性；P3/P4 需要并发安全的数据结构。如果 P0 不过，后面必然全线崩溃。
2. **早发现比晚发现好**：如果 P0 计分但允许低分通过，学生会在 P1 花三倍时间补 C++ 基础，最后退课。设成硬门槛能让学生在第一周就做出「补 C++ 还是退课」的决定。
3. **P0 的测试是「客观的」**：哈希表的正确性可以完全自动验证（插入/删除/查找/容量/探测距离），不像 P1/P2 有大量隐藏的并发边界。所以「满分」是一个明确、可达的标准。
4. **并发要求是筛选器**：「加速比 > 1.2 且禁止全局锁」这条要求，直接筛掉了「只会写单线程代码」的学生。

**对自学者的启示**：即使不做后续项目，P0 也是一个**极好的 C++ 并发练习**——它把模板、RAII、移动语义、开放寻址、分片锁全部串在一起，两三天能写完，性价比很高。

</details>

**Q2.** 为什么课程把「缓冲池」放在「B+ 树」之前？

<details><summary>参考答案</summary>

因为**缓冲池是 B+ 树的运行时基础设施**。

**具体依赖**：

1. **B+ 树的节点存在磁盘页上**：一个 B+ 树节点 = 一个 `Page`（4KB）。访问节点必须先把页读进内存——这正是缓冲池的 `FetchPage`。
2. **B+ 树的操作会触发淘汰**：一次范围扫描可能访问几百个页，远超内存帧数，缓冲池必须能淘汰并回写脏页。
3. **latch 在页上**：B+ 树的 latch crabbing 是在 `Page` 对象上加读写闩锁——这个 `Page` 的并发语义由 P1 定义。
4. **脏页回写**：B+ 树的插入会修改页，页变脏，需要缓冲池在淘汰时刷盘。

**如果顺序反过来**：学生在写 B+ 树时会不断遇到「页从哪来」「页被淘汰了我的指针还有效吗」「脏页什么时候刷」这些问题，而这些问题本应由 P1 解决。

**更深层的原因**：这是数据库的**存储层次**决定的。磁盘 → 缓冲池 → 索引 → 执行 → 事务，每一层都建立在前一层之上。课程顺序 = 架构顺序。

</details>

**Q3.** 「Debug & Reasoning Check」这种考核方式，能防住哪些「作弊」？防不住什么？

<details><summary>参考答案</summary>

**能防住的**：

1. **AI 生成代码但作者不懂**：如果代码是 Copilot 写的，学生在现场看到一段有 bug 的代码时，无法快速定位——因为他不理解原始设计的意图。
2. **抄同学的代码**：抄来的代码风格与自己的思维不一致，Debug 时会「看不懂自己的代码」。
3. **试错式提交**：靠反复提交猜测隐藏测试的行为，能过测试但没有真正的理解。Debug Check 考察的是**推理过程**，不是最终答案。
4. **过拟合公开测试**：只让公开测试通过、隐藏测试崩溃的实现，在 Debug Check 中会暴露（因为 Debug Check 的代码往往是「边界条件写错」的典型）。

**防不住的**：

1. **真正理解了但用了 AI 辅助**：如果一个学生完全理解缓冲池的原理，用 AI 帮他写样板代码（`#include`、getter/setter），Debug Check 他照样能过。这种情况下「作弊」的界定本身就很模糊——这也是为什么 P3/P4 直接允许 AI + 要求 reflection。
2. **背题**：如果 Debug Check 的题目每年重复，学生可以背答案。
3. **团队协作但不申报**：两个学生私下讨论，Debug Check 时各自都能解释——无法检测。
4. **「理解」与「能写」的差距**：有些学生能看懂并解释代码，但自己写不出来。Debug Check 考的是「读 + 改」，不是「从零写」。

**教学启示**：任何考核都有漏洞。Debug Check 的价值不在于「完全防作弊」，而在于**提高作弊的成本**——让「不理解就交代码」这条路的期望收益变负。

</details>

**Q4.** 作为自学者，你无法提交 Autolab。你如何判断自己的 P1 缓冲池实现是「对的」？

<details><summary>参考答案</summary>

**四层验证策略**（从弱到强）：

1. **公开测试**：BusTub 仓库的 `test/buffer/` 目录下有公开测试（`lru_k_replacer_test.cpp`、`buffer_pool_manager_test.cpp` 等）。跑通它们是**必要条件**，不是充分条件。
   ```bash
   make buffer_pool_manager_test -j$(nproc)
   ./test/buffer_pool_manager_test
   ```

2. **自己写边界测试**：公开测试覆盖不到的地方，自己补。
   - 所有帧都被 pin 住时 `FetchPage` 应返回 `nullptr`（而不是崩溃）。
   - 同一个页被多次 `FetchPage`，`pin_count` 应正确累加。
   - 淘汰一个脏页时，`DiskManager` 应收到 `WritePage` 调用（用 mock 验证）。
   - 并发：多线程同时 `FetchPage` 同一个页，不应重复读盘（需要 latch）。

3. **Sanitizer**：用 ASAN + LSAN 跑测试，确认**无内存泄漏、无越界、无 use-after-free**。BusTub 默认开启 sanitizer，这正是官方希望你用的。
   ```bash
   cmake -DCMAKE_BUILD_TYPE=Debug ..   # 默认开 ASAN+LSAN
   ```
   另外用 **TSAN**（ThreadSanitizer）检查数据竞争——BusTub 可能不默认支持，需要手动改 CMake。

4. **压力测试 + 不变式检查**：写一个随机操作生成器（随机 Fetch/Unpin/Delete/NewPage），跑几百万次，同时**持续检查不变式**：
   - 每个 frame 的 `pin_count >= 0`。
   - 每个页在 `page_table` 中的映射与 frame 的实际内容一致。
   - 被 pin 的页永远不在 replacer 的淘汰候选里。
   - 所有帧的 `pin_count` 之和 = 所有未 Unpin 的引用数。

**「金标准」**：把缓冲池接到一个**真实负载**上——比如用 BusTub 的 B+ 树（如果 P2 已完成）跑大量插入/查找，看是否正确。这能发现单元测试覆盖不到的交互 bug。

**注意**：这些都不能保证你通过隐藏测试。隐藏测试往往覆盖**你没想过的边界**（比如「淘汰时正好有另一个线程在 pin 同一页」）。所以**代码审查**（自己逐行读，或让另一个 agent 读）是必要的补充。

</details>
