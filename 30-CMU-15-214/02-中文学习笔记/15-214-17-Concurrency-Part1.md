# 第 17 讲 并发之险（The Perils of Concurrency）

> 说明：本课程公开页面为 **2013 年秋季学期（Fall 2013）** 版本，本笔记按该版本整理（讲义由 Jonathan Aldrich 与 Charlie Garrod 编写）。

## 1. 本节学习目标

- 能解释为什么 2005 年前后处理器从「提高主频」转向「增加核心」，并用功耗公式说明原因。
- 能区分 Concurrency（并发）与 Parallelism（并行），并说明「并发是结构、并行是执行」。
- 能用 Work（功）、Depth/Span（深度/跨度）、Breadth（宽度）三个量描述一段计算，并判断应当先优化哪一个。
- 能用 Amdahl 定律（Amdahl's Law）估算给定可并行比例下的加速上限。
- 能解释 Process（进程）与 Thread（线程）在隔离性与通信成本上的差别。
- 能判断一条 Java 语句是否为原子动作（atomic action），并能说明 `i++` 为什么不是。

## 3. 核心概念

- **Concurrency（并发）**：程序中存在多个控制点（control point）——多个线程或多个进程——它们共享资源。并发不等于「同时执行」，而是「多股执行流在时间上重叠推进」。
- **Parallelism（并行）**：并发的一种特例，指多个执行流真正在同一时刻运行在不同核心上。并发是程序结构，并行是硬件执行方式。
- **Thread（线程）**：同一进程内的一条执行流。同一进程的所有线程共享堆内存与静态字段，各自拥有独立的栈与程序计数器。
- **Process（进程）**：拥有独立内存空间的执行环境。进程间只能通过消息传递（message passing / IPC）通信，隔离性好但开销大。
- **Race Condition（竞态条件）**：计算结果依赖于程序事件的先后顺序或时序的情形。同一份代码跑两次可能得到不同答案。
- **Atomic Action（原子动作）**：不可再分割的操作——要么完整发生，要么完全不发生，中间状态对其他线程不可见。
- **Work（功）**：整段计算总共需要的操作数，等于把所有并行分支串起来执行时的总步数。
- **Depth / Span（深度/跨度）**：沿着依赖链最长的那条路径所需的步数，也就是「核心无限多时最快多久跑完」。
- **Breadth（宽度）**：Work ÷ Depth，粗略表示「平均有多少事可以同时做」。
- **Amdahl's Law（阿姆达尔定律）**：若程序中比例为 F 的部分必须串行，则无论用多少核心，加速比上限是 1/F。

## 4. 通俗理解

**为什么突然要学并发？** 想象一条高速公路。过去二十年，工程师靠「把限速从 60 提到 120」来提升通行量（提高主频）。但 2005 年前后发现：限速再提，车会过热烧毁（功耗与散热墙）。于是改为「多修几条车道」（多核）。车道多了，但如果你的车队只会排成一列开，多出来的车道完全用不上——这就是「程序没有并发结构，多核也帮不了你」。

**功耗为什么会撞墙？** 处理器的动态功耗近似为

```
Power ≈ Capacitance × Voltage² × Frequency
```

- Capacitance（电容）由工艺与芯片面积决定，短期内基本固定；
- Voltage（电压）提高频率往往要同步提高电压，于是电压的平方项放大得更快；
- Frequency（频率）是主频。

三项相乘意味着频率翻倍时功耗增长远快于两倍，散热根本跟不上。所以主频停在 3–4 GHz 附近，厂商转而在一颗芯片上放 2、4、8、16 个核心。

**一个具体数字：** 假设某程序有 10% 的代码必须串行（F = 0.1），那么即便你有 1000 个核心，加速比也只有 1/0.1 = 10 倍。这就是 Amdahl 定律的威力——它把「买更多机器」这条路的收益上限钉死了。

## 5. 原理与推导

### 5.1 从「免费午餐」到「必须自己动手」

课件把处理器的发展讲成一条因果链：

1. 单核性能提升依赖频率提升；
2. 频率提升导致功耗按频率的高次方增长，散热无法承受；
3. 于是工业界转向多核（multicore）；
4. 多核只有程序本身具备并发结构时才能带来加速。

课件同时提到「破坏性创新」的三个来源以及 Metcalfe 定律（梅特卡夫定律）：网络价值约等于 n(n-1)/2，其中 n 是节点数——节点越多，连接数按平方增长。这是后面分布式系统一讲「规模带来价值」的伏笔。

### 5.2 并发在历史上的两种角色

课件强调：**过去**并发只是一种便利的抽象，例如

- GUI 事件线程：主线程画界面，后台线程算数据，界面不卡；
- 服务器为每个客户端开一条线程，天然隔离各客户端的状态；
- 生产者–消费者：一个线程产数据、一个线程消费。

这些都是「写起来方便」，不是「跑得更快」。**现在**并发变成必需：不用并发，多核硬件就浪费了。于是问题从「怎么写得舒服」变成「怎么写得对且快」。

课件列出并发带来的三大问题：

1. 如何发挥硬件的全部潜力（性能问题）；
2. 需要什么样的语言抽象来表达并发（表达力问题）；
3. 非确定性（non-determinism）：同一程序多次运行结果可能不同（正确性问题）。

### 5.3 用 Work / Depth / Breadth 给计算「量体型」

设一段计算可以画成一张依赖图（DAG）：节点是操作，边是「必须先做 A 才能做 B」的依赖。

- **Work**：所有节点数之和，即串行执行的总步数。
- **Depth（又称 Span）**：从入口到出口最长路径上的节点数。
- **Breadth**：Work ÷ Depth。

三条推论：

- 用 P 个核心的理想加速比上限为 `Work / max(Depth, Work/P)`；
- 如果 Depth 很大（依赖链很长），再多核心也没用——这正呼应 Amdahl 定律；
- 设计并行算法的原则是**先最小化 Depth，再最小化 Work**。

为什么顺序是这样？因为 Work 往往会被并行度「摊薄」，而 Depth 是硬下限：Depth 决定了「无论多少核心，至少要走这么多步」。

### 5.4 Amdahl 定律的推导

设程序总工作量归一化为 1，其中比例 F 只能串行执行，剩下 (1-F) 可以完美并行到 N 个核心。则执行时间为

```
T(N) = F + (1 - F) / N
```

串行版本（N = 1）时间为 F + (1-F) = 1，所以

```
Speedup(N) = 1 / (F + (1 - F)/N)
```

令 N → ∞，得 `Speedup → 1/F`。把 F = 0.1 代入：上限 10 倍；F = 0.05 代入：上限 20 倍。

课件进一步追问：F 本身会随问题规模 M 变化吗？很多科学计算中，串行部分（如初始化、归约收尾）增长慢于并行部分，于是**问题越大，F 越小，可扩展性越好**（这正是「强扩展性 / 弱扩展性」讨论的起点）。课件引用了 Intel 的 Doron Rajwan 关于这一点的论述。

### 5.5 进程与线程：隔离性 vs 通信成本

| 维度 | Process（进程） | Thread（线程） |
|---|---|---|
| 内存 | 独立地址空间 | 共享堆与静态区 |
| 通信 | 消息传递（IPC），需序列化 | 直接读写共享变量 |
| 隔离性 | 强，一个崩溃通常不拖垮其它 | 弱，一个线程写坏数据全体受害 |
| 开销 | 创建/切换重 | 创建/切换轻 |
| 主要风险 | 通信协议设计 | 竞态条件与数据竞争 |

课件用一句话概括：进程是「隔离的执行环境 + 消息传递」，线程是「共享的执行环境 + 共享状态」。

### 5.6 硬件的真实视图

课件给出的一张关键图：每个线程有自己的**寄存器（registers）**与**缓存（cache）**（严格说是每核心私有的一级/二级缓存），而**主内存（memory）**与部分缓存是共享的。

这带来两个后果：

- 一个线程写入的值可能停留在自己的缓存里，另一个线程读不到——这就是**可见性（visibility）**问题，第 18 讲的 `volatile` 与 happens-before 就是为解决它而生；
- 「读-改-写」这类操作在寄存器与内存之间分多步完成，因此天然不是原子的。

### 5.7 原子性：`i++` 为什么不是一步

课件把原子性定义为「不可分割、中间状态不可见」。而在字节码/机器指令层面，`i++` 实际是三步：

1. **load**：把 `i` 的值从内存读进寄存器；
2. **increment**：寄存器加一；
3. **store**：把结果写回内存。

任何两步之间都可能发生线程切换，于是出现了下面的经典交错。设静态字段 `classData` 初值为 41，两个线程各执行一次 `classData++`：

| 步骤 | 线程 A | 线程 B | 内存中的 classData |
|---|---|---|---|
| 1 | load → 41 | | 41 |
| 2 | | load → 41 | 41 |
| 3 | 41+1 = 42 | | 41 |
| 4 | | 41+1 = 42 | 41 |
| 5 | store 42 | | 42 |
| 6 | | store 42 | 42 |

结果 42，而不是期望的 43。一次自增凭空消失——这就是**丢失更新（lost update）**。

课件还对比了另一种情形：线程 A 执行 `ans = i;`，线程 B 执行 `int i = 7;`，执行前 `i` 已是 42。答案可能是 42，也可能是 7，取决于两条语句谁先完成；但**不会出现撕裂值（torn value）**，因为 Java 中 `int` 的读与写各自都是原子的。

### 5.8 64 位 long 的陷阱

课件特别指出：Java 中 64 位的 `long`（以及 `double`）的读和写**不保证原子**。若一个线程写 `10000000000`，另一个线程同时读，可能读到高 32 位来自新值、低 32 位来自旧值的混合结果（例如得到一个既不是旧值也不是新值的数）。解决办法是加 `volatile` 或用 `java.util.concurrent.atomic.AtomicLong`。

> 待核实：讲义未逐一列出 JLS 的具体条款号；按 Java 语言规范，非 volatile 的 64 位 long/double 允许分两次 32 位访问。

### 5.9 check-then-act：更隐蔽的竞态

课件用两个生活化的例子说明「先检查、后动作」的模式为何危险：

**高速公路并线**：你从后视镜看到旁边车道空着（检查），于是打方向盘（动作）。但在「看到」与「转过去」之间，另一辆车可能已经占住了那个位置。

**银行转账**：Alice 账上有 $40，她同时向 Bob 和 Bill 各付 $30。转账分三步：① 查余额是否足够；② 给对方加钱；③ 从自己账上扣钱。两个线程的交错可以是：

| 顺序 | 线程（付 Bob） | 线程（付 Bill） | Alice 余额 |
|---|---|---|---|
| 1 | ① 查余额 = 40 ≥ 30 ✓ | | 40 |
| 2 | | ① 查余额 = 40 ≥ 30 ✓ | 40 |
| 3 | ② Bob +30 | | 40 |
| 4 | | ② Bill +30 | 40 |
| 5 | ③ Alice −30 | | 10 |
| 6 | | ③ Alice −30 | −20 |

结果是 Bob 和 Bill 各拿到 $30，而 Alice 只被扣了一次 30 又欠了 20——银行凭空多付了 $30。检查与动作之间缺少原子性，是这类缺陷的共同根源。

## 6. 代码示例

### 6.1 官方课程代码

讲义 `18-concurrency-part1.pdf` 第 23 页给出 Java 并发的两个基础类型：

```java
public interface Runnable {
    void run();
}

public class Thread implements Runnable {
    Thread(Runnable r);
    void start();                     // 启动新线程，立即返回
    static void sleep(long millis);   // 当前线程休眠
    void join();                      // 等待该线程结束
    boolean isAlive();
    static Thread currentThread();
}
```

要点：`start()` 会创建新的执行流并回调 `run()`；直接调用 `run()` 只是在当前线程里普通地执行一遍，**不会**产生并发。这是初学者最常犯的错误之一。

同页还引用了示例文件 `IncrementTest.java`（讲义未给出完整源码，只给出文件名）。

讲义第 29 页给出 `StringConverter.java`：

```java
public class StringConverter {
    private Object o;

    public void set(Object o) { this.o = o; }

    public String get() {
        if (o == null) return "null";
        return o.toString();
    }
}
```

（同页另列 `Getter.java`、`Setter.java`。）这段代码的隐患在于：`get()` 先判断 `o == null`，再调用 `o.toString()`；若另一个线程在这两步之间执行 `set(null)`，第二次检查时 `o` 已为 null，于是抛出 `NullPointerException`。这就是典型的 check-then-act 竞态，第 18 讲会用它引出 `synchronized`。

### 6.2 Agent 自行编写的教学示例

> 非官方，仅用于说明概念。

下面用最短的代码复现第 5.7 节的丢失更新，并打印出「实际值」与「期望值」的差异：

```java
public class LostUpdateDemo {
    static int classData = 41;   // 共享可变状态：两个线程都会读改写

    public static void main(String[] args) throws InterruptedException {
        Runnable inc = () -> {
            for (int k = 0; k < 100_000; k++) {
                classData++;      // 不是原子操作：load / increment / store
            }
        };

        Thread t1 = new Thread(inc);
        Thread t2 = new Thread(inc);
        t1.start();               // 真正的并发从这里开始
        t2.start();
        t1.join();                // 主线程等待两条线程结束
        t2.join();

        System.out.println("期望: " + (41 + 200_000));
        System.out.println("实际: " + classData);   // 几乎总是偏小
    }
}
```

运行结果每次不同，且几乎总小于期望值——**非确定性**正是竞态条件最难对付的地方：它不可复现、不可靠测试。

## 7. 容易混淆的概念

| 概念 A | 概念 B | 关键差别 |
|---|---|---|
| Concurrency（并发） | Parallelism（并行） | 并发是「多股执行流在时间上重叠」的程序结构；并行是「同一时刻真正同时执行」的硬件事实。单核也能并发（分时切换），多核才能并行 |
| Process（进程） | Thread（线程） | 进程有独立地址空间、靠消息传递通信、隔离强开销大；线程共享堆、直接读写共享变量、隔离弱开销小 |
| Work（功） | Depth / Span（深度） | Work 是总步数（决定能耗与总吞吐）；Depth 是最长依赖链（决定最短完成时间，是加速的硬下限） |
| 原子性（Atomicity） | 可见性（Visibility） | 原子性管「中间状态会不会被看到」；可见性管「一个线程的写什么时候对别的线程生效」。`i++` 既不原子也不保证可见 |
| 竞态条件（Race Condition） | 数据竞争（Data Race） | 竞态条件是「结果依赖时序」的广义现象；数据竞争是其中一种具体成因（多线程无同步地访问同一内存且至少一个写），第 18 讲会正式定义 |

## 10. 本节复习

- 功耗 ≈ 电容 × 电压² × 频率，这三项相乘使主频提升撞上散热墙，工业界转向多核。
- 并发不是新事物，但过去只是便利抽象（GUI、服务器、生产者–消费者），现在关系到能否用满硬件。
- 用 Work、Depth、Breadth 描述并行计算；设计时先压 Depth，再压 Work。
- Amdahl 定律：串行比例 F 决定加速上限 1/F；F 可能随问题规模增大而变小。
- 线程共享堆与静态区，各有独立栈；共享是性能来源，也是缺陷来源。
- `i++` 是 load / increment / store 三步，两步之间可被切换，导致丢失更新。
- Java 中 `int` 读写原子，64 位 `long`/`double` 读写不保证原子。
- check-then-act 模式（先查后改）是竞态的高发区，检查与动作必须放在同一个原子区间内。

<summary>参考答案</summary>

**A1.** Speedup(N) = 1 / (F + (1−F)/N)。F = 0.2、N = 8：1 / (0.2 + 0.8/8) = 1 / 0.3 ≈ 3.33 倍。N → ∞ 时上限 1/0.2 = 5 倍。若 F = 0.05：N = 8 时 1 / (0.05 + 0.95/8) = 1 / 0.16875 ≈ 5.93 倍；上限 1/0.05 = 20 倍。

**A2.** Work = 1000，Depth = 50，Breadth = 1000/50 = 20。16 核心时上限为 Work / max(Depth, Work/16) = 1000 / max(50, 62.5) = 1000/62.5 = 16 倍，此时核心数仍是瓶颈；若核心增到 32，则 1000 / max(50, 31.25) = 1000/50 = 20 倍，瓶颈变成 Depth。也就是说 Depth = 50 决定绝对上限 20 倍。

**A3.** `run()` 只是普通方法调用，在当前线程的调用栈里同步执行完毕才返回，因此两条「线程」实际上串行跑在主线程上。只有 `start()` 才会向操作系统申请新线程并由它回调 `run()`。结果正确恰恰说明没有并发——一旦改为 `start()`，共享状态上的竞态就可能暴露出来。

**A4.** 都不会自动变安全，需分别看：① `classData = classData + 1` 与 `classData++` 在字节码层面等价（读、加、写），同样有丢失更新；② 加 `synchronized` 后整个方法成为临界区，互斥 + 内存可见性同时得到保证，安全（但每次自增都要抢锁，有开销）；③ `AtomicInteger.incrementAndGet()` 用 CPU 的 CAS（compare-and-swap）指令实现，无锁且原子，也安全，通常是高竞争场景的首选。

**A5.** 若「检查余额 + 扣钱」在数据库里是一条原子语句（依赖数据库的行锁或 CAS），则丢失更新消失。但仍有残留问题：① 转账的「扣一方、加另一方」两步之间若崩溃，钱会凭空消失，需要事务（transaction）保证原子性；② 两笔转账互相等待对方账户的锁可能死锁；③ 若存在多个副本，还要考虑副本间的一致性。这些正是第 25 讲「数据一致性」的主题。
